## P-001 请求幂等键与秒杀业务幂等键的职责冲突

- **日期**：2026-10-20（结论）；问题最早在轮次 2 识别
- **状态**：🚧 结论已定，02/03/04/OpenAPI 待统一修改
- **涉及模块**：秒杀（seckill）

### 背景

秒杀下单原设计同时存在两套幂等机制：

| 层 | 键 | 位置 |
|---|---|---|
| 请求级 | 客户端生成 `requestId` | 04 接口请求体、`t_seckill_order.request_id`、`uk_request_id` |
| 业务级 | `(userId, activityId)` | Redis `bought` Hash、消费端 `idem:{userId}:{activityId}`、DB `uk_user_activity` |

### 问题

`requestId` 的生效点在秒杀业务幂等**之后**：

```
① Redis Lua
   ├─ 查 bought            ← 一人一单在这里生效
   ├─ 扣库存
   └─ bought +1
   （全程不看 requestId）

② 发 MQ（消息里带 requestId）

③ 消费端
   ├─ SETNX idem:{userId}:{activityId}   ← 仍是业务键
   ├─ DB 条件扣库存
   └─ 插订单
        ├─ uk_user_activity  ← 一人一单最终兜底
        └─ uk_request_id     ← 仅“同一 requestId 重投”时多一层
```

结果是：

1. 重复请求在到达 `requestId` 之前，已经被 `bought` / `uk_user_activity` 拦截；
2. 一人一单场景下，`uk_user_activity` 已覆盖所有重复下单，`uk_request_id` 是冗余的；
3. `uk_request_id` 是全局唯一，同一个 `requestId` 跨活动复用会误伤；
4. 响应丢失时 `requestId` 也一起丢失；`activityId` 在 URL 里，反而更可靠；
5. 客户端还要额外生成 UUID、处理 `40301` 归属校验，成本大于收益。

### 历史方案演进

| 轮次 | 方案 | 结果 |
|---|---|---|
| 10 | 为区分“旧消息重投”与“新一次抢购”，订单表增加 `request_id` 唯一索引 | 当时有效，但建立在“可能多次抢购”的假设上 |
| 26 | 改为严格一人一单，`uk_user_activity` 覆盖所有重复订单 | `uk_request_id` 变为冗余 |
| 29 | 复盘 requestId 的实际生效顺序 | 确认它不是幂等键，只是追踪号 |

### 关联问题：requestId 缺少结果状态

轮次 2 还识别出：接口返回“排队中”后，若消费者最终失败，用户侧没有可查询的失败终态。后续处理：

- 订单页是最终真相源；
- 提供按 `requestId` / 按 `activityId` 的结果查询；
- 对账任务兜底“已扣库存但无订单”；
- P-001 进一步说明：MVP 可按 `activityId` 查询，`requestId` 可去掉。

### 分析

请求级幂等键真正有价值的场景是：

> **创建型操作 + 没有天然唯一键 + 重复会产生用户可见或有成本的副作用。**

秒杀不满足这个条件：`(userId, activityId)` 是天然业务唯一键，一人一单已经由它保证。因此 `requestId` 不是幂等键，最多只是“请求追踪号”。

### 结论

1. **MVP 去掉客户端 `requestId`**，保留 `uk_user_activity` 作为唯一业务幂等键；
2. 抢购结果查询改为按 `activityId`：`GET /seckill/activities/{id}/my-order`；
3. 删除 `uk_request_id`、`40301`、`GET /seckill/orders/by-request/{requestId}`；
4. 若暂不改已定稿文档，则保留 `requestId` 但明确其定位：**追踪号，不是幂等键**，不再宣传“请求幂等”；
5. N>1 / 一人多单时再引入请求级幂等键，并优先采用“一单多件”的订单模型。

### 影响文档

| 文档 | 改动 |
|---|---|
| 02 架构设计 | §5.2 删除/改写 `idem` 与 requestId 定位；§6.7 明确业务键幂等 |
| 03 数据库设计 | `t_seckill_order` 删除 `request_id` / `uk_request_id`（或保留 nullable，不做唯一键） |
| 04 接口设计 | §1.7 幂等表、§9.4 发起抢购、§9.5 查询结果；新增按活动查询我的订单 |
| OpenAPI / PRD | 同步 |

### 经验规则

| 操作类型 | 幂等手段 |
|---|---|
| 点赞 / 收藏 / 关注 | 业务唯一键 |
| 抢购 / 注册 | 业务唯一键 |
| 支付 / 审核 / 下架 / 关单 | 状态 CAS + 业务单号 |
| 编辑 | PUT 语义 + 乐观锁 |
| 删除 | DELETE 语义 |
| 发帖 / 评论 / 创建活动 | 无天然唯一键，才考虑请求级幂等键 |

## P-002 限购 N 与消费者幂等键冲突

- **日期**：2026-10-18（轮次 2；轮次 4/26 收敛）
- **状态**：✅ MVP 已解决（N=1）；N>1 为演进待办
- **涉及模块**：秒杀

### 背景

Redis Lua 预留了 `limitNum` 参数，允许多次抢购；消费端幂等键 `glimmer:seckill:idem:{userId}:{activityId}` 与 DB `uk_user_activity (user_id, activity_id)` 都等价于“一个用户一个活动只能一单”。

### 问题

当 `limitNum > 1` 时：

```
第 1 次抢购 → Lua 扣库存、bought=1 → 订单创建成功
第 2 次抢购 → Lua 判断 bought < limit，扣库存、bought=2
            → 消费者看到 idem:{userId}:{activityId} 已存在
            → 当作重复消息 ACK
            → 结果：Redis 扣了库存，但没有第二张订单
```

即 **限购数量与幂等键口径不一致**，造成“幽灵扣减”。

### 分析

- 业务键 `(userId, activityId)` 的语义是“一人一单”，与 N>1 天然冲突；
- 请求级幂等键也无法解决“一个用户同一活动多单”的订单模型问题；
- 真正的解法不是加幂等键，而是先确定订单模型。

### 结论

1. **MVP 收敛为 `limitNum = 1`、严格一人一单**；
2. N>1 不作为 MVP 范围，优先采用 **“一单多件”**（订单加 `quantity`，`uk_user_activity` 保留）；
3. 若未来必须“一人多单”，需要配额表或去掉 `uk_user_activity`，复杂度高，不推荐；
4. 对应 `bought` 计数的扩展空间保留，但不在 MVP 实现。

### 影响文档

| 文档 | 内容 |
|---|---|
| 02 §6.7.2 | 明确 MVP `limitNum=1`，N>1 需“一单多件”或配额表 |
| 03 | `uk_user_activity` 唯一键 |
| 04 §9.4 | 抢购按一人一单返回 |
| 00 演进待办 | N>1 的配额模型 |

### 经验

> 限购数量、订单模型、幂等键必须在同一张设计图上定；先定“一单多件还是多单”，再定 Redis 计数和唯一键。

## P-003 对账把在途请求误判为幽灵扣减

- **日期**：2026-10-18（轮次 2–6）
- **状态**：✅ MVP 已解决（静默期对账）；请求账本/自动回补为演进
- **涉及模块**：秒杀 / 对账

### 背景

最初的兜底思路是：比较 Redis `bought` 与订单表，找出“Redis 已扣、DB 无订单”的用户，回补库存。

### 问题

`bought` 与订单表的差集天然包含 **在途请求**：

```
刚扣减、消息还在队列
正在消费、DB 事务未提交
已建单、Redis 状态尚未更新
```

如果在运行期直接按差集回补，会把正常在途当成幽灵扣减，导致 **多放库存、最终超卖**。

### 分析

- 异步系统必须允许“在途差额”，不能要求任一时刻 Redis 与 DB 完全相等；
- `bought` 只有计数，没有 requestId / 时间戳 / 状态，无法区分“在途”和“真丢失”；
- 要做运行期自动补偿，必须引入请求级账本（pending ZSet + 每请求状态 + 时间水位），复杂度高。

### 结论

采用 **“静默期 + DB 真相”** 的 MVP 方案：

1. **运行期只读**：只做一致性检查与告警，不做破坏性自动补偿；
2. **静默期判定**：活动已结束或 `stock == 0`；订单队列 `ready=0` 且 `unacked=0`；DLQ 无堆积；距最后一笔订单创建 > `T_quiet`（5–10 分钟）；
3. **静默期动作**：
   - 对“Redis 已预占、DB 无订单”的用户，只做**重投补建订单**；
   - **库存回补不自动执行**，只告警/人工处理；
   - 以 DB 为准重建 Redis 库存与 `bought`；
4. **执行时机**：活动结束后 10 分钟第一次执行；队列未排空每 5 分钟重试，最多 30 分钟；第一次成功后 35 分钟做第二次关单补偿兜底；应用重启补跑逾期任务；不轮询；
5. 请求级账本、W1/W2/W3 水位、CAS 释放列为演进。

### 影响文档

| 文档 | 内容 |
|---|---|
| 02 §6.7.8 | 静默期判定、两次执行、只补单不回补 |
| 00 演进待办 | 请求级账本、自动库存回补 |

### 经验

> 对账的第一步不是“修复”，而是证明“现在没有在途”。运行期只读、静默期再动手，是异步系统最安全的兜底姿势。

## P-004 消费者 SETNX 命中后直接 ACK

- **日期**：2026-10-18（轮次 5）
- **状态**：✅ 已解决
- **涉及模块**：秒杀 / MQ

### 背景

消费端用 `SETNX glimmer:seckill:idem:{userId}:{activityId}` 做幂等：如果键已存在，就认为消息重复。

### 问题

如果消费者在 `SETNX` 成功后、DB 事务提交前崩溃：

```
第 1 次消费：SETNX 成功 → 扣库存 → 建单前崩溃
第 2 次消费：SETNX 失败 → 直接 ACK
→ 订单永远不会创建，形成幽灵扣减
```

`SETNX` 只能证明“开始处理过”，不能证明“处理成功”。

### 分析

消费幂等必须回查 **业务终态**，不能只依赖一个“处理中”标记；MQ 是至少一次投递，消费者必须允许重复执行。

### 结论

`SETNX` 命中后：

1. 查 DB 是否已有该用户的订单（含已关闭）；
2. 有订单 → ACK（真重复）；
3. 无订单 → 继续执行建单（上次可能崩溃在提交前）；
4. DB `uk_user_activity` 作为最终兜底；`DuplicateKeyException` → 幂等 ACK。

### 影响文档

| 文档 | 内容 |
|---|---|
| 02 §6.7.6 | 消费幂等流程 |

### 经验

> 幂等标记要区分“开始处理”和“处理成功”；消费者永远以业务终态为准，不以锁/标记为准。

## P-005 一人一单唯一键 vs 关单后重抢

- **日期**：2026-10-19（轮次 10）→ 2026-10-20（轮次 26 定稿）
- **状态**：✅ 已解决（严格一人一单）
- **涉及模块**：秒杀 / 数据库

### 背景

`uk_user_activity (user_id, activity_id)` 阻止同一用户对同一活动下第二单。产品曾考虑“订单超时关闭后，允许用户重新抢购”。

### 问题

严格唯一键与“关单后重抢”冲突：

- 若保留唯一键，关单后用户无法再抢；
- 若允许重抢，需要 `active_flag` 生成列 + `uk_user_activity_active`，只对有效订单唯一；
- 关单后释放资格，用户可反复下单占库存，再关单，形成“占库存”攻击面。

### 分析

- MVP 优先简单与防占库存；
- 未支付关单后不能再次抢购，是可接受的业务规则；
- `active_flag` 方案不是不能用，而是当前复杂度不值得；
- 若未来要支持重抢，应作为独立产品规则重新设计，而不是靠生成列临时绕过。

### 结论

1. 采用 **`uk_user_activity (user_id, activity_id)` 严格一人一单**；
2. 删除 `active_flag` 与 `uk_user_activity_active`；
3. 关单只回补库存，**不释放资格**；`bought` 关单不回落；
4. 仅“订单创建失败（DB 无订单）”时回滚库存与 `bought`，允许重试；
5. 对应 `idem` 标记在关单后保留（标记 CLOSED）。

### 影响文档

| 文档 | 内容 |
|---|---|
| 03 v1.2 | 删除 `active_flag`，使用 `uk_user_activity` |
| 02 §5.2 / §6.7 | `bought` 关单不回落；Lua 注释 |
| 04 §9.4 | 一人一单错误语义 |
| ER 图 | 同步删除 `active_flag` |

### 经验

> 唯一键是最终防线；生成列/条件唯一是“允许例外”的工具，不是默认方案。先确认业务是否真的需要例外。

## P-006 先审后发 vs 先发后审

- **日期**：2026-10-19（轮次 15 先审后发 → 轮次 18 改先发后审）
- **状态**：✅ 已解决（先发后审）
- **涉及模块**：内容 / 审核

### 背景

产品需要内容治理。最初选择“先审后发”：普通用户发帖后进入待审核，审核通过才公开。

### 问题

先审后发把审核放进发布关键路径：

- 发帖接口要等审核，体验差；
- 审核积压会阻塞发布；
- 若想改为先发后审，需要表达“已公开但待审核”的状态，且不想新增 `audit_status` 字段或表。

### 分析

- 复用现有 `status` 四态：`0=已发布·待审核`、`1=已发布`、`2=审核拒绝`、`3=已下架`；
- 公开可见条件统一为 `status IN (0,1) AND is_deleted=0`；
- 审核通过（0→1）只改状态，不重复 Feed 扩散、不重置 `published_at`；
- 审核拒绝（0→2）立即从公开列表 / Feed / 热榜 / 搜索移除；
- 下架（0/1→3）、恢复（3→1）、编辑重提（2→0）均不重置 `published_at`、不重复扩散；
- 不新增 `audit_status`，避免破坏 11 表结构。

### 结论

1. 改为 **先发后审**：普通用户发帖后立即公开并进入待审队列；管理员发帖跳过审核；
2. 状态语义按上述四态解释；
3. 发布关键路径只剩“落库 + 异步扩散/索引”；
4. 审核拒绝/下架成为内容治理关键路径。

### 影响文档

| 文档 | 内容 |
|---|---|
| PRD v1.4 | 审核规则 |
| 03 v1.1 | 状态机、`published_at`、DDL、ES 事件 |
| 04 v1.1 | 可见性、发帖、详情、编辑、重提、管理端审核 |
| 02 | Feed / 搜索同步口径 |
| 用户故事地图 / ER 图 | 同步 |

### 经验

> 状态字段可以复用，但语义必须写死；审核应是治理关键路径，不应成为发布关键路径。

## P-007 MySQL 8.0 vs 5.7

- **日期**：2026-10-19（轮次 13）
- **状态**：✅ 已解决（MySQL 8.0）
- **涉及模块**：数据库 / 部署

### 背景

项目需要确定 MySQL 版本；5.7 已于 2023-10 EOL，8.0 是当前稳定选择。

### 问题

- 5.7 已停止维护，不应作为新项目选择；
- 8.0 默认 `caching_sha2_password`，旧驱动/Navicat 可能报 `Public Key Retrieval is not allowed` 或 `Authentication plugin ... cannot be loaded`；
- 需要明确本地与生产的认证配置。

### 分析

- 8.0 默认 `utf8mb4`、CHECK 约束生效、支持 CTE/窗口函数；
- 与 Spring Boot 3 + `mysql-connector-j` 8.x 匹配；
- 本项目的 11 张表在 5.7 上也能跑，因此不是“非 8 不可”，而是没有理由选已 EOL 的版本；
- `mysql_native_password` 在 8.0.34 起废弃、8.4 默认禁用、9.0 移除，不作为正式方案。

### 结论

1. 使用 **MySQL 8.0**；
2. 驱动使用 `com.mysql:mysql-connector-j` 8.x；
3. 本地 JDBC 加 `allowPublicKeyRetrieval=true&sslMode=DISABLED`，生产启用 TLS；

## P-008 搜索 FULLTEXT vs ES

- **日期**：2026-10-19（轮次 16）
- **状态**：✅ 已解决（ES 8 + IK）
- **涉及模块**：搜索 / 内容

### 背景

搜索方案有三个候选：

1. MySQL FULLTEXT + ngram；
2. 仅标签/前缀匹配；
3. Elasticsearch 8 + IK 中文分词。

### 问题

- FULLTEXT 中文分词与相关性较弱，复杂查询能力有限；
- 仅标签/前缀召回率低，不像“搜索”；
- ES 增加一个中间件、运维成本与一致性负担；
- 需要明确 ES 与 MySQL 的职责边界、同步与降级。

### 分析

- 项目目标包含搜索能力展示，ES 的分词/相关性/扩展性更合适；
- MySQL 仍是真相源，ES 是可全量重建的派生索引；
- 一致性用 MQ 事件 + 5 分钟增量补偿 + 全量重建（别名切换）；
- ES 故障时搜索降级为热榜/最新，标记 `degraded=true`，不影响主链路。

### 结论

1. 采用 **Elasticsearch 8 + IK 8**；
2. MySQL 不建全文索引；
3. ES 只存公开可见帖子的搜索字段，作为派生索引；
4. 同步/补偿/重建/降级四件套写入 02 §6.12；
5. 版本必须与 IK 对齐，Compose 中固定 8.15.x。

### 影响文档

| 文档 | 内容 |
|---|---|
| 02 §6.12 | 索引结构、MQ 同步、回表、补偿、重建、降级 |
| 03 附录 A | ES mapping、DSL、同步事件 |
| PRD v1.3 | F-08 改为 ES |
| ADR-017 | ES + IK |

### 经验

> 引入派生索引前，先想清楚三件事：能否全量重建、增量如何补偿、故障如何降级。想不清楚就不要引入。

## P-010 鉴权默认放行 vs 默认拒绝

- **日期**：2026-10-19（轮次 19）
- **状态**：✅ 已解决（fail-closed）
- **涉及模块**：认证 / 安全

### 背景

最初考虑逐接口加 `@RequireLogin` / `@RequireRole` / `@OptionalAuth` 注解。

### 问题

注解方案是“默认放行、手动收紧”：

- 新增接口忘记加注解，就会意外公开数据；
- 与项目“userId 必须来自 JWT”的安全红线冲突；
- 管理端接口分散，容易漏配角色校验。

### 分析

- 需要 fail-closed：默认要求登录，只有白名单免登录；
- 白名单按“方法 + 路径”精确匹配，不用 `/auth/**` 通配；
- 管理端按 `/api/v1/admin/**` 前缀统一校验 `role=ADMIN`；
- 公开接口可选携带 Token，合法则注入 `UserContext`；
- 资源归属（作者本人/订单所有者）在 Service 层按 JWT `userId` 校验。

### 结论

1. `/api/v1/**` 默认全部要求登录；
2. 仅白名单免登录，`AuthInterceptor` 集中鉴权；
3. 管理端路径前缀校验角色；
4. CORS `OPTIONS` 放行；`/uploads/**` 不走 API 拦截器；WebSocket 握手单独校验 JWT；
5. 取消逐接口注解方案。

### 影响文档

| 文档 | 内容 |
|---|---|
| 02 §6.10.1 / §6.10.2 | 鉴权与白名单 |
| 04 §1.3 | 认证与鉴权规则 |

### 经验

> 安全默认值必须是 fail-closed；白名单比黑名单安全；不要用通配路径放行整个模块。

## P-011 限流维度 IP vs 用户

- **日期**：2026-10-20（轮次 20 → 轮次 23 收敛）
- **状态**：✅ 已解决（纯用户/手机号小时额度）
- **涉及模块**：限流 / 安全

### 背景

初版设计为“核心四类 + 全站 IP 100 QPS 兜底”：

- 验证码：手机号 1 次/60 秒、5 次/小时；IP 100 次/小时；
- 登录：手机号 + IP 10 次/小时；
- 抢购：用户 1 次/秒；
- AI：用户 20 次/小时；
- 全站：单 IP 100 QPS。

### 问题

- NAT 下同一出口的正常用户会被 IP 限流误伤；
- 依赖 `X-Forwarded-For` 还要处理代理信任问题；
- MVP 使用本地 Mock 验证码，没有真实短信费用；
- 逐接口限流维护成本高，容易误伤正常用户。

### 分析

- 限流是“防刷 / 控成本 / 保库存”工具，不是每个接口的标配；
- 抢购正确性由库存/限购 Lua 保证，限流只承担防脚本；
- 非关键写入链路依靠登录校验、唯一约束、幂等、分页与容量控制；
- 抢购不做活动级全局限流，避免活动开始瞬间整体挡掉正常用户。

### 结论

1. **只保留四类限流**，全部按手机号/用户的小时额度：
   - 验证码：同一手机号 5 次/小时；
   - 登录：同一手机号 10 次/小时；
   - 抢购：同一用户 10 次/小时；
   - AI：同一用户 20 次/小时，同时 1 条流；
2. 删除 IP 维度与全站 IP 兜底；
3. 前端保留 60 秒重发倒计时，服务端只校验小时额度；
4. 非关键接口不单独限流；
5. 公网部署或接真实短信时，在 Nginx 层补 `limit_req` / `limit_conn`，不进入业务代码。

### 影响文档

| 文档 | 内容 |
|---|---|
| 02 §6.10.3 | 限流表与实现方式 |
| 04 §1.9 | 限流说明与 42901 |
| ADR-019 | 限流策略 |

### 经验

> 限流键要选“不会被共享出口误伤”的维度；先保证正确性（库存/唯一键），再谈防刷。

## P-012 PageHelper vs MyBatis-Plus 分页插件

- **日期**：2026-10-20（轮次 21）
- **状态**：✅ 已解决
- **涉及模块**：持久层 / 接口

### 背景

项目同时有两种分页：

- 用户端 Feed / 搜索 / 评论 / 收藏：游标分页；
- 管理端列表：页码分页。

MyBatis-Plus 自带 `PaginationInnerInterceptor`，PageHelper 也有自己的分页拦截器。

### 问题

- 两个分页插件同时存在会重复改写 SQL；
- PageHelper 的 `startPage` 使用 ThreadLocal，后面必须紧跟目标查询，否则会污染下一次查询；
- 游标分页与页码分页的 DTO、SQL、索引策略不同，混用容易出错。

### 分析

- 一个项目只保留一套分页拦截器；
- 管理端页码分页用 PageHelper，用户端游标分页手写 SQL；
- 不注册 MyBatis-Plus 的 `PaginationInnerInterceptor`；
- `reasonable=false`、`pageSizeZero=false`，分页参数由 DTO 校验；
- `startPage` 后必须立即执行目标查询。

### 结论

1. PageHelper **仅用于管理端页码分页**；
2. 用户端 Feed / 搜索 / 评论 / 收藏使用游标分页，不经过 PageHelper；
3. 不注册 MyBatis-Plus 分页拦截器；
4. 两类分页 DTO 分离命名：`PageQuery/PageResult`、`CursorQuery/CursorPage`。

### 影响文档

| 文档 | 内容 |
|---|---|
| 02 §4.2.2 | PageHelper 实现与边界 |
| ADR-018 | 分页方案 |

### 经验

> 分页插件只能留一套；游标分页不要交给页码插件，否则 SQL 和索引都会被带偏。

## P-013 弹幕 ACK / 乐观渲染

- **日期**：2026-10-20（轮次 22 → 轮次 25 定稿）
- **状态**：✅ 已解决（不做 ACK）
- **涉及模块**：弹幕 / WebSocket

### 背景

客户端发送 `SEND` 帧时带 `clientMsgId`，原设计标注为“用于前端去重”；服务端广播 `DANMAKU` 帧时没有回传该字段。

### 问题

- 发送者无法把本地乐观消息与服务端广播对应起来；
- 若做乐观渲染，需要 ACK 帧 `{type:"ACK", clientMsgId, messageId}` 或让 `DANMAKU` 回显 `clientMsgId`；
- 未知客户端 `type` 没有错误码，客户端无法区分“不支持”与“内容错误”。

### 分析

- ACK、临时 ID 映射、失败回滚只在“乐观渲染”时才需要；
- MVP 可以不做乐观渲染：服务端广播给房间内所有人（包括发送者），客户端收到后再统一渲染；
- 这样所有客户端看到的顺序、内容、`messageId` 完全一致，省掉 ACK 和本地对账；
- `clientMsgId` 仍可用于日志排查/重试去重，但不是协议关键字段。

### 结论

1. **不做乐观渲染**；
2. **不引入 ACK 帧**；
3. 服务端广播 `DANMAKU` 给所有人（含发送者），客户端收到后渲染；
4. `clientMsgId` 降级为可选字段；
5. 新增 `UNSUPPORTED_TYPE` 错误码；连接保持，连续大量非法帧可按滥用关闭。

### 影响文档

| 文档 | 内容 |
|---|---|
| 04 v1.5 §7.2 / §7.3 / §7.4 | 客户端帧、错误码、边界 |

### 经验

> 协议复杂度应跟随产品交互；不做乐观 UI 就不要引入 ACK。先定“谁来保证顺序”，再定帧。

## P-014 封禁即时生效且不查库

- **日期**：2026-10-20（轮次 26 / 28）
- **状态**：✅ 已解决
- **涉及模块**：认证 / 用户

### 背景

用户被封禁后，已签发的 JWT 仍在有效期内（7 天）；不能为了封禁在每个请求上查 `t_user.status`。

### 问题

- 如何让封禁立即生效？
- 旧 Token 应该返回什么错误？
- 重新登录时如何提示“账号已被封禁”？
- 登出与封禁的语义如何区分？

### 分析

- Redis 白名单 `glimmer:user:token:{userId}` 是 Token 有效性的真相源；
- 封禁时删除该 Token，旧 Token 后续请求查不到/不匹配 → `40101`；
- 登录时校验 `t_user.status=1`，返回 `40302`；
- 登出只删除 Token，不修改 `t_user.status`；
- 不引入 Refresh Token / `jti`，7 天到期重新登录。

### 结论

1. **封禁 = 删 Token + 登录拦截**；
2. 旧 Token → `40101`；重新登录 → `40302`；
3. 登出 ≠ 封禁；登出只结束当前会话；
4. 不在每个请求上查用户状态；
5. JWT 载荷保持 `userId / role / iat / exp`。

### 影响文档

| 文档 | 内容 |
|---|---|
| 02 §6.10.1 | 登录态与封禁 |
| 04 §1.3.1 / §3.3 | 封禁语义、登出 |

### 经验

> 会话失效与账号状态分开；用 Redis 白名单做主动失效，避免每请求查库。

## P-015 编辑已发布帖子 vs 审核绕过

- **日期**：2026-10-20（轮次 26）
- **状态**：✅ 已解决
- **涉及模块**：内容 / 审核

### 背景

作者希望编辑已发布、待审核、被拒绝的帖子；但编辑可能绕过审核，或与正在进行的审核并发。

### 问题

- 哪些状态允许编辑？
- 编辑后是否重新审核？
- 是否重置 `published_at`、是否重复 Feed 写扩散？
- 审核期间作者编辑，管理端以哪版内容为准？
- 已下架帖子是否允许编辑？

### 分析

- `status=0/1/2` 都允许作者编辑；
- 编辑后统一回到 `0`（已发布待审核），清空 `audit_*`，重新入审；
- 原状态 1/2 编辑后立即重新公开，原状态 0 保持公开；
- 不重置 `published_at`、不重复 Feed 写扩散；
- `status=3` 已下架不可编辑，避免绕过治理；
- `resubmit` 保留为“不修改内容直接重新提交”；
- 审核期间编辑以最新内容为准，管理端审核前应刷新详情。

### 结论

1. 编辑即重新提交：0/1/2 → 0；
2. 清除审核字段，重新入审；
3. 不重置 `published_at`、不重复扩散；
4. 3 已下架不可编辑；
5. 管理端审核前刷新详情。

### 影响文档

| 文档 | 内容 |
|---|---|
| 04 §5.4 / §5.6 | 编辑、直接重提 |
| 03 v1.2 | 编辑事务、状态机 |
| PRD v1.5 | 编辑规则 |

### 经验

> 编辑和审核共用状态机；所有可能绕过治理的入口都要显式封死，不能只靠前端隐藏按钮。
