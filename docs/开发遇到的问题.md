## P-001 请求幂等键与秒杀业务幂等键的职责冲突

- **日期**：2026-10-20（结论）；问题最早在轮次 2 识别
- **状态**：✅ 已解决（2026-10-20），02/03/04/OpenAPI 已统一
- **涉及模块**：秒杀（seckill）

### 背景

秒杀下单原设计同时存在两套幂等机制：

| 层 | 键 | 位置 |
|---|---|---|
| 请求级 | 客户端生成 `requestId` | 04 接口请求体、`t_seckill_order.request_id`、`uk_request_id` |
| 业务级 | `(userId, activityId)` | Redis `bought` Hash、消费端 `idem:{userId}:{activityId}`、DB `uk_user_activity` |

### 问题

`requestId` 的生效点在秒杀业务幂等**之后**：

```
① Redis Lua
   ├─ 查 bought            ← 一人一单在这里生效
   ├─ 扣库存
   └─ bought +1
   （全程不看 requestId）

② 发 MQ（消息里带 requestId）

③ 消费端
   ├─ SETNX idem:{userId}:{activityId}   ← 仍是业务键
   ├─ DB 条件扣库存
   └─ 插订单
        ├─ uk_user_activity  ← 一人一单最终兜底
        └─ uk_request_id     ← 仅“同一 requestId 重投”时多一层
```

结果是：

1. 重复请求在到达 `requestId` 之前，已经被 `bought` / `uk_user_activity` 拦截；
2. 一人一单场景下，`uk_user_activity` 已覆盖所有重复下单，`uk_request_id` 是冗余的；
3. `uk_request_id` 是全局唯一，同一个 `requestId` 跨活动复用会误伤；
4. 响应丢失时 `requestId` 也一起丢失；`activityId` 在 URL 里，反而更可靠；
5. 客户端还要额外生成 UUID、处理 `40301` 归属校验，成本大于收益。

### 历史方案演进

| 轮次 | 方案 | 结果 |
|---|---|---|
| 10 | 为区分“旧消息重投”与“新一次抢购”，订单表增加 `request_id` 唯一索引 | 当时有效，但建立在“可能多次抢购”的假设上 |
| 26 | 改为严格一人一单，`uk_user_activity` 覆盖所有重复订单 | `uk_request_id` 变为冗余 |
| 29 | 复盘 requestId 的实际生效顺序 | 确认它不是幂等键，只是追踪号 |

### 关联问题：requestId 缺少结果状态

轮次 2 还识别出：接口返回“排队中”后，若消费者最终失败，用户侧没有可查询的失败终态。后续处理：

- 订单页是最终真相源；
- 提供按 `requestId` / 按 `activityId` 的结果查询；
- 对账任务兜底“已扣库存但无订单”；
- P-001 进一步说明：MVP 可按 `activityId` 查询，`requestId` 可去掉。

### 分析

请求级幂等键真正有价值的场景是：

> **创建型操作 + 没有天然唯一键 + 重复会产生用户可见或有成本的副作用。**

秒杀不满足这个条件：`(userId, activityId)` 是天然业务唯一键，一人一单已经由它保证。因此 `requestId` 不是幂等键，最多只是“请求追踪号”。

### 结论

1. **MVP 去掉客户端 `requestId`**，保留 `uk_user_activity` 作为唯一业务幂等键；
2. 抢购结果查询改为按 `activityId`：`GET /seckill/activities/{id}/my-order`；
3. 删除 `uk_request_id`、`40301`、`GET /seckill/orders/by-request/{requestId}`；
4. 失败不持久化为查询状态：消费者回滚 Redis 库存与 `bought`，用户回到 `NOT_PARTICIPATED`，可重新抢购；
5. N>1 / 一人多单时再引入请求级幂等键，并优先采用“一单多件”的订单模型。

> **2026-10-20 确认**：按上述方案执行。秒杀幂等只保留 Redis `bought` / `idem:{userId}:{activityId}` + MySQL `uk_user_activity`；发帖/评论的 `Idempotency-Key` 另行讨论，暂缓落地。
>
> **2026-10-20 落地**：02 §5.2 / §6.7 已去掉 `requestId`；03 → v1.3，删除 `t_seckill_order.request_id` / `uk_request_id` 并重生成 ER 图；04 → v1.7，新增 `GET /seckill/activities/{activityId}/my-order`，移除 `by-request` 与秒杀场景的 `40301`；OpenAPI → 1.7.0，54 条路径 / 69 个 Schema，JSON 与 `$ref` 校验通过。

|---|---|---|
| 02 架构设计 | §5.2 `idem` 定位；§6.7 流程 / 消息 / 关单 / 对账 / JMeter | ✅ |
| 03 数据库设计 | `t_seckill_order` 删除 `request_id` / `uk_request_id`；ER 图重生成 | ✅ v1.3 |
| 04 接口设计 | §1.7 幂等表、§9.4 发起抢购、§9.5 查询结果、§11.2 / §12.3 / §13 | ✅ v1.7 |

### 经验规则

| 操作类型 | 幂等手段 |
|---|---|
| 点赞 / 收藏 / 关注 | 业务唯一键 |
| 抢购 / 注册 | 业务唯一键 |
| 支付 / 审核 / 下架 / 关单 | 状态 CAS + 业务单号 |
| 编辑 | PUT 语义 + 乐观锁 |

| 发帖 / 评论 / 创建活动 | 无天然唯一键，才考虑请求级幂等键 |

## P-002 限购 N 与消费者幂等键冲突

- **日期**：2026-10-18（轮次 2；轮次 4/26 收敛）
- **状态**：✅ MVP 已解决（N=1）；N>1 为演进待办
- **涉及模块**：秒杀

### 背景

Redis Lua 预留了 `limitNum` 参数，允许多次抢购；消费端幂等键 `glimmer:seckill:idem:{userId}:{activityId}` 与 DB `uk_user_activity (user_id, activity_id)` 都等价于“一个用户一个活动只能一单”。

### 问题

当 `limitNum > 1` 时：

```
第 1 次抢购 → Lua 扣库存、bought=1 → 订单创建成功
第 2 次抢购 → Lua 判断 bought < limit，扣库存、bought=2
            → 消费者看到 idem:{userId}:{activityId} 已存在
            → 当作重复消息 ACK
            → 结果：Redis 扣了库存，但没有第二张订单
```

即 **限购数量与幂等键口径不一致**，造成“幽灵扣减”。

### 分析

- 业务键 `(userId, activityId)` 的语义是“一人一单”，与 N>1 天然冲突；
- 请求级幂等键也无法解决“一个用户同一活动多单”的订单模型问题；
- 真正的解法不是加幂等键，而是先确定订单模型。

### 结论

1. **MVP 收敛为 `limitNum = 1`、严格一人一单**；
2. N>1 不作为 MVP 范围，优先采用 **“一单多件”**（订单加 `quantity`，`uk_user_activity` 保留）；
3. 若未来必须“一人多单”，需要配额表或去掉 `uk_user_activity`，复杂度高，不推荐；
4. 对应 `bought` 计数的扩展空间保留，但不在 MVP 实现。

### 影响文档

| 文档 | 内容 |
|---|---|
| 02 §6.7.2 | 明确 MVP `limitNum=1`，N>1 需“一单多件”或配额表 |
| 03 | `uk_user_activity` 唯一键 |
| 04 §9.4 | 抢购按一人一单返回 |
| 00 演进待办 | N>1 的配额模型 |

### 经验

> 限购数量、订单模型、幂等键必须在同一张设计图上定；先定“一单多件还是多单”，再定 Redis 计数和唯一键。

## P-003 对账把在途请求误判为幽灵扣减

- **日期**：2026-10-18（轮次 2–6）
- **状态**：✅ MVP 已解决（静默期对账）；请求账本/自动回补为演进
- **涉及模块**：秒杀 / 对账

### 背景

最初的兜底思路是：比较 Redis `bought` 与订单表，找出“Redis 已扣、DB 无订单”的用户，回补库存。

### 问题

`bought` 与订单表的差集天然包含 **在途请求**：

```
刚扣减、消息还在队列
正在消费、DB 事务未提交
已建单、Redis 状态尚未更新
```

如果在运行期直接按差集回补，会把正常在途当成幽灵扣减，导致 **多放库存、最终超卖**。

### 分析

- 异步系统必须允许“在途差额”，不能要求任一时刻 Redis 与 DB 完全相等；
- `bought` 只有计数，没有 requestId / 时间戳 / 状态，无法区分“在途”和“真丢失”；
- 要做运行期自动补偿，必须引入请求级账本（pending ZSet + 每请求状态 + 时间水位），复杂度高。

### 结论

采用 **“静默期 + DB 真相”** 的 MVP 方案：

1. **运行期只读**：只做一致性检查与告警，不做破坏性自动补偿；
2. **静默期判定**：活动已结束或 `stock == 0`；订单队列 `ready=0` 且 `unacked=0`；DLQ 无堆积；距最后一笔订单创建 > `T_quiet`（5–10 分钟）；
3. **静默期动作**：
   - 对“Redis 已预占、DB 无订单”的用户，只做**重投补建订单**；
   - **库存回补不自动执行**，只告警/人工处理；
   - 以 DB 为准重建 Redis 库存与 `bought`；
4. **执行时机**：活动结束后 10 分钟第一次执行；队列未排空每 5 分钟重试，最多 30 分钟；第一次成功后 35 分钟做第二次关单补偿兜底；应用重启补跑逾期任务；不轮询；
5. 请求级账本、W1/W2/W3 水位、CAS 释放列为演进。

### 影响文档

| 文档 | 内容 |
|---|---|
| 02 §6.7.8 | 静默期判定、两次执行、只补单不回补 |
| 00 演进待办 | 请求级账本、自动库存回补 |

### 经验

> 对账的第一步不是“修复”，而是证明“现在没有在途”。运行期只读、静默期再动手，是异步系统最安全的兜底姿势。

## P-004 消费者 SETNX 命中后直接 ACK

- **日期**：2026-10-18（轮次 5）
- **状态**：✅ 已解决
- **涉及模块**：秒杀 / MQ

### 背景

消费端用 `SETNX glimmer:seckill:idem:{userId}:{activityId}` 做幂等：如果键已存在，就认为消息重复。

### 问题

如果消费者在 `SETNX` 成功后、DB 事务提交前崩溃：

```
第 1 次消费：SETNX 成功 → 扣库存 → 建单前崩溃
第 2 次消费：SETNX 失败 → 直接 ACK
→ 订单永远不会创建，形成幽灵扣减
```

`SETNX` 只能证明“开始处理过”，不能证明“处理成功”。

### 分析

消费幂等必须回查 **业务终态**，不能只依赖一个“处理中”标记；MQ 是至少一次投递，消费者必须允许重复执行。

### 结论

`SETNX` 命中后：

1. 查 DB 是否已有该用户的订单（含已关闭）；
2. 有订单 → ACK（真重复）；
3. 无订单 → 继续执行建单（上次可能崩溃在提交前）；
4. DB `uk_user_activity` 作为最终兜底；`DuplicateKeyException` → 幂等 ACK。

### 影响文档

| 文档 | 内容 |
|---|---|
| 02 §6.7.6 | 消费幂等流程 |

### 经验

> 幂等标记要区分“开始处理”和“处理成功”；消费者永远以业务终态为准，不以锁/标记为准。

## P-005 一人一单唯一键 vs 关单后重抢

- **日期**：2026-10-19（轮次 10）→ 2026-10-20（轮次 26 定稿）
- **状态**：✅ 已解决（严格一人一单）
- **涉及模块**：秒杀 / 数据库

### 背景

`uk_user_activity (user_id, activity_id)` 阻止同一用户对同一活动下第二单。产品曾考虑“订单超时关闭后，允许用户重新抢购”。

### 问题

严格唯一键与“关单后重抢”冲突：

- 若保留唯一键，关单后用户无法再抢；
- 若允许重抢，需要 `active_flag` 生成列 + `uk_user_activity_active`，只对有效订单唯一；
- 关单后释放资格，用户可反复下单占库存，再关单，形成“占库存”攻击面。

### 分析

- MVP 优先简单与防占库存；
- 未支付关单后不能再次抢购，是可接受的业务规则；
- `active_flag` 方案不是不能用，而是当前复杂度不值得；
- 若未来要支持重抢，应作为独立产品规则重新设计，而不是靠生成列临时绕过。

### 结论

1. 采用 **`uk_user_activity (user_id, activity_id)` 严格一人一单**；
2. 删除 `active_flag` 与 `uk_user_activity_active`；
3. 关单只回补库存，**不释放资格**；`bought` 关单不回落；
4. 仅“订单创建失败（DB 无订单）”时回滚库存与 `bought`，允许重试；
5. 对应 `idem` 标记在关单后保留（标记 CLOSED）。

### 影响文档

| 文档 | 内容 |
|---|---|
| 03 v1.2 | 删除 `active_flag`，使用 `uk_user_activity` |
| 02 §5.2 / §6.7 | `bought` 关单不回落；Lua 注释 |
| 04 §9.4 | 一人一单错误语义 |
| ER 图 | 同步删除 `active_flag` |

### 经验

> 唯一键是最终防线；生成列/条件唯一是“允许例外”的工具，不是默认方案。先确认业务是否真的需要例外。

## P-006 先审后发 vs 先发后审

- **日期**：2026-10-19（轮次 15 先审后发 → 轮次 18 改先发后审）
- **状态**：✅ 已解决（先发后审）
- **涉及模块**：内容 / 审核

### 背景

产品需要内容治理。最初选择“先审后发”：普通用户发帖后进入待审核，审核通过才公开。

### 问题

先审后发把审核放进发布关键路径：

- 发帖接口要等审核，体验差；
- 审核积压会阻塞发布；
- 若想改为先发后审，需要表达“已公开但待审核”的状态，且不想新增 `audit_status` 字段或表。

### 分析

- 复用现有 `status` 四态：`0=已发布·待审核`、`1=已发布`、`2=审核拒绝`、`3=已下架`；
- 公开可见条件统一为 `status IN (0,1) AND is_deleted=0`；
- 审核通过（0→1）只改状态，不重复 Feed 扩散、不重置 `published_at`；
- 审核拒绝（0→2）立即从公开列表 / Feed / 热榜 / 搜索移除；
- 下架（0/1→3）、恢复（3→1）、编辑重提（2→0）均不重置 `published_at`、不重复扩散；
- 不新增 `audit_status`，避免破坏 11 表结构。

### 结论

1. 改为 **先发后审**：普通用户发帖后立即公开并进入待审队列；管理员发帖跳过审核；
2. 状态语义按上述四态解释；
3. 发布关键路径只剩“落库 + 异步扩散/索引”；
4. 审核拒绝/下架成为内容治理关键路径。

### 影响文档

| 文档 | 内容 |
|---|---|
| PRD v1.4 | 审核规则 |
| 03 v1.1 | 状态机、`published_at`、DDL、ES 事件 |
| 04 v1.1 | 可见性、发帖、详情、编辑、重提、管理端审核 |
| 02 | Feed / 搜索同步口径 |

### 经验

- **涉及模块**：搜索 / 内容

### 背景

搜索方案有三个候选：

1. MySQL FULLTEXT + ngram；
2. 仅标签/前缀匹配；
3. Elasticsearch 8 + IK 中文分词。

- FULLTEXT 中文分词与相关性较弱，复杂查询能力有限；

## P-010 鉴权默认放行 vs 默认拒绝

- **日期**：2026-10-19（轮次 19）
- **状态**：✅ 已解决（fail-closed）
- **涉及模块**：认证 / 安全

### 背景

最初考虑逐接口加 `@RequireLogin` / `@RequireRole` / `@OptionalAuth` 注解。

### 问题

注解方案是“默认放行、手动收紧”：

- 新增接口忘记加注解，就会意外公开数据；
- 与项目“userId 必须来自 JWT”的安全红线冲突；
- 管理端接口分散，容易漏配角色校验。

### 分析

- 需要 fail-closed：默认要求登录，只有白名单免登录；
- 白名单按“方法 + 路径”精确匹配，不用 `/auth/**` 通配；
- 管理端按 `/api/v1/admin/**` 前缀统一校验 `role=ADMIN`；
- 公开接口可选携带 Token，合法则注入 `UserContext`；
- 资源归属（作者本人/订单所有者）在 Service 层按 JWT `userId` 校验。

### 结论

1. `/api/v1/**` 默认全部要求登录；
2. 仅白名单免登录，`AuthInterceptor` 集中鉴权；
3. 管理端路径前缀校验角色；
4. CORS `OPTIONS` 放行；`/uploads/**` 不走 API 拦截器；WebSocket 握手单独校验 JWT；
5. 取消逐接口注解方案。

|---|---|
| 02 §6.10.1 / §6.10.2 | 鉴权与白名单 |
| 04 §1.3 | 认证与鉴权规则 |

### 经验

> 安全默认值必须是 fail-closed；白名单比黑名单安全；不要用通配路径放行整个模块。

## P-011 限流维度 IP vs 用户

- **日期**：2026-10-20（轮次 20 → 轮次 23 收敛）
- **状态**：✅ 已解决（纯用户/手机号小时额度）
- **涉及模块**：限流 / 安全

### 背景

初版设计为“核心四类 + 全站 IP 100 QPS 兜底”：

- 验证码：手机号 1 次/60 秒、5 次/小时；IP 100 次/小时；
- 登录：手机号 + IP 10 次/小时；
- 抢购：用户 1 次/秒；
- AI：用户 20 次/小时；
- 全站：单 IP 100 QPS。

### 问题

- NAT 下同一出口的正常用户会被 IP 限流误伤；
- 依赖 `X-Forwarded-For` 还要处理代理信任问题；
- MVP 使用本地 Mock 验证码，没有真实短信费用；
- 逐接口限流维护成本高，容易误伤正常用户。

### 分析

- 限流是“防刷 / 控成本 / 保库存”工具，不是每个接口的标配；
- 抢购正确性由库存/限购 Lua 保证，限流只承担防脚本；
- 非关键写入链路依靠登录校验、唯一约束、幂等、分页与容量控制；
- 抢购不做活动级全局限流，避免活动开始瞬间整体挡掉正常用户。

### 结论

1. **只保留四类限流**，全部按手机号/用户的小时额度：
   - 验证码：同一手机号 5 次/小时；
   - 登录：同一手机号 10 次/小时；
   - 抢购：同一用户 10 次/小时；
   - AI：同一用户 20 次/小时，同时 1 条流；
2. 删除 IP 维度与全站 IP 兜底；
3. 前端保留 60 秒重发倒计时，服务端只校验小时额度；
4. 非关键接口不单独限流；
5. 公网部署或接真实短信时，在 Nginx 层补 `limit_req` / `limit_conn`，不进入业务代码。

### 影响文档

| 文档 | 内容 |
|---|---|
| 02 §6.10.3 | 限流表与实现方式 |
| 04 §1.9 | 限流说明与 42901 |
| ADR-019 | 限流策略 |

### 经验

> 限流键要选“不会被共享出口误伤”的维度；先保证正确性（库存/唯一键），再谈防刷。

## P-012 PageHelper vs MyBatis-Plus 分页插件

- **日期**：2026-10-20（轮次 21）
- **状态**：✅ 已解决
- **涉及模块**：持久层 / 接口

### 背景

项目同时有两种分页：

- 用户端 Feed / 搜索 / 评论 / 收藏：游标分页；
- 管理端列表：页码分页。

MyBatis-Plus 自带 `PaginationInnerInterceptor`，PageHelper 也有自己的分页拦截器。

### 问题

- 两个分页插件同时存在会重复改写 SQL；
- PageHelper 的 `startPage` 使用 ThreadLocal，后面必须紧跟目标查询，否则会污染下一次查询；
- 游标分页与页码分页的 DTO、SQL、索引策略不同，混用容易出错。

### 分析

- 一个项目只保留一套分页拦截器；
- 管理端页码分页用 PageHelper，用户端游标分页手写 SQL；
- 不注册 MyBatis-Plus 的 `PaginationInnerInterceptor`；
- `reasonable=false`、`pageSizeZero=false`，分页参数由 DTO 校验；
- `startPage` 后必须立即执行目标查询。

### 结论

1. PageHelper **仅用于管理端页码分页**；
2. 用户端 Feed / 搜索 / 评论 / 收藏使用游标分页，不经过 PageHelper；
3. 不注册 MyBatis-Plus 分页拦截器；
4. 两类分页 DTO 分离命名：`PageQuery/PageResult`、`CursorQuery/CursorPage`。

### 影响文档

| 文档 | 内容 |
|---|---|
| 02 §4.2.2 | PageHelper 实现与边界 |
| ADR-018 | 分页方案 |

### 经验

> 分页插件只能留一套；游标分页不要交给页码插件，否则 SQL 和索引都会被带偏。

## P-013 弹幕 ACK / 乐观渲染

- **日期**：2026-10-20（轮次 22 → 轮次 25 定稿）
- **状态**：✅ 已解决（不做 ACK）
- **涉及模块**：弹幕 / WebSocket

### 背景

客户端发送 `SEND` 帧时带 `clientMsgId`，原设计标注为“用于前端去重”；服务端广播 `DANMAKU` 帧时没有回传该字段。

### 问题

- 发送者无法把本地乐观消息与服务端广播对应起来；
- 若做乐观渲染，需要 ACK 帧 `{type:"ACK", clientMsgId, messageId}` 或让 `DANMAKU` 回显 `clientMsgId`；
- 未知客户端 `type` 没有错误码，客户端无法区分“不支持”与“内容错误”。

### 分析

- ACK、临时 ID 映射、失败回滚只在“乐观渲染”时才需要；
- MVP 可以不做乐观渲染：服务端广播给房间内所有人（包括发送者），客户端收到后再统一渲染；
- 这样所有客户端看到的顺序、内容、`messageId` 完全一致，省掉 ACK 和本地对账；
- `clientMsgId` 仍可用于日志排查/重试去重，但不是协议关键字段。

### 结论

1. **不做乐观渲染**；
2. **不引入 ACK 帧**；
3. 服务端广播 `DANMAKU` 给所有人（含发送者），客户端收到后渲染；
4. `clientMsgId` 降级为可选字段；
5. 新增 `UNSUPPORTED_TYPE` 错误码；连接保持，连续大量非法帧可按滥用关闭。

### 影响文档

| 文档 | 内容 |
|---|---|
| 04 v1.5 §7.2 / §7.3 / §7.4 | 客户端帧、错误码、边界 |

### 经验

> 协议复杂度应跟随产品交互；不做乐观 UI 就不要引入 ACK。先定“谁来保证顺序”，再定帧。

## P-014 封禁即时生效且不查库

- **日期**：2026-10-20（轮次 26 / 28）
- **状态**：✅ 已解决
- **涉及模块**：认证 / 用户

### 背景

用户被封禁后，已签发的 JWT 仍在有效期内（7 天）；不能为了封禁在每个请求上查 `t_user.status`。

### 问题

- 如何让封禁立即生效？
- 旧 Token 应该返回什么错误？
- 重新登录时如何提示“账号已被封禁”？
- 登出与封禁的语义如何区分？

### 分析

- Redis 白名单 `glimmer:user:token:{userId}` 是 Token 有效性的真相源；
- 封禁时删除该 Token，旧 Token 后续请求查不到/不匹配 → `40101`；

- 登出只删除 Token，不修改 `t_user.status`；
- 不引入 Refresh Token / `jti`，7 天到期重新登录。

### 结论

1. **封禁 = 删 Token + 登录拦截**；
2. 旧 Token → `40101`；重新登录 → `40302`；
3. 登出 ≠ 封禁；登出只结束当前会话；
4. 不在每个请求上查用户状态；
5. JWT 载荷保持 `userId / role / iat / exp`。

## P-016 跨模块调用：Facade vs 注入 Service

- **日期**：2026-10-20（轮次 32）
- **状态**：✅ 已解决，02 / 04 已同步
- **涉及模块**：全部（重点 interaction / ai / content）

### 背景

02 原规则是“跨模块只走 Facade，禁止注入 Service 实现”，但正文里 interaction 点赞消费者直接写 `t_post.like_count`、评论事务直接写 `t_post.comment_count`、ai 消费者直接写 `t_post_tag`。规则与方案冲突。讨论中对照了苍穹外卖的写法：分层单体里 A 注入 B 的 Service 很常见。

### 问题

- 是否必须为每次跨模块写操作单独建 `XxxFacade`？
- 允许注入 Service 实现，会不会破坏模块边界？
- 直接写对方表到底错在哪里？
- 事务、缓存失效、循环依赖怎么处理？

### 分析

- 苍穹外卖的 `Service` 就是事实上的 Facade；A 调 `contentService.onLikeChanged(...)` 与调 `ContentCounterFacade.onLikeChanged(...)` 没有本质区别，前者少一个类。
- 真正的边界不是“有没有 Facade 类”，而是：
  1. Mapper 是否私有；
  2. 依赖是否单向；
  3. 每张表 / 每个计数列是否只有一个写入口；
  4. 跨模块调用是否在同一本地事务、缓存失效是否由拥有方负责。
- 直接写表的根因风险：绕过拥有方的状态校验（如已删除帖子仍被 AI 打标）、计数双写、缓存失效责任分散、content 表结构变化连锁破坏 interaction / ai。
- 允许 Service 注入后仍需防环：content 不能反向注入 interaction / ai；详情计数由 content 读自己的计数列或 Redis Key。
- 拆分微服务时，跨模块 Service 调用改成 HTTP / RPC 即可；Mapper 没有跨模块，数据归属不需要重划。

### 结论

1. 允许跨模块注入对方 **Service 接口**，不强制单独建 Facade 类；
2. Mapper 永远私有，禁止跨模块注入 Mapper 或直接写对方表；
3. 写入口唯一：`t_post.like_count` / `comment_count` / `last_interaction_at` / `t_post_tag` 由 content 的 Service 统一写；interaction 只写 `t_like` / `t_comment`，ai 只提交标签结果；
4. 依赖单向：content 不反向依赖 interaction / ai；
5. 跨模块 Service 调用默认加入调用方本地事务；拥有方不得用 `REQUIRES_NEW` 拆事务；OSS / LLM 等外部 IO 不进事务；
6. 写 `t_post` 的 Service 方法负责失效 `content:post:{id}`；
7. 骨架阶段加 ArchUnit：禁止跨模块访问 `*.mapper`，模块依赖无环。

## P-017 单实例 Redis 淘汰策略与关键分布式锁冲突

- **日期**：2026-10-21（轮次 33）
- **状态**：✅ 已落地（拆 `redis-core` / `redis-cache`；关键锁范围已确认；02 v1.1 + `deploy/` 已同步）
- **涉及模块**：全部（重点 seckill / content / feed / search）

### 背景

2026-10-21 讨论 Redis 单实例淘汰策略。最初选择 `volatile-lru`，随后发现当前 TTL 设计与该策略冲突：带 TTL 的 Token、`idem`、分布式锁会被优先淘汰，而 Feed、点赞等无 TTL 大对象反而不受淘汰。对比 `volatile-ttl` 后，它按 TTL 长短淘汰，更贴合原 TTL 语义，但 Redisson 锁 TTL 约 30 秒，会成为最先被淘汰的一批。用户明确：**坚持使用 Redisson 分布式锁保护关键逻辑**。

### 问题

1. 锁 Key 被淘汰等于锁直接消失，不只是 TTL 提前到期；两个线程可能同时进入临界区。
2. 若临界区是“查库存 → 扣库存”这类先查后改，可能导致超卖、重复扣减、重复退款等数据错误。
3. 即使 `noeviction` 不淘汰，Redis 重启、AOF everysec 丢 1 秒、主从切换仍可能让锁丢失；Redis 锁本身不是强正确性保证。
4. 单实例同时承载核心数据与可丢缓存，无法给关键锁提供硬隔离。

### 分析

- 本项目秒杀路径当前**不使用锁**：Lua 原子扣减 + DB `stock >= 1` 条件更新 + `uk_user_activity` 唯一索引；锁被淘汰不会导致秒杀超卖。02 §4.2.3 的“秒杀兜底锁”是死表述，§6.7 没有定义对应 Key，应删除。
- 当前实际锁：详情缓存重建 `lock:post:{id}`、热榜重算 `lock:job:hot`、搜索补偿 `lock:job:search-sync`。重复执行主要是多做一次；缓存重建存在旧快照覆盖新缓存的低概率窗口，热榜 / 搜索任务幂等。它们不是“扣库存”类临界区。
- `volatile-lru`：锁可能因访问少被淘汰；`volatile-ttl`：锁 TTL 最短，最先淘汰；`allkeys-*`：同样可能淘汰锁。单实例 + 淘汰策略无法保护关键锁。
- `noeviction`：锁不被淘汰，但缓存撑满后写命令 OOM，登录 / 秒杀可能一起失败。
- 拆分 `redis-core` / `redis-cache`：core 用 `noeviction` + AOF，放锁、Token、`stock`、`bought`、`idem`、布隆；cache 用 `allkeys-lru`，放详情、Feed、点赞、AI、限流。原 TTL 设计可保留（Token 7d、idem 24h），锁也不受淘汰影响；代价是多一个容器与两套连接配置。
- 即使拆分，Redis 锁仍不是故障切换下的强正确性保证；关键不变量必须继续由 DB 唯一键 / CAS 兜底，锁只做协调与减少重复执行。

### 结论（2026-10-21 已拍板）

1. **采用拆分拓扑**：`redis-core` 使用 `noeviction` + AOF everysec，承载锁、Token、`stock`、`bought`、`idem`、布隆；`redis-cache` 使用 `allkeys-lru`、不持久化，承载详情、Feed、点赞、AI、验证码 / 限流、弹幕历史。单实例 `volatile-*` 方案作废。
2. **秒杀保持无锁**：Lua + DB 条件更新 + `uk_user_activity`；禁止在抢购热路径加 Redisson 锁，否则会把 1000 QPS 串行化，且没有必要。
3. **锁清单与归属**：`lock:post:{id}`、`lock:job:hot`、`lock:job:search-sync` 全部放 core；明确 lease / wait / 超时与监控。
4. **锁不是最终正确性保证**：DB 唯一键 / CAS 仍是最后防线；若关键不变量无法用 DB 约束表达，需引入 fencing token 或 DB 行锁。
5. **Token / idem 保持原 TTL**：core noeviction 下 Token 7d、idem 24h 可安全保留；idem 仍建议消费端先查订单再扣库存，防止重复消息多扣。
6. 删除 02 §4.2.3 “秒杀的兜底锁”表述。
7. **部署方式**：Compose 起两个 Redis 服务，部署在 CentOS 7 VM `192.168.157.129`；`redis-core` 挂 AOF volume 并绑定 `192.168.157.129:6379`，`redis-cache` 绑定 `192.168.157.129:6380` 且不持久化；Spring 配两套 `RedisConnectionFactory` / `RedisTemplate`，Redisson 只连 core。

## P-018 秒杀同步等待 publisher confirm 3 秒，故障会放大成全站不可用

- **日期**：2026-10-21（轮次 34）
- **状态**：✅ 已落地（02 §6.7.5 / §6.7.6 / §7.2；03 v1.4；04 v1.8）
- **涉及模块**：seckill、infra（RabbitMQ）

### 背景

原方案（02 §6.7.5）：Redis Lua 扣减成功后，请求线程同步等待 publisher confirm，超时 3 秒；失败则回滚 Redis 库存并返回“系统繁忙”。用户追问“300ms 会不会太短”，进一步讨论发现真正的问题不是 300ms 还是 3s，而是**同步等待本身**。

### 问题

1. Tomcat 默认约 200 个工作线程。1000 QPS 下，每个请求等 3 秒：`1000 × 3 = 3000` 个并发线程，线程池 0.2 秒内打满。
2. 线程池打满后，不只秒杀不可用，**Feed、登录、详情等所有接口**一起不可用；Broker 的局部故障被放大成全站故障。
3. `waitForConfirms` 是 channel 级别的等待，存在队头阻塞；一个慢 confirm 会拖住同 channel 的其他消息。
4. confirm 超时是**假阴性**：消息可能已经到达 Broker，消费者可能已经建单；此时直接回滚库存并告诉用户失败，会导致“用户以为没抢到、实际有订单”或反向超卖。

### 分析

| 方案 | 做法 | 结论 |
|---|---|---|
| A. 异步 confirm + 补偿 | Lua 成功后立即返回 202；confirm 回调失败时延迟查订单，确认未建单再回滚 | ✅ 采用 |
| B. 短超时 + 舱壁 | 请求线程最多等 300–500ms，独立线程池满则快速失败 | 可用，但仍有同步等待与假阴性 |
| C. 轻量 Outbox | Lua 同时写 pending ZSet，后台任务重发 | 可靠性最高，MVP 过重，列演进 |

关键设计：**先写 cancel 标记，再回滚资格**。否则 confirm 超时后消息晚到，消费者仍可能建单，造成“已回滚但订单存在”。

### 结论

1. **禁止请求线程同步等待 confirm**；使用 `CorrelationData.getFuture()` 异步回调，`publisher-confirm-type=correlated`，同时开启 `publisher-returns` + `mandatory`。
2. **舱壁**：秒杀发送使用独立 `ThreadPoolTaskExecutor`（32–64 线程、queue=0、`AbortPolicy`）；池满立即回滚 Lua 并返回 `50301`，不排队。
3. **连接隔离**：秒杀使用独立 `CachingConnectionFactory` / `RabbitTemplate`，不与点赞、AI、搜索共用连接。
4. **confirm 失败 / 超时**（默认 1s，可配置 500ms–2s）：不立即回滚；延迟 5s 按 `(userId, activityId)` 查订单。有订单 → 不回滚；无订单 → 先写 `glimmer:seckill:cancel:{userId}:{activityId}`（TTL 24h），再回滚 stock / bought。
5. **消费者先查 cancel 标记**：存在直接 ACK，不建单；晚到消息不会破坏已回滚状态。
6. **202 语义**：`202` = “已获得资格，MQ 投递中”，不是“订单已创建”；客户端必须轮询 `my-order`。舱壁满 / MQ 不可用返回 `50301`。
7. **消费端事务**：先查订单，再在同一本地事务内“条件扣库存 + 插订单”；`DuplicateKeyException` 回滚整个事务（含库存扣减）；`idem` 只是快路径，不是成功标记。
8. **监控**：confirm 失败率、超时率、cancel 标记数、回滚次数、舱壁拒绝数、DLQ 堆积；任一持续 > 0 告警。
9. **演进**：阶段 7 微服务化时升级 Outbox；MVP 不引入 pending ZSet / 请求级账本。

|---|---|

### 经验

> 同步等待一个“可能很慢、可能假阴性”的外部确认，是把依赖故障放大成全站故障的最短路径。正确做法不是把 3s 调成 300ms，而是让请求线程不等待，把补偿做成异步、可重试、可取消的。

## P-020 CORS 白名单 vs Nginx 同源反代

- **日期**：2026-10-24（轮次 41）
- **状态**：✅ 已定稿（06 v1.1；`nginx.conf` 模板已补；待后端容器化后启动）
- **涉及模块**：deploy、backend 配置、frontend

### 背景

开发期前端跑在 Vite `localhost:5173`，后端跑在 `localhost:8080`，浏览器视为跨域。原方案是后端 `CorsProperties` 白名单 + Spring MVC `addCorsMappings`；用户提出「苍穹外卖这类项目没有 `CorsProperties`」，进而讨论是否改用 Nginx 同源反代。

### 问题

1. CORS 是浏览器行为，不是服务端鉴权；配置了 CORS 也不代表接口安全。
2. 每套环境都要维护 Origin 白名单；多前端、域名、HTTPS 切换时容易漏配。
3. Authorization + JSON 会触发预检，`OPTIONS` 必须绕过登录拦截；自定义响应头还要额外 `exposedHeaders`。
4. 生产若用 Nginx 同源，CORS 配置就失去意义；两套方式并存会增加排查成本。
5. `CorsProperties` 是否还有必要保留。

### 分析

| 方案 | 浏览器视角 | 生产可用 | 代价 |
|---|---|---|---|
| A. 后端 CORS 白名单 | 两个 Origin，跨域 | ✅ | 每环境配白名单；预检；暴露头；后端端口暴露 |
| B. Nginx 同源反代 | 只有一个 Origin | ✅ | 多一个组件；需容器化、静态托管、TLS |
| C. Vite dev proxy | 只有一个 Origin | ❌ 仅开发 | 仅解决本地，生产仍需 Nginx |

关键结论：**CORS 不是鉴权，同源只是消除跨域限制**。同源反代把静态资源、API、SSE、WebSocket、上传统一到一个入口，运维和安全边界更清晰；开发期用 Vite proxy 可以保持与生产一致的“相对路径 `/api`”调用方式。

### 结论

1. **生产 / 演示**：Nginx 同源反代，后端不配置生产 CORS 白名单。
2. **本地开发**：优先 Vite proxy；`glimmer.cors.allowed-origins` 仅保留在 `application-dev.yml`，作为“前端直连 8080”的调试兜底。
3. **`CorsProperties` 暂不删除**：等前端 proxy 稳定、确认无人直连后，再评估删除 `CorsProperties` 与 `addCorsMappings`。
4. **Nginx 模板**：补前端静态托管与 history 回退、API keepalive、`X-Trace-Id` 生成/透传、SSE/上传转发头。
5. **验证顺序**：API → 鉴权 → 上传 → WebSocket → SSE → traceId 对齐。

|---|---|
| 06 §6.5 / §14.1 | 同源反代定稿、切换清单、文档版本 v1.1 |

> 跨域不是安全问题，只是浏览器的同源策略。能用一个入口解决的事，不要在两个 Origin 之间维护 CORS 白名单；开发期用和生产相同的相对路径，能提前暴露部署差异。

## P-021 VM 上 SSH 能通，但 Docker 发布端口从宿主机超时

- **日期**：2026-10-27（轮次 46）
- **状态**：✅ 已修复（VM 已持久化 + 文档同步）
- **涉及模块**：deploy、VM 网络、后端联调

### 背景

VM 上 `docker compose up -d mysql redis-core redis-cache` 成功，三个容器 healthy；FinalShell 的 SSH 连接正常，但 Windows 上的 Redis 图形客户端、MySQL 客户端以及 `Test-NetConnection` 连接 3306 / 6379 / 6380 全部超时。

### 问题

1. SSH 22 能通，说明 VM 主机可达；3306 / 6379 / 6380 不通。
2. firewalld 已经 `inactive`，排除主机防火墙。
3. `iptables -S` 中 Docker 的 DNAT、FORWARD 放行规则都存在，INPUT 策略为 ACCEPT。
4. `sysctl net.ipv4.ip_forward` 为 `0`。

### 分析

- SSH 是“到 VM 本机”的连接，走 INPUT 链；Docker 发布端口是 `PREROUTING DNAT → FORWARD → 容器`，必须开启内核转发。
- `ip_forward=0` 时，DNAT 后的包无法转发到 `172.28.0.0/16`，宿主机看到的就是连接超时，而不是 connection refused。
- `rp_filter=1` 是 CentOS 默认值，但 Docker 会为桥接口单独处理；实测开启转发后即可连通，不需要改 `rp_filter`。
- 该值可能被 `sysctl --system`、停止 firewalld 或重启后的系统默认值重置，因此不能只做临时 `sysctl -w`。

### 结论

```bash
sysctl -w net.ipv4.ip_forward=1
echo 'net.ipv4.ip_forward=1' | sudo tee /etc/sysctl.d/99-docker-forward.conf
sysctl --system
sysctl net.ipv4.ip_forward
```

注意 `/etc/sysctl.conf` 在 `sysctl --system` 中最后加载；若其中有 `net.ipv4.ip_forward=0`，需要一并修改。

| 文档 | 内容 |
|---|---|
| `deploy/README.md` §4 / §10 | sysctl 增加 `net.ipv4.ip_forward=1`；故障排查增加 SSH 通但 Docker 端口超时 |
| `docs/06-部署文档.md` §7.1 / §12 | 同步 sysctl 与排查项 |

### 经验

> 排查“端口不通”先分层：主机是否可达（SSH / ping）→ 本机防火墙（firewalld / iptables）→ 内核转发（`ip_forward`）→ 容器监听。Docker 发布端口不是本机监听，`ip_forward=0` 时 SSH 正常但业务端口全超时，现象很有迷惑性。

## P-022 `.env` 中带空格的值未加引号，`smoke.sh` source 时退出

- **日期**：2026-10-27（轮次 46）
- **状态**：✅ 已修复（`.env.example` / 06 文档已改）
- **涉及模块**：deploy、`smoke.sh`

### 背景

在 VM 上执行 `set -a; . ./.env; set +a` 时出现：

```
-bash: -Xmx512m: 未找到命令
```

### 问题

`.env` 中有一行：

```ini
ES_JAVA_OPTS=-Xms512m -Xmx512m
```

docker compose 能把它当作完整值，但 bash `source` 会把第二个词 `-Xmx512m` 当成命令执行并返回 127。

`smoke.sh` 开头是 `set -euo pipefail`，随后 `source .env`；该错误会让脚本在真正检查之前直接退出。

### 分析

- `.env` 同时承担两个角色：Compose 的 dotenv 输入、`smoke.sh` 的 shell 变量来源。
- Compose 的 dotenv 语法允许不带引号的空格值；shell 不允许。
- 给值加双引号后，shell 得到去掉引号的完整字符串；Compose 也会去掉引号，双方语义一致。

### 结论

```ini
ES_JAVA_OPTS="-Xms512m -Xmx512m"
```

以后 `.env` 中任何含空格的值都必须加引号；密码建议使用 `openssl rand -hex` 生成，避免 `$`、空格等 shell 特殊字符。

### 影响文档

| 文档 | 内容 |
|---|---|
| `deploy/.env.example` | `ES_JAVA_OPTS` 加引号并注明原因 |
| `docs/06-部署文档.md` §6.1 | 同步写法 |
| `docs/00-开发进度.md` | 轮次 46 |

### 经验

> 当一个文件既给 Compose 读、又被 shell `source`，就不能只按 dotenv 语法写；带空格、`$`、`#` 的值要加引号，或者脚本只解析明确需要的键，不要整文件 source。
