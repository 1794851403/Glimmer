## 1. 总体结论

### 1.1 表的分类

11 张表不是按“功能”一一对应，而是按**数据本质**分成四类：

| 数据本质 | 表 | 说明 |
|---|---|---|
| 主体 / 字典 | `t_user`、`t_tag`、`t_post`、`t_seckill_activity` | 有独立生命周期，被其他表引用 |
| 关系 | `t_user_follow`、`t_like`、`t_collect`、`t_post_tag` | 多对多关系，靠唯一键做幂等 |
| 从属明细 | `t_post_image`、`t_comment` | 依附于帖子，一对多 |
| 业务单据 | `t_seckill_order` | 有状态机，必须独立 |

### 1.2 表之间的关系

```
t_user 1 ── N t_post 1 ── N t_post_image
  │              │
  │              ├── N t_post_tag N ── 1 t_tag
  │              ├── N t_like      N ── 1 t_user
  │              ├── N t_collect   N ── 1 t_user
  │              └── N t_comment   N ── 1 t_user
  │
  ├── N t_user_follow N ── 1 t_user
  │
  └── N t_seckill_order N ── 1 t_seckill_activity
```

> 图中只表达逻辑关系；物理上**不使用外键**，由应用层 + 索引 + 对账保证一致性。

### 1.3 有意不落库的数据

| 数据 | 存储 | 原因 |
|---|---|---|
| Feed 收件箱 / 发件箱、热榜 | Redis ZSet | 可重建，读性能优先 |
| 点赞实时集合与计数 | Redis Set / String | 高频写，异步落库 |
| 秒杀库存、限购计数、幂等标记 | Redis | 抢购路径不能查 MySQL |
| 验证码、Token、限流计数 | Redis | 短期状态 |
| 弹幕历史 | Redis List | MVP 允许丢失、不落库 |
| AI 会话上下文 | Redis JSON | ADR-014：即时性需求，历史价值低 |
| 帖子图片本体 | 阿里云 OSS | MySQL 只存 URL |
| 帖子搜索索引 | **Elasticsearch** | 派生数据，可从 MySQL 全量重建；MySQL 不建全文索引 |
| 通知（F-15）、Outbox、请求账本、AI 会话历史 | P2 / 演进 | 初版不做 |

## 2. 逐表说明

### 2.1 user 模块

#### `t_user` —— 账号与身份主表

**解决的问题**：系统中所有“人”的唯一身份来源，同时承载角色、封禁状态和用户资料。

| 使用场景 | 怎么用 |
|---|---|
| F-01 注册 / 登录 | 按 `uk_phone` 查用户；不存在则插入；验证码在 Redis，不在本表 |
| F-02 JWT 鉴权 | JWT 携带 `userId/role`，但每次请求仍校验 `status`（是否被封禁）；Redis 存 Token 白名单 |
| F-03 资料查看 / 编辑 | 直接读写昵称、头像、简介 |
| 帖子 / 评论 / Feed 展示作者 | 按 `user_id` 批量查；Feed 必须批量 `IN`，禁止 N+1 |
| F-27 封禁 / 解封 | 改 `status`，并删除 Redis Token 让用户下线 |
| 弹幕连接 | 连接建立时取一次昵称，缓存在 session attribute，不逐条查 DB |
| AI 助手 | 校验会话归属 `session.userId` |
| 秒杀下单 | 校验用户存在且未被封禁 |

**建议字段**：

```
id, phone, nickname, avatar_url, bio, role, status,
following_count, follower_count,
created_at, updated_at
```

**生命周期**：不物理删除；封禁通过 `status` 表达。手机号唯一。

**不放在这里的数据**：验证码、JWT、在线状态——它们在 Redis。

---

#### `t_user_follow` —— 关注关系

**解决的问题**：关注是 Feed 推拉模式的输入，也是用户主页“关注 / 粉丝”列表的数据源。

| 使用场景 | 怎么用 |
|---|---|
| F-04 关注 / 取关 | 插入或物理删除；`uk_follower_followee` 保证重复关注幂等 |
| F-16 写扩散 | 发帖后按 `followee_id` 查粉丝列表，给每个粉丝的 Redis 收件箱 `ZADD` |
| F-16 拉模式 | 按 `follower_id` 查出我关注的人，筛出粉丝数 ≥ 1000 的大 V，再查他们的帖子 |
| 关注时回填 | 关注成功后查 `t_post` 中该作者最近 50 条帖子，写入我的收件箱 |
| 用户主页 | 展示关注数、粉丝数；列表分页 |

**关键设计**：

- **物理删除**，不用逻辑删除——否则重新关注会被唯一键挡住；
- 粉丝数不实时 `COUNT(*)`，放在 `t_user.follower_count`；
- 索引建议：`uk(follower_id, followee_id)`、`idx(followee_id, created_at)`、`idx(follower_id, created_at)`。

### 2.2 content 模块

#### `t_post` —— 帖子主体

**解决的问题**：内容真相源，同时是互动计数的落点、热榜任务的扫描入口。

| 使用场景 | 怎么用 |
|---|---|
| F-05 发帖 | 插入标题、正文、作者、状态（普通用户=已发布待审核、管理员=已发布）；提交后触发布隆、AI 打标、Feed 扩散与搜索索引 |
| F-06 列表 | 按 `status + is_deleted + published_at` 查最新（`status IN (0,1)`）；热度排序走 Redis 热榜 |
| F-07 详情 | 按主键查；公开详情要求公开可见（`status IN (0,1)`）；作者本人可查看自己的拒绝 / 下架帖 |
| F-08 搜索 | 标题 / 正文检索；标签检索走 `t_post_tag`；只返回公开可见帖 |
| F-10 / F-28 审核 / 下架 | 审核通过 / 拒绝、下架 / 恢复；改 `status`（及审核字段）；拒绝 / 下架时删缓存与 ES 文档 |
| F-16 关注流拉模式 | 按 `(user_id, status, is_deleted, published_at)` 查大 V 最近公开帖子 |
| F-17 / F-18 热榜 | 定时扫描 `last_interaction_at >= now-24h` 且公开可见的帖子，用本表计数算分 |
| F-11 / 12 / 13 计数 | `like_count / comment_count / collect_count / view_count` 异步更新 |
| F-23 AI 打标 | `ai_tag_status` 标记待处理 / 成功 / 降级 / 失败，供重试任务扫描 |
| F-31 AI 助手 | 读标题、正文作为 Prompt 的帖子上下文 |
| 管理端 | 待审队列、审核 / 下架 / 恢复、数据看板聚合 |

**建议字段**：

```
id, user_id, title, content, status, is_deleted, published_at,
like_count, comment_count, collect_count, view_count,
ai_tag_status, last_interaction_at,
audit_reason, audited_at, audited_by,
created_at, updated_at
```

**状态与时间口径**：

- `status`：0=已发布待审核、1=已发布、2=审核拒绝、3=已下架；管理员发帖直接置 1。**`0` 和 `1` 均公开可见**。
- `published_at`：首次发布（创建成功）时写入；Feed / 热榜 / 搜索按它排序；审核通过、下架恢复、编辑重新提交均不重置。
- `audit_*`：最近一次发布态裁决（通过 / 拒绝 / 下架 / 恢复）的操作人、时间与原因；拒绝 / 下架必填原因，通过 / 恢复清空原因。只保留最后一次，完整历史留给演进 `t_audit_log`。

**生命周期**：逻辑删除。`is_deleted=1` 或 `status IN (2,3)` 时公开详情返回 404，列表过滤；作者本人可在“我的帖子”查看自己的拒绝 / 下架帖；缓存靠空值缓存兜住。

**索引对应关系**：

| 索引 | 支撑的查询 |
|---|---|
| `idx_user_deleted_created` | 作者的“我的帖子”（全部状态），按创建时间 |
| `idx_user_status_deleted_created` | 作者的“我的帖子”按状态筛选 |
| `idx_user_status_deleted_published` | 作者主页、拉模式取大 V 最近公开帖子 |
| `idx_status_deleted_created` | 审核队列（待审核按提交时间） |
| `idx_status_deleted_published` | 最新帖子列表、搜索未命中时的兜底 |
| `idx_status_deleted_interaction` | 热榜扫描最近 24h 有互动的公开帖子 |
| `idx_ai_tag_status` | AI 打标失败重试 |
| `idx_updated_at` | ES 增量同步补偿扫描 |

#### `t_post_image` —— 帖子图片明细

**解决的问题**：一篇帖子多张图，且必须保持展示顺序。

| 使用场景 | 怎么用 |
|---|---|
| F-05 / F-09 | 后端中转上传 OSS 后，发布时把 URL 批量写入本表 |
| F-07 详情 | 按 `post_id ORDER BY sort_order` 取图 |
| F-06 / Feed | 取 `sort_order=0` 作为封面，避免查出全部图片 |

**为什么独立成表**：如果存成 `t_post` 的 JSON 字段，无法按顺序索引、无法单独替换某张图，且会让帖子主表行过宽。

**约束**：`uk_post_sort(post_id, sort_order)`；`sort_order=0` 为封面。不单独逻辑删除，随帖子一起隐藏。

---

#### `t_tag` —— 标签字典

**解决的问题**：标签不能是帖子里的自由文本，否则无法聚合、无法作为 AI 候选集、无法做标签推荐。

| 使用场景 | 怎么用 |
|---|---|
| F-05 发帖 | 用户从字典中选择标签 |
| F-23 AI 打标 | Prompt 的候选标签集直接从本表读取，而不是写死在代码里 |
| F-07 详情 | 展示帖子标签 |
| F-17 推荐 / 筛选 | 按标签召回帖子 |
| F-08 搜索 | 标签过滤 |

**量级**：10~100 条，初始化时种子数据。不存标签计数，需要时从 `t_post_tag` 聚合。

---

#### `t_post_tag` —— 帖子与标签的关系

**解决的问题**：多对多关系，并记录标签来源，区分人工标签、AI 标签、规则降级标签。

| 使用场景 | 怎么用 |
|---|---|
| F-05 发帖 | 写入手动选择的标签，`source=MANUAL` |
| F-23 AI 打标 | 消费者写入 `source=AI`，并记录 `prompt_version` |
| AI 降级 | 关键词匹配写入 `source=RULE`，保证功能有输出 |
| F-07 详情 | 按 `post_id` 查标签名 |
| F-17 推荐 | 按 `tag_id` 反查帖子，`idx_tag_post` |
| F-31 AI 助手 | 读取标签拼进 Prompt |

**关键设计**：

- `uk_post_tag(post_id, tag_id)` 防止同一帖子重复标签；
- `idx_tag_post(tag_id, post_id)` 支持按标签反查帖子；`idx_created_at(created_at)` 供 ES 标签变更补偿；
- **人工标签优先**：AI 写入时用 `INSERT IGNORE`，不能把 `source=MANUAL` 覆盖成 `AI`；
- 物理删除，允许用户编辑标签后重新添加。

### 2.3 interaction 模块

#### `t_like` —— 点赞关系

**解决的问题**：点赞的**真相源**。Redis 的 Set/Count 只是实时层，DB 才是可重建、可对账的依据。

| 使用场景 | 怎么用 |
|---|---|
| F-11 点赞 | Redis Lua 原子判断 + 计数；发送 MQ；消费者插入本表并更新 `t_post.like_count` |
| F-11 取消 | Redis `SREM/DECR`；消费者删除本表并减计数 |
| F-07 详情 | 查当前用户是否点过赞：优先 Redis `SISMEMBER`，未命中查本表 |
| 用户点赞列表 | 按 `(user_id, created_at)` 分页 |
| 对账任务 | 按 `post_id` 统计本表行数，修正 `t_post.like_count` 与 Redis 计数 |

**关键设计**：

- 物理删除，允许取消后重新点赞；
- `uk_user_post` 防重复；
- 1 亿行量级，所以详情页判断“我是否点赞”尽量走 Redis，列表页才查 DB。

---

#### `t_collect` —— 收藏关系

**解决的问题**：收藏关系与收藏列表。

| 使用场景 | 怎么用 |
|---|---|
| F-12 收藏 / 取消 | 插入 / 删除本表；同事务更新 `t_post.collect_count` |
| F-07 详情 | 查当前用户是否收藏 |
| 收藏列表 | 按 `(user_id, created_at)` 分页 |
| 计数对账 | 按 `post_id` 统计修正 |

**与点赞的差异**：架构没有为收藏设计 Redis + MQ 链路。收藏 QPS 远低于点赞，**MVP 建议同步写库 + 同事务更新计数**，靠唯一键保证幂等；后续量大了再复制点赞的异步方案。

---

#### `t_comment` —— 评论 / 回复与情感分析结果

**解决的问题**：评论树、评论计数、AI 情感分析结果的落点。

| 使用场景 | 怎么用 |
|---|---|
| F-13 评论 | 插入评论；同事务 `t_post.comment_count + 1`、更新 `last_interaction_at` |
| F-13 回复 | 两级结构：`parent_id=0` 为一级评论；回复的 `parent_id` 指向根评论，`reply_to_user_id` 记录被回复人 |
| F-13 评论列表 | 一级评论按 `(post_id, parent_id=0, is_deleted, created_at)` 查；回复按 `parent_id` 查 |
| F-24 情感分析 | 评论提交后发 MQ；消费者更新 `sentiment (1/0/-1)` 与 `sentiment_prompt_version` |
| US-11 / 后台 | 按帖子聚合情感分布，`idx_post_sentiment` |
| F-25 摘要（P2） | 读取评论内容做摘要，不新增表 |
| F-18 热榜 | 评论数从 `t_post.comment_count` 取 |

**生命周期**：逻辑删除。删除一级评论时建议保留子回复并显示“评论已删除”占位，避免回复树断裂。

### 2.4 seckill 模块

#### `t_seckill_activity` —— 活动、商品与库存

**解决的问题**：秒杀活动的主体，既是活动配置，也是 DB 侧库存的落点。

| 使用场景 | 怎么用 |
|---|---|
| F-19 / F-29 活动管理 | 管理员创建、编辑、上下架；`total_stock` 与 `stock` 分开 |
| F-20 抢购预热 | 发布时把活动信息、`stock` 写入 Redis，加入秒杀布隆过滤器 |
| F-20 异步下单 | 消费者执行 `UPDATE ... SET stock=stock-1 WHERE id=? AND stock>=1`，这是第二道防超卖 |
| F-21 超时关单 | 关单时 `stock=stock+1` 回补；不恢复该用户的抢购资格 |
| F-22 订单查询 | 订单关联活动，取标题、图片、价格 |
| 对账 | `dbStock + Σ有效订单qty == total_stock` |

**关键设计**：

- `status`：0=草稿、1=已发布、2=已下架；进行中 / 已结束由时间推导，不单独存状态；
- 不建商品表：MVP 商品信息直接内嵌在活动里，秒杀刻意与内容模块解耦（ADR-012）；
- `limit_num` MVP 固定为 1。

---

#### `t_seckill_order` —— 秒杀订单与状态机

**解决的问题**：订单的完整生命周期，以及三个幂等唯一键。

| 使用场景 | 怎么用 |
|---|---|
| F-20 异步下单 | 消费者在同一个事务里扣活动库存 + 插入订单（状态=待支付） |
| F-21 支付 | 支付回调 CAS：`status 0 → 1`，写 `paid_at/pay_trade_no` |
| F-21 超时关单 | 延迟消息或定时扫描；CAS：`status 0 → 2`，写 `closed_at`，再回补 DB/Redis 库存；不回补限购计数 |
| F-22 订单查询 | 按 `(user_id, created_at)` 分页；详情校验归属 |
| 对账 | 按活动统计有效订单数量，与活动库存核对 |
| 一人一单 | `uk_user_activity` 保证同一用户对同一活动只能创建一个订单；已关闭订单仍占用唯一键，不能重新抢 |

**三个唯一键各自解决什么**：

| 唯一键 | 解决的问题 |
|---|---|
| `uk_order_no` | 订单号全局唯一 |
| `uk_request_id` | 同一 MQ 消息重投不会复活已关闭订单 |
| `uk_user_activity` | 一人一单；同一用户对同一活动只能创建一个订单，关闭后也不释放 |

## 3. 功能 → 表 映射总表（速查）

| 功能 | 用到的表 | 用法一句话 |
|---|---|---|
| F-01 注册 / 登录 | `t_user` | 按手机号查 / 建用户；验证码、Token 在 Redis |

### 4.1 账号模块

#### F-01 手机号 + 验证码注册 / 登录（P0）

**架构落点**：§6.10.1、§6.10.2

**用到的表**：`t_user`

**怎么做**：

1. **发送验证码**：不写表。验证码写 Redis `glimmer:auth:sms:{phone}`（5 min），发送限流写 `glimmer:auth:limit:sms:{phone}`（5 次/小时）。
2. **校验验证码**：从 Redis 读取并比对；成功后立即删除，防止重复使用。
3. **登录 / 注册**：`SELECT * FROM t_user WHERE phone = ?`。
   - 已存在：校验 `status`，被封禁则拒绝。
   - 不存在：`INSERT t_user (phone, nickname, role, status, following_count, follower_count, ...)`，昵称可默认为“用户 + 随机串”，`role=0`、`status=0`。
4. **签发登录态**：生成 JWT，同时写 Redis `glimmer:user:token:{userId}`（7 d），用于登出 / 踢人。
5. **返回**：`userId`、`nickname`、`avatarUrl`、`role`、Token。

**不落库**：验证码、发送限流、Token 全在 Redis。

**边界**：

- `phone` 唯一索引是注册并发的最终防线，重复插入捕获唯一键异常后转为登录；
- 不在响应中返回完整手机号；
- 管理员与普通用户共用本表，靠 `role` 区分。

#### F-02 JWT 登录态与接口鉴权（P0）

**架构落点**：§6.10.1、§6.10.2

**用到的表**：`t_user`（读 `role`、`status`）

**怎么做**：

1. 拦截器解析 `Authorization: Bearer <token>`，校验签名与过期时间。
2. 用 JWT 中的 `userId` 读 Redis `glimmer:user:token:{userId}`，与请求 Token 比对；不一致说明已登出或被踢下线。
3. 读用户信息（优先用户缓存，未命中查 `t_user`），校验 `status` 未被封禁。
4. 把 `userId`、`role` 注入 `UserContext`（ThreadLocal）。
5. 默认拒绝：未命中白名单的接口要求登录；`/api/v1/admin/**` 再校验 `role=ADMIN`。
6. 白名单接口（登录、帖子列表 / 详情、热榜、活动列表、静态资源）按「方法 + 路径」放行；有合法 Token 时注入 `UserContext`，否则按游客处理。

**不落库**：Token、登录态、权限缓存都在 Redis。

**边界**：

- **userId 一律从 JWT 取，绝不从请求参数取**；
- 管理端统一 `/api/v1/admin/**` 前缀，由全局拦截器校验 `ADMIN`；鉴权不写在 Controller 注解上；
- 封禁用户即使持有未过期 JWT，也会在第 3 步被拦下。

#### F-03 用户信息查看 / 编辑（P1）

**架构落点**：§6.10.4（越权与敏感信息）

**用到的表**：`t_user`

**怎么做**：

1. **查看**：按 `id` 查 `t_user`，返回昵称、头像、简介、关注数、粉丝数；手机号只返回脱敏值。
2. **编辑**：校验操作者 `userId == 目标 userId`（从 JWT 取），`UPDATE t_user SET nickname=?, avatar_url=?, bio=? WHERE id=?`。
3. 头像先走 F-09 上传到 OSS，再把 URL 写入 `avatar_url`。
4. 更新成功后删除用户缓存（若使用 Cache Aside），下次读取回填。

**不落库**：头像文件本体的 OSS 对象。

**边界**：

- 不单独建用户资料表：字段少、与账号强绑定，拆表只会增加一次 JOIN；
- 昵称、简介需做长度校验与 XSS 转义；
- 手机号、角色、状态不允许用户自行修改。

#### F-04 关注 / 取关（P0）

**架构落点**：§6.5.3（关注关系变更）、§6.5.5（拉模式）

**用到的表**：`t_user_follow`（写）、`t_user`（计数）、`t_post`（关注时回填）

**怎么做**：

1. **关注**：
   - 事务内 `INSERT t_user_follow (follower_id, followee_id, created_at)`；
   - `UPDATE t_user SET following_count = following_count + 1 WHERE id = followerId`；
   - `UPDATE t_user SET follower_count = follower_count + 1 WHERE id = followeeId`；
   - 提交后更新 Redis `follow:ing:{followerId}`、`follow:ers:{followeeId}`；
   - 查 `t_post` 中该博主最近 50 条公开可见帖子（走 `idx_user_status_deleted_published`），写入我的 Redis 收件箱。
2. **取关**：
   - 事务内 `DELETE FROM t_user_follow WHERE follower_id=? AND followee_id=?`；
   - 删除成功才递减双方计数（受影响行数为 0 说明本来就没关注）；
   - 更新 Redis 两个 Set；
   - **不清理收件箱**，查询时按当前关注列表过滤。
3. **幂等**：`uk_follower_followee` 保证重复关注 / 重复取关不重复改计数。

**不落库**：收件箱、关注 Set 在 Redis。

**边界**：

- `t_user_follow` **物理删除**，否则重新关注会被唯一键挡住；
- 粉丝数用于判断 Feed 推 / 拉模式（`follower_count >= 1000` 走拉模式），不能每次 `COUNT(*)`；
- 关注 / 取关本身是强一致操作，先写 MySQL，再更新 Redis；Redis 丢数据可从本表重建。

### 4.2 内容模块

#### F-05 发布图文帖子（P0）

**架构落点**：§6.2.2（布隆同步）、§6.5.3（写扩散）、§6.9.2（AI 打标）

**用到的表**：`t_post`、`t_post_image`、`t_post_tag`、`t_tag`

**怎么做**：

1. 鉴权取 `userId` 与 `role`，校验标题、正文、图片 URL、标签 ID。
2. **确定初始状态**：
   - 普通用户：`status=已发布待审核(0)`，`published_at=NOW(3)`；
   - 管理员：跳过审核，`status=已发布(1)`，`published_at=NOW(3)`（`audited_by/audited_at/audit_reason` 留空）。
3. **事务内**：
   - `INSERT t_post (user_id, title, content, status, published_at, is_deleted=0, ai_tag_status=待处理, last_interaction_at=NOW(3), ...)`，拿到 `postId`；
   - 批量 `INSERT t_post_image (post_id, url, sort_order)`，`sort_order` 从 0 开始，0 为封面；
   - 批量 `INSERT t_post_tag (post_id, tag_id, source=MANUAL, prompt_version=NULL)`。
4. **提交事务**。
5. **提交后异步**：
   - 布隆过滤器 `add(postId)`；失败由补偿消息兜底；
   - 发送 AI 打标消息（与审核并行，辅助管理员审核）；
   - **Feed 写扩散**：普通用户与管理员帖子都在此时发 MQ（先发后审，帖子已公开）；
   - **搜索索引**：发送 `SEARCH_UPSERT`，消费者回查 MySQL 后写入 ES（`status IN (0,1)`）。

**不落库**：帖子详情缓存、Feed 收件箱、布隆位图在 Redis；图片本体在 OSS。

**边界**：

- 图片必须在发帖前已上传（F-09），发帖只保存 URL；
- AI 打标失败不能影响发帖：发帖事务已提交，AI 走 MQ + 重试 / 规则降级；
- `t_post_tag` 的唯一键保证同一帖子同一标签只出现一次；
- 普通用户帖子创建后立即公开，同时进入审核队列；管理员发帖不经过审核；
- `last_interaction_at` 在创建时置为 `published_at`，让新帖能被热榜扫描到；审核通过不重置。

#### F-06 帖子列表（按时间 / 热度排序）（P0）

**架构落点**：§6.5.5（关注流归并）、§6.5.6（游标分页）、§6.6（热榜）

**用到的表**：`t_post`、`t_user`、`t_post_image`

**怎么做**：

1. **按时间列表**：
   - `SELECT ... FROM t_post WHERE status IN (0,1) AND is_deleted=0 ORDER BY published_at DESC LIMIT ?`，走 `idx_status_deleted_published`；
   - 使用游标 `published_at < ?`，不用 `OFFSET`。
2. **按热度列表**：
   - 从 Redis `glimmer:feed:hot` 用 `ZREVRANGEBYSCORE` 取 `postId` 列表；
   - 按 `postId` 批量查 `t_post`，过滤审核拒绝 / 已删除 / 已下架；
3. **组装**：
   - 批量查 `t_user` 取作者昵称 / 头像；
   - 批量查 `t_post_image`，每帖只取 `sort_order=0` 的封面；
   - 计数直接取 `t_post` 冗余列或 Redis 实时值。
4. 列表摘要可写 Redis 缓存，减少重复查询。

**不落库**：热榜 ZSet、列表缓存。

**边界**：

- 禁止对每条帖子单独查作者 / 图片（N+1）；
- 审核拒绝 / 已删除 / 已下架的帖子即使还在热榜 ZSet 里，也必须在返回前过滤；
- 游标分页避免翻页漂移。

#### F-07 帖子详情（P0）

**架构落点**：§6.2.2（布隆 + 空值缓存）、§6.2.3（互斥锁重建）、§6.2.5（Cache Aside）

**用到的表**：`t_post`、`t_user`、`t_post_image`、`t_post_tag`、`t_tag`、`t_like`、`t_collect`、`t_comment`

**怎么做**：

1. **读缓存路径**：
   - 布隆过滤器判定“一定不存在”→ 直接 404；
   - Redis `glimmer:content:post:{postId}` 命中 → 返回；
   - 空值缓存命中 → 404；
   - 都未命中 → 查 MySQL，回填缓存（TTL 30 min + 随机抖动）。
2. **查 MySQL**：
   - `t_post`：按主键查，公开详情校验 `status IN (0,1) AND is_deleted=0`；作者本人可查看自己的拒绝 / 下架帖（走“我的帖子”接口，需登录 + 归属校验）；
   - `t_user`：作者信息；
   - `t_post_image`：按 `post_id ORDER BY sort_order`；
   - `t_post_tag JOIN t_tag`：标签；
   - `t_like` / `t_collect`：当前登录用户是否点赞 / 收藏（未登录跳过）；
   - `t_comment`：一级评论首页（`parent_id=0 AND is_deleted=0 ORDER BY created_at`）。
3. **计数**：点赞 / 评论 / 收藏数优先读 Redis 实时值，未命中读 `t_post` 冗余列。
4. **组装 DTO** 后回填 Redis。

**不落库**：详情缓存、空值缓存、实时计数。

**边界**：

- 布隆过滤器不支持删除，帖子删除后靠空值缓存兜底；
- 详情缓存只缓存公开可见帖；作者查看自己的拒绝 / 下架帖不走公共缓存，避免状态变更后串数据；
- 热点 Key 重建需要分布式锁，避免击穿；
- 评论只取首页，分页另走 F-13 的评论接口。

#### F-08 帖子搜索（关键词，Elasticsearch）（P1）

**架构落点**：§6.12（搜索方案，MVP 引入 ES）

**用到的表**：`t_post`、`t_post_tag`、`t_tag`、`t_user` + ES 索引 `glimmer_post`

**职责边界**：

- **MySQL 是真相源**：帖子正文、标签、状态、发布时间只以 MySQL 为准；
- **ES 是派生索引**：只存检索与排序字段（`postId/userId/title/content/tagIds/tagNames/publishedAt/status/updatedAt`），不存点赞数、评论数、封面、作者昵称等展示字段；
- 搜索结果只返回 `postId` 列表与高亮片段，再按 `postId` 批量回表取 `t_post`、`t_user`、`t_post_image`，避免高频计数变化同步到 ES。

**怎么做**：

1. **索引结构**：
   - 别名 `glimmer_post` 指向物理索引 `glimmer_post_v1`，重建时新建 `v2` 后原子切换别名；
   - `title` / `content` 用 IK 分词（`ik_max_word` 建索引、`ik_smart` 查询），`title^3`、`tagNames^2`、`content^1`；
   - `tagIds` 用于标签精确过滤，`tagNames` 同时保留 `keyword` 与 `text` 子字段；
   - 只索引公开可见的帖子（`status IN (0,1) AND is_deleted=0`）；审核拒绝 / 下架 / 删除时移除文档。
2. **写入同步**：
   - 发帖（普通用户=0、管理员=1）、审核通过（0→1）、恢复（3→1）、编辑（0/1/2→0，重新提交）、AI 打标完成（标签变化）→ 提交事务后发送 `SEARCH_UPSERT` 事件；
   - 审核拒绝（0→2）、下架（0/1→3）、作者删除 → 发送 `SEARCH_DELETE` 事件；
   - 消费者**不信任事件里的字段**，只取 `postId` 回查 MySQL 当前状态：公开可见则 `index`，否则 `delete`。因此事件乱序、重复投递都能收敛到正确状态，无需版本号。
3. **查询流程**：
   - `multi_match` 检索标题 / 正文 / 标签，`bool.filter` 兜底 `status IN (0,1)`；
   - 按 `_score` + `publishedAt` 排序，前 N 页用 `from/size`，深分页用 `search_after`；
   - 取回 `postId` 后批量查 `t_post` 过滤逻辑删除 / 非发布状态，再批量查作者与封面；
   - 标签筛选直接把 `tagId` 作为 `term` 过滤，不再回 `t_post_tag` 反查。
4. **兜底与重建**：
   - ES 不可用：搜索接口降级返回热榜 / 最新帖子，并告警；不阻塞其他功能；
   - 事件漏发或消费失败：每 5 分钟扫描 `t_post.updated_at` 与 `t_post_tag.created_at` 的近期变更补索引；
   - 全量重建：管理端触发或运维脚本 scroll MySQL 公开可见帖，写入新索引后切换别名。

**不落库**：ES 索引不写入 MySQL；MySQL 不建全文索引。ES 数据可随时从 MySQL 重建。

**边界**：

- `LIKE '%关键词%'` 用不上 B+Tree，1000 万帖子会全表扫，已被 ES 取代；
- ES 与 MySQL 是最终一致（正常秒级，补偿分钟级）；搜索结果的点赞 / 评论数回表读取，不承诺与 ES 文档同步；
- 帖子编辑若改变正文或标签，必须重新发 `SEARCH_UPSERT`；仅计数变化不发搜索事件，避免 ES 写放大；
- IK 分词插件版本必须与 ES 版本严格一致，Docker 镜像中预装。

#### F-09 图片上传（OSS）（P0）

**架构落点**：§4.2.5（后端中转上传）

**用到的表**：上传阶段**不写表**；发帖时写 `t_post_image`

**怎么做**：

1. 前端以 `multipart/form-data` 提交 `POST /api/v1/files/images`。
2. 后端校验扩展名与大小，生成对象名，由 `OssStorageService` 上传到 OSS，返回图片 URL。
3. 发帖（F-05）时后端校验：
   - URL 域名 / 路径白名单；
   - 文件大小、类型元数据；
   - 然后写入 `t_post_image`。
4. 开发与发布都只使用 OSS，共用一个桶，不提供本地存储实现。

**不落库**：图片二进制在 OSS；MySQL 只存 URL 与顺序。

**边界**：

- MVP 文件流经后端中转，受 5MB 上限约束；直传 OSS（预签名 URL）列为演进；
- 未发帖的孤儿图片可由 OSS 生命周期规则清理；
- 图片是必需数据，上传失败明确报错，不做降级。

#### F-10 内容审核 / 下架（管理员）（P0 审核动作 / P1 下架恢复）

**架构落点**：§3.4（admin 模块）、§6.10.4（垂直越权）

**用到的表**：`t_post` + ES 索引 `glimmer_post`（发布态同步）

**状态机**：

```
普通用户发帖 → 已发布·待审核(0) ──通过──→ 已发布(1) ──下架──→ 已下架(3)
                    │                       ↑                    │
                    ├──拒绝──→ 审核拒绝(2)  └────── 恢复 ────────┘
                    └──下架──────────────────────────────────────→ 已下架(3)

编辑（作者本人，status=0/1/2）→ 状态回到 已发布·待审核(0)
管理员发帖 → 已发布(1)（跳过审核）
```

**怎么做**：

1. **待审队列**：管理端按 `status=0 AND is_deleted=0 ORDER BY created_at` 分页查 `t_post`；可按作者、时间筛选；`idx_status_deleted_created` 支撑。`status=0` 的帖子已公开，审核不是发布前置条件。
2. **通过**（0→1）：
   - `UPDATE t_post SET status=1, audited_at=NOW(), audited_by=?, audit_reason=NULL WHERE id=? AND status=0 AND is_deleted=0`；
   - 不修改 `published_at`、`last_interaction_at`，不重复写扩散；可见性不变；
   - 删详情缓存（状态字段变化）；发送 `SEARCH_UPSERT` 更新 ES 中的状态字段；
   - 作者在“我的帖子”看到状态变为已发布。
3. **拒绝**（0→2）：
   - 原因必填：`UPDATE t_post SET status=2, audit_reason=?, audited_at=NOW(), audited_by=? WHERE id=? AND status=0 AND is_deleted=0`；
   - 帖子立即从公开列表 / Feed / 热榜 / 搜索消失；已进入粉丝收件箱的 ID 不主动清理，读 Feed 时过滤；
   - 发送 `SEARCH_DELETE`，从搜索索引移除；
   - 作者可查看拒绝原因，编辑后重新提交（2→0，清空 `audit_*`，重新进入队列，并立即重新公开）；
   - 作者也可编辑 `status=0/1` 的帖子，编辑后统一回到 0 待审核；已下架（`status=3`）不可编辑，需管理员恢复或作者删除。
4. **下架**（0/1→3）：
   - 原因必填；CAS 更新 `status=3, audit_reason=?, audited_at=NOW(), audited_by=? WHERE id=? AND status IN (0,1) AND is_deleted=0`；
   - 删除 Redis 详情缓存；布隆过滤器不能删除，但详情查询会先查 `t_post` 状态，不影响正确性；
   - 发送 `SEARCH_DELETE`，从搜索索引移除；Feed / 热榜读取时过滤。
5. **恢复**（3→1）：
   - `UPDATE t_post SET status=1, audited_at=NOW(), audited_by=?, audit_reason=NULL WHERE id=? AND status=3 AND is_deleted=0`；
   - 不重置 `published_at`；删除缓存；不重复做 Feed 扩散（帖子已在粉丝收件箱里，只是重新可见）；
   - 发送 `SEARCH_UPSERT`，重新进入搜索索引。
6. **管理员自己的帖子**：
   - 发帖时直接 `status=1`，跳过审核；
   - 管理端“审核 / 下架 / 恢复”拒绝操作自己发的帖子（`post.user_id != currentUserId`）；作者要撤回走用户端删除（`is_deleted=1`）。

**不落库**：审核操作日志 MVP 不建表；如后续需要完整审计，再加 `t_audit_log`（演进）。

**边界**：

- 用户删除帖子走 `is_deleted=1`，与管理员下架的 `status` 分开，两条链路互不替代；
- 作者删除同样要删详情缓存、发 `SEARCH_DELETE`；已进入粉丝收件箱的帖子不主动清理，读 Feed 时过滤；
- 已删除的帖子不能被审核 / 下架 / 恢复，所有管理端 SQL 都带 `is_deleted=0`；
- 下架不影响 `t_like` / `t_comment` 数据，只是不再对外可见；
- Feed / 热榜 / 搜索都必须过滤 `status IN (0,1)` 与 `is_deleted=0`；
- 审核通过 / 拒绝 / 下架 / 恢复都要删详情缓存；状态 CAS 防止并发重复操作。

### 4.3 互动模块

#### F-11 点赞 / 取消点赞（P0）

**架构落点**：§6.4（Lua 原子脚本、异步落库、对账）

**用到的表**：`t_like`、`t_post`

**怎么做**：

1. **实时层（Redis）**：
   - 点赞：Lua 判断 `SISMEMBER liked:{postId}`，未点赞则 `SADD` + `INCR like:count:{postId}`；已点赞幂等返回；
   - 取消：`SREM` + `DECR`，并防止计数为负。
2. **异步落库**：
   - 发送 MQ `{postId, userId, action, timestamp}`；
   - 消费者处理点赞：`INSERT t_like`，插入成功才 `UPDATE t_post SET like_count=like_count+1`；唯一键冲突说明重复，跳过；
   - 消费者处理取消：`DELETE t_like`，删除成功才 `UPDATE t_post SET like_count=GREATEST(like_count-1,0)`；未删除说明重复，跳过。
3. **查询**：
   - 详情页“我是否点赞”：优先 Redis `SISMEMBER`，未命中查 `t_like`；
   - 用户点赞列表：按 `t_like (user_id, created_at)` 分页。
4. **对账**：定时按 `post_id` 统计 `t_like` 行数，修正 `t_post.like_count` 与 Redis 计数。

**不落库**：Redis 点赞 Set、实时计数。

**边界**：

- `uk_user_post` 是最终幂等保障；Redis 标记会过期 / 丢失，不能作为正确性依据；
- 先写关系、再改计数，保证重复消息不会重复加 / 减；
- `t_like` 物理删除，允许取消后重新点赞。

#### F-12 收藏 / 取消收藏（P1）

**架构落点**：架构未单列收藏方案；MVP 按低频互动简化处理

**用到的表**：`t_collect`、`t_post`

**怎么做**：

1. **收藏**（同步事务）：
   - `INSERT t_collect (user_id, post_id, created_at)`；
   - 插入成功 → `UPDATE t_post SET collect_count=collect_count+1 WHERE id=?`；
   - 唯一键冲突 → 视为已收藏，幂等返回。
2. **取消**：
   - `DELETE FROM t_collect WHERE user_id=? AND post_id=?`；
   - 删除成功 → `UPDATE t_post SET collect_count=GREATEST(collect_count-1,0)`。
3. **查询**：
   - 详情页“我是否收藏”：查 `t_collect`；
   - 我的收藏列表：按 `(user_id, created_at)` 分页，再批量取帖子摘要。
4. **对账**：定时按 `post_id` 统计 `t_collect` 修正计数。

**不落库**：MVP 不为收藏单独建 Redis 集合或 MQ 链路。

**边界**：

- 收藏频率远低于点赞，同步写库足够；后续量级上来再复制点赞的异步方案；
- `uk_user_post` 防重复；
- 物理删除，允许重新收藏。

#### F-13 评论 / 回复（P0）

**架构落点**：§6.9.3（情感分析异步）

**用到的表**：`t_comment`、`t_post`、`t_user`（展示作者）

**怎么做**：

1. **发一级评论**：
   - 事务内 `INSERT t_comment (post_id, user_id, parent_id=0, reply_to_user_id=NULL, content, ...)`；
   - `UPDATE t_post SET comment_count=comment_count+1, last_interaction_at=NOW(3) WHERE id=?`。
2. **回复**：
   - 校验父评论属于同一帖子；
   - 若父评论本身是回复，把 `parent_id` 归一化为根评论 ID，`reply_to_user_id` 记录被回复人；
   - 同样在事务内插入并更新 `comment_count`、`last_interaction_at`。
3. **异步情感分析**：提交后发 MQ，消费者 `UPDATE t_comment SET sentiment=?, sentiment_prompt_version=?`。
4. **查询**：
   - 一级评论：`WHERE post_id=? AND parent_id=0 AND is_deleted=0 ORDER BY created_at`，走 `idx_post_parent_created`；
   - 回复：`WHERE parent_id=? AND is_deleted=0 ORDER BY created_at`；
   - 作者信息批量查 `t_user`。
5. **删除**：逻辑删除 `is_deleted=1`，`comment_count` 递减；若存在子回复，保留占位避免回复树断裂。

**不落库**：评论列表缓存（如需）、情感分析结果直接在 `t_comment`。

**边界**：

- 只做两级，不做无限嵌套；
- 评论内容入库前转义，防 XSS；
- 情感分析失败保持 `sentiment=NULL`，不阻塞评论。

#### F-14 弹幕（WebSocket 实时）（P0）

**架构落点**：§6.8（连接鉴权、消息处理、广播、历史）

**用到的表**：`t_user`（仅连接时取昵称）；**不建弹幕表**

**怎么做**：

1. **握手鉴权**：`/ws/danmaku?roomId=...&token=...`，校验 JWT + Redis Token；从用户缓存或 `t_user` 取一次昵称，写入 session attributes。
2. **发送消息**：
   - 长度 ≤ 50 个 Unicode code point；
   - HTML 转义 / 去标签；
   - 组装 `messageId/userId/nickname/content/ts`；
   - `LPUSH glimmer:ws:history:{roomId}` + `LTRIM 0 199` + `EXPIRE 24h`；
   - 广播给本机该房间所有 session。
3. **历史回放**：连接成功后 `LRANGE 0 49`，反转成时间正序推送。
4. **不落库**：消息、历史、在线状态均不写 MySQL。

**边界**：

- MVP 单机本地广播；多实例演进用 Redis Pub/Sub；
- 敏感词过滤不做，列为演进；
- Redis 故障时历史降级，广播继续；
- `t_user` 只在连接时读一次，不能逐条弹幕查库。

### 4.4 Feed 流与推荐

#### F-16 关注流（推 / 拉结合）（P0）

**架构落点**：§6.5（阈值 1000、写扩散、拉模式、归并、游标分页）

**用到的表**：`t_user_follow`、`t_user`、`t_post`、`t_post_image`

**怎么做**：

1. **写扩散（推）**：
   - 发帖事务提交后，查作者粉丝列表；
   - 粉丝数 < 1000：分批 `ZADD glimmer:feed:inbox:{fanId} {timestamp} {postId}`，并 `ZREMRANGEBYRANK 0 -201` 只保留最近 200 条；只推给最近 30 天登录过的粉丝（`glimmer:user:active`）；
   - 粉丝数 ≥ 1000 的大 V：**不推送**，走拉模式。
2. **关注时回填**：关注成功后查该博主最近 50 条公开可见帖子，写入我的收件箱。
3. **读关注流**：
   - 取我的收件箱首页；
   - 查我关注的大 V（`t_user_follow JOIN t_user`，筛 `follower_count >= 1000`）；
   - 对这些大 V，按 `t_post (user_id, status, is_deleted, published_at)` 各取最近公开帖子；
   - K 路归并，按时间倒序取一页；
   - 过滤审核拒绝 / 已删除 / 已下架帖子；
   - 批量取 `t_user` 作者信息与 `t_post_image` 封面。
4. **冷启动**：收件箱为空时先按“关注列表 + 最近公开帖子”回源重建一页并异步补箱，无关注或结果为空再降级返回热榜 Top N。

**不落库**：收件箱、发件箱都在 Redis。

**边界**：

- 收件箱必须裁剪，否则冷用户会无限增长；
- 取关不清理收件箱，查询时按当前关注列表过滤；
- 写扩散失败按决策 2 处理（best-effort，不新增 Outbox 表）；
- 大 V 的最近帖子可用 Redis 发件箱缓存，避免每次查 DB。

#### F-17 推荐流（按热度 / 标签）（P1）

**架构落点**：§6.6（热榜）、PRD F-17

**用到的表**：`t_post`、`t_post_tag`、`t_tag`、`t_user`

**怎么做**：

1. **热度召回**：从 Redis 热榜 ZSet 取 Top N 帖子。
2. **标签召回**：
   - 按用户兴趣标签（MVP 可先取热榜帖子的标签或人工配置）找到 `tag_id`；
   - 经 `t_post_tag.idx_tag_post` 取帖子 ID；
   - 关联 `t_post` 过滤状态，按时间 / 热度排序。
3. **合并去重**：热度 + 标签结果按 `postId` 去重，再按分数或时间排序。
4. **组装**：批量查 `t_post`、`t_user`、`t_post_image`。

**不落库**：推荐结果可短 TTL 缓存；MVP 不建推荐表。

**边界**：

- F-26 的向量召回是 P2，不在 MVP；
- 推荐流必须复用 F-06 的过滤与批量组装逻辑，避免重复实现。

#### F-18 帖子热榜（P1）

**架构落点**：§6.6（热度公式、每 5 分钟重算、Top 1000）

**用到的表**：`t_post`（扫描与计数）

**怎么做**：

1. 定时任务每 5 分钟执行，用 Redisson 分布式锁防重入。
2. 扫描 `t_post`：
   - `WHERE last_interaction_at >= NOW() - INTERVAL 24 HOUR AND status IN (0,1) AND is_deleted=0`；
   - 走 `idx_status_deleted_interaction`。
3. 计算 `score = (1×like_count + 2×comment_count + 0.1×view_count) / (ageHours + 2)^1.5`。
4. `ZADD glimmer:feed:hot {score} {postId}`，`ZREMRANGEBYRANK 0 -1001` 保留 Top 1000。
5. 查询时 `ZREVRANGE` 取 `postId`，批量取帖子摘要。

**不落库**：热榜 ZSet；浏览量先在 Redis 累加，定时合并回 `t_post.view_count` 并更新 `last_interaction_at`。

**边界**：

- 时间衰减项持续变化，所以必须定时重算；
- 冷启动时全量扫描最近 24h 帖子重建；
- 刷赞 / 刷评论的治理是演进项，MVP 只做权重克制与唯一键限制。

#### F-20 秒杀抢购（防超卖、限购、幂等）（P0）

**架构落点**：§6.7.2（Lua）、§6.7.5（Publisher Confirm）、§6.7.6（异步下单）

**用到的表**：`t_user`（鉴权）、`t_seckill_activity`（DB 库存）、`t_seckill_order`（订单）

**怎么做**：

1. **抢购入口**：
   - `userId` 从 JWT 取；
   - 从 Redis 活动缓存校验活动存在、已开始、未结束；
   - 执行 Lua：校验库存 > 0、`bought < limit_num`，然后 `DECR stock` + `HINCRBY bought 1`；
   - 生成 `requestId`，发送 MQ 消息 `{userId, activityId, requestId}`；
   - 返回“排队中 + requestId”。
2. **Publisher Confirm 失败**：回滚 Redis 库存与 `bought`，返回“系统繁忙”。
3. **消费者下单**（事务）：
   - 幂等快速校验：Redis SETNX `glimmer:seckill:idem:{userId}:{activityId}`；已存在则查 DB 是否已有订单，有则 ACK，无则继续（防止 SETNX 后、提交前崩溃）；
   - `UPDATE t_seckill_activity SET stock=stock-1 WHERE id=? AND stock>=1`；受影响行数为 0 → 告警并回补 Redis；
   - `INSERT t_seckill_order (order_no, request_id, user_id, activity_id, quantity=1, amount=活动价快照, status=待支付)`；
   - 唯一键冲突 → 幂等返回；
   - 提交后发送延迟关单消息，ACK。

**不落库**：Redis 库存、限购计数、幂等标记、活动缓存。

**边界**：

- 抢购主链路**不查 MySQL**；
- 三个唯一键分别兜底订单号、消息重投、一人一单；
- `request_id` 唯一索引防止已关闭订单被旧消息复活；
- MVP 限购 N=1，一人一单；关单不释放抢购资格。

#### F-21 秒杀订单（异步下单、超时关单）（P0）

**架构落点**：§6.7.4（延迟消息）、§6.7.7（关单回补）、§6.7.8（对账）

**用到的表**：`t_seckill_order`、`t_seckill_activity`

**怎么做**：

1. **建单**：消费者在事务内扣活动库存 + 插入订单，订单状态 = 待支付。
2. **支付**：
   - 支付回调按 `order_no` CAS：`UPDATE t_seckill_order SET status=已支付, paid_at=?, pay_trade_no=? WHERE order_no=? AND status=待支付`；
   - 受影响行数为 0 说明已处理或状态不符，幂等返回。
3. **超时关单**：
   - 延迟消息 30 分钟触发；定时扫描兜底（创建 > 35 分钟仍待支付）；
   - 事务内 `UPDATE t_seckill_order SET status=已关闭, closed_at=? WHERE order_no=? AND status=待支付`；
   - 同一事务 `UPDATE t_seckill_activity SET stock=stock+1 WHERE id=?`；
   - 提交后 Redis 库存 +1；**不回补 `bought`**（一人一单），`requestId` 结果标记为 `CLOSED` 供查询。
4. **一人一单**：已关闭订单仍占用 `uk_user_activity`，用户不能用新 `requestId` 重新抢。
5. **对账**：活动结束后按 `t_seckill_activity.stock + Σ有效订单 quantity == total_stock` 校验；静默期以 DB 重建 Redis。

**不落库**：延迟消息、Redis 库存 / 限购 / 幂等标记。

**边界**：

- DB 扣库存与建单必须同一事务；
- 关单回补 Redis 前要判断活动是否仍在有效期，避免错误创建库存 Key；
- 库存回补不自动执行（除关单这条确定性路径），异常只告警。

#### F-22 抢购记录 / 订单查询（P1）

**架构落点**：§6.7（订单查询）、§6.10.4（越权）

**用到的表**：`t_seckill_order`、`t_seckill_activity`、`t_user`

**怎么做**：

1. **我的订单列表**：
   - `SELECT ... FROM t_seckill_order WHERE user_id=? ORDER BY created_at DESC`，走 `idx_user_created`；
   - 关联 `t_seckill_activity` 取活动标题、图片、价格；
   - 支持按状态筛选（待支付 / 已支付 / 已关闭）。
2. **订单详情**：
   - 按 `order_no` 或主键查；
   - 校验 `order.user_id == 当前 userId`，防止水平越权。
3. **管理端 / 对账**：
   - 按 `(activity_id, status)` 统计订单，走 `idx_activity_status`；
   - 超时扫描按 `(status, created_at)`，走 `idx_status_created`。

**不落库**：订单查询缓存（可选）。

**边界**：

- 不建支付流水表：MVP 模拟支付，`pay_trade_no` 直接记在订单上；
- 订单列表必须按 `user_id` 过滤，不能只按 `order_no` 查；
- 已关闭订单保留历史，不物理删除。

### 4.6 AI 能力模块

#### F-23 帖子自动打标签 / 分类（P1）

**架构落点**：§6.9.2（异步打标、候选集、规则降级、Prompt 版本）

**用到的表**：`t_post`、`t_tag`、`t_post_tag`

**怎么做**：

1. 发帖提交后发送 MQ 到独立队列 `glimmer.ai.tag`。
2. 消费者读取 `t_post` 的标题、正文（截断 500 字）。
3. 从 `t_tag` 读取候选标签集，拼进 Prompt；**不在代码里硬编码标签**。
4. 调 DeepSeek，要求只输出 JSON 数组。
5. 解析并校验标签必须在候选集内。
6. `INSERT IGNORE t_post_tag (post_id, tag_id, source=AI, prompt_version=...)`；人工标签（`source=MANUAL`）不被覆盖。
7. `UPDATE t_post SET ai_tag_status=成功`。
8. 标签写入后发送 `SEARCH_UPSERT`（仅当帖子公开可见，即 `status IN (0,1)`）；审核拒绝 / 下架帖不索引。
9. 失败降级：本地关键词规则匹配，写 `source=RULE`，`ai_tag_status=规则降级`；仍失败则 `ai_tag_status=失败待重试`，由 `idx_ai_tag_status` 扫描重试。

**不落库**：AI 调用结果缓存（相同内容哈希，24h）、队列本身。

**边界**：

- AI 打标绝不能阻塞发帖；
- 输入截断、结果缓存、限流控制成本；
- `prompt_version` 随结果落库，便于定位效果变化；
- 不建 AI 任务表：状态在 `t_post.ai_tag_status`，关系在 `t_post_tag`。

#### F-24 评论情感分析（P1）

**架构落点**：§6.9.3（异步分析、降级）

**用到的表**：`t_comment`（写）、`t_post`（后台聚合时关联）

**怎么做**：

1. 评论提交后发送 MQ 到情感分析队列。
2. 消费者读取评论文本，调 LLM，返回正面 / 中性 / 负面。

5. 失败处理：`sentiment=NULL` 表示未分析，不阻塞评论，不反复重试。

**不落库**：情感分析原始响应、Prompt 全文（只存版本号）。

**边界**：

- 情感分析是增强功能，失败不能影响评论发布；
- 同一评论重复消息只更新同一行，天然幂等；

#### F-31 帖子 AI 助手（流式对话）（P1）

**架构落点**：§6.11（SSE、SseEmitter、中断传播、Redis 上下文、ADR-014）

**用到的表**：`t_post`、`t_post_tag`、`t_tag`（只读）；**不建会话表 / 消息表**

**怎么做**：

1. **创建会话**：
   - `POST /api/v1/ai/chat/session {postId}`；
   - 校验 `t_post` 存在且已发布；
   - 写 Redis `glimmer:ai:chat:{sessionId}`：`userId`、`postId`、`createdAt`、`messages=[]`；
   - 返回 `sessionId`。
2. **流式提问**：
   - 校验会话归属 `userId`、会话 `postId` 与请求一致；
   - 读 `t_post` 标题 / 正文（截断 1000 字）；
   - 读 `t_post_tag JOIN t_tag` 标签；
   - 组装 System Prompt + 历史消息 + 本轮问题；
   - 调 DeepSeek 流式接口，`SseEmitter` 逐片段推送；
   - 正常结束后把本轮问答写回 Redis 上下文。
3. **中断**：客户端 abort → `onCompletion/onTimeout/onError` 取消上游流、中断读取线程、释放线程池配额；**已生成内容不写入上下文**。
4. **不落库**：会话上下文 30 分钟滑动过期；无历史会话列表。

**边界**：

- 每条流必须校验会话归属，防止横向越权；
- 上下文丢失视为新会话，只带 System Prompt；
- 不建 AI 会话表 / 消息表（ADR-014）；
- 线程池满时快速失败，返回友好错误，不无限排队。

### 4.8 横向方案与表的关系

> 架构中的缓存、幂等、鉴权是跨功能的横向方案，不直接对应某个 F 编号，但决定了表怎么被读写。

#### 6.2 缓存设计

**涉及的表**：`t_post`（详情）、`t_user`（用户信息）、`t_seckill_activity`（活动信息）

**怎么做**：

1. **Cache Aside**：读时未命中查 MySQL 并回填；写时先更新 MySQL，再删除缓存。
2. **延迟双删**：更新 DB → 删缓存 → 延迟 500ms 再删一次，清理窗口期内被回填的旧值。
3. **防穿透**：布隆过滤器数据来自 `t_post` 主键；空值缓存兜住假阳性与已删除数据。
4. **防击穿**：热点帖子缓存重建加分布式锁。
5. **防雪崩**：TTL 加随机抖动；热榜前 100 帖预热。
6. **秒杀活动缓存**：`t_seckill_activity` 预热到 Redis，抢购路径不查 DB。

**表与缓存的关系**：MySQL 是真相源，Redis 可重建；只有秒杀库存是“Redis 为权威、DB 落账”的有损设计，需要 §6.7.8 对账兜底。

---

#### 6.3 统一幂等方案

**涉及的表与唯一键**：

| 场景 | 表 | 唯一键 / 幂等手段 |
|---|---|---|
| 点赞 | `t_like` | `uk_user_post` |
| 收藏 | `t_collect` | `uk_user_post` |
| 关注 | `t_user_follow` | `uk_follower_followee` |
| 帖子标签 | `t_post_tag` | `uk_post_tag` |
| 秒杀订单 | `t_seckill_order` | `uk_order_no`、`uk_request_id`、`uk_user_activity` |
| 抢购入口 | Redis | `SETNX glimmer:seckill:idem:{userId}:{activityId}` |
| MQ 消费 | Redis + 业务唯一键 | `SETNX consumed:{msgId}`，最终靠业务唯一键兜底 |

**原则**：

- Redis 幂等标记是**性能优化**，会过期、会丢；
- 真正的正确性由数据库唯一索引 / 状态机 CAS 兜底；
- **MVP 不建 MQ 消费记录表**：消费者用 Redis SETNX + 业务唯一键，架构 §6.3.1 的“消费记录表”表述需要修订。

---

#### 6.10 鉴权与安全

**涉及的表**：`t_user`（`role`、`status`）

**怎么做**：

1. JWT 的 `userId` 是唯一可信身份来源，禁止从请求参数取 userId。
2. `t_user.role` 控制管理端权限；`t_user.status` 控制封禁。
3. 登出 / 踢人靠 Redis Token 白名单，不建 Token 表。
4. 登录、验证码、抢购、AI 提问限流走 Redis，不建限流表；其余接口不单独限流。
5. 手机号唯一索引防止重复注册；响应 DTO 脱敏。
6. 上传只允许白名单类型与大小，URL 写入 `t_post_image` / `t_user.avatar_url` 前校验。

**与表设计的关系**：

- 不在业务表存密码（本项目用验证码登录）；
- 不在业务表存 Token；
- 敏感字段（手机号）只在 `t_user`，不冗余到帖子 / 评论 / 订单。

## 5. 关键链路中的表操作

### 5.1 发帖（F-05 → F-23 / F-16）

```
① 鉴权取 userId
② 校验图片 URL
③ 事务：INSERT t_post
        → 批量 INSERT t_post_image
        → 批量 INSERT t_post_tag（source=MANUAL）
④ 提交
⑤ 提交后异步：
   - 布隆过滤器 add(postId)
   - MQ 触发 Feed 写扩散（读 t_user_follow 的粉丝）
   - MQ 触发 AI 打标
⑥ AI 消费者：读 t_post → 调 LLM → 校验标签
   → INSERT IGNORE t_post_tag（source=AI/RULE）
   → UPDATE t_post.ai_tag_status
```

### 5.2 帖子详情（F-07）

```
布隆 → Redis 缓存 → 空值缓存 → MySQL

MySQL 内：
  t_post（主表）
  + t_user（作者，批量）
  + t_post_image（按 sort_order）
  + t_post_tag JOIN t_tag
  + t_like / t_collect（当前用户是否点赞 / 收藏）
  + t_comment（一级评论首页）

计数：Redis 实时值优先，DB 兜底
```

### 5.3 点赞（F-11）

```
请求 → Redis Lua：SISMEMBER / SADD / INCR
     → 发 MQ → 返回

消费者：
  INSERT t_like（uk_user_post）
    ├─ 插入成功 → t_post.like_count + 1
    └─ 唯一键冲突 → 跳过，不重复加

取消点赞对称：先删 t_like，删除成功才减计数

对账：每小时按 t_like 统计修正 t_post.like_count 和 Redis
```

### 5.4 评论（F-13 → F-24）

```
① 事务：INSERT t_comment
        UPDATE t_post
          SET comment_count = comment_count + 1,
              last_interaction_at = now()
② 提交
③ MQ → 情感分析消费者
   → UPDATE t_comment
       SET sentiment = ?, sentiment_prompt_version = ?
④ 列表：
   一级评论 WHERE post_id=? AND parent_id=0 AND is_deleted=0
   回复     WHERE parent_id=?
```

### 5.5 关注流（F-16）

```
写扩散：
  发帖提交后 → 查 t_user_follow 的粉丝
  → 每个粉丝 ZADD Redis 收件箱
  → 大 V（t_user.follower_count ≥ 1000）跳过

读：
  ① 取我的 Redis 收件箱
  ② 查我关注的大 V（t_user_follow JOIN t_user）
  ③ 按 t_post 的 (user_id, status, is_deleted, published_at)
     取他们最近公开可见帖
  ④ 归并排序、过滤审核拒绝 / 已删除 / 已下架
  ⑤ 批量取帖子摘要与作者
```

### 5.6 热榜（F-18）

```
每 5 分钟（分布式锁）：
  ① 扫描 t_post
     WHERE last_interaction_at >= now-24h
       AND status IN (0,1) AND is_deleted = 0
     走 idx_status_deleted_interaction
  ② score = (1×like_count + 2×comment_count + 0.1×view_count)
             / (ageHours + 2)^1.5
  ③ ZADD glimmer:feed:hot，保留 Top 1000
  ④ 查询时 ZREVRANGE + 批量 MGET 帖子摘要
```

浏览量由 Redis 累加，定时合并到 `t_post.view_count` 并重置，同时更新 `last_interaction_at`。

### 5.7 秒杀（F-19 ~ F-22）

```
活动创建：
  INSERT t_seckill_activity
  → 发布时预热 Redis：stock、活动信息、布隆

抢购：
  Redis Lua 校验库存 / 限购 → 扣减 → 发 MQ → 返回排队中

下单消费者：
  幂等校验
  → 事务：
      UPDATE t_seckill_activity
        SET stock = stock - 1
        WHERE id = ? AND stock >= 1
      INSERT t_seckill_order
        （status=0, request_id）
  → 提交 → 发延迟关单消息

支付：
  UPDATE t_seckill_order
    SET status=1, paid_at=?, pay_trade_no=?
  WHERE order_no=? AND status=0

超时关单：
  事务：
    UPDATE t_seckill_order
      SET status=2, closed_at=?
    WHERE order_no=? AND status=0
    UPDATE t_seckill_activity
      SET stock = stock + 1
    WHERE id=?
  提交后：
    Redis 库存 +1；不回补 bought；requestId 结果标记 CLOSED

对账：
  t_seckill_activity.stock
  + Σ t_seckill_order.quantity（status in 0,1）
  == total_stock
```

### 5.8 AI 助手（F-31）

```
创建会话：
  校验 t_post 存在且可见
  → Redis 写 glimmer:ai:chat:{sessionId}
     （userId、postId、messages）

流式提问：
  读 t_post（标题 / 正文）
  + t_post_tag JOIN t_tag（标签）
  → 组装 System Prompt
  → 调 DeepSeek 流式
  → SSE 逐片段推送
  → 更新 Redis 上下文

全程不写 MySQL；会话 30 分钟过期。
```

## 6. 分析结论：需要补充的字段、索引与口径

### 6.1 建议直接补进表设计（不增加表）

| 项 | 建议 | 原因 |
|---|---|---|
| 关注 / 粉丝计数 | `t_user` 增加 `following_count`、`follower_count` | Feed 判断大 V 需要粉丝数；1000 万行上 `COUNT(*)` 不可接受 |
| 帖子审核字段 | `t_post` 增加 `audit_reason`、`audited_at`、`audited_by` | 支撑先发后审的通过 / 拒绝与发布后的下架 / 恢复 |
| 帖子发布时间 | `t_post` 增加 `published_at` | 创建（首次发布）时写入，Feed / 热榜 / 搜索按它排序；审核、下架恢复、编辑重新提交不重置 |
| 关注列表索引 | `t_user_follow` 补 `(follower_id, created_at)`、`(followee_id, created_at)` | 关注 / 粉丝列表按时间分页 |
| 评论查询索引 | `t_comment` 的评论查询索引包含 `is_deleted` | 逻辑删除后避免回表过滤 |
| 收藏链路 | `t_collect` 同步写库 + 同事务更新 `t_post.collect_count` | 收藏频率低，不值得复制点赞的异步链路 |
| AI 标签合并 | AI 写 `t_post_tag` 用 `INSERT IGNORE`，不覆盖 `source=MANUAL` | 人工标签优先 |
| AI 标签状态 | `ai_tag_status`：0=待处理、1=成功、2=规则降级、3=失败待重试 | 供重试任务扫描 |
| 搜索增量同步 | `t_post` 增加 `idx_updated_at`；`t_post_tag` 增加 `idx_created_at` | ES 漏事件补偿：按更新时间 / 标签写入时间扫描近期变更 |

### 6.2 决策结论（三项均已拍板）

#### 决策 1：F-08 搜索用什么索引？（已拍板：Elasticsearch）

**结论**：MVP 直接引入 Elasticsearch 8 + IK 分词，MySQL 不建全文索引。

- MySQL 是帖子正文、标签、状态的真相源；ES 只保存检索与排序字段，索引是派生数据；
- 搜索结果只拿 `postId` 与高亮，再回表批量补全作者、封面、计数，避免高频计数写入 ES；
- 同步链路：业务事务提交后发 MQ → 消费者按 `postId` 回查 MySQL 当前状态 → `index` 或 `delete`；事件乱序 / 重复都能收敛；
- 补偿：每 5 分钟扫描 `t_post.updated_at` 与 `t_post_tag.created_at` 近期变更；另提供全量重建脚本；
- 取舍：多一个 ES 容器与 IK 插件、一套同步与重建流程；换来中文分词、相关度排序、标签过滤与后续向量检索的复用能力。

**为什么不选 MySQL FULLTEXT ngram**：中文分词与相关度弱于 ES；全文索引与状态过滤无法组合成理想索引；后续仍要迁移 ES，重复建设。**为什么不选“标签 + 标题前缀”**：正文搜不到，中文前缀匹配体验差，达不到 F-08 的关键词搜索目标。

#### 决策 2：Feed 写扩散失败后怎么补偿？（已拍板：best-effort + 告警）

**结论**：扩散失败只记录指标并告警，不做自动补偿；同时修订 02 §6.5.7 的“未投递记录”表述。

- 发帖成功后异步扩散（普通用户与管理员一致）；发送失败不影响帖子发布；
- 漏推的帖子仍可从作者主页、热榜、搜索、拉模式看到；关注流允许这一极端情况下的缺失；
- 保持 11 张 MySQL 表，不引入 Outbox；若后续对关注流完整性要求提高，再将 Outbox 作为演进项。

#### 决策 3：审核状态语义（已拍板：先发后审）

**结论**：采用「先发后审」。

- `status`：0=已发布待审核、1=已发布、2=审核拒绝、3=已下架；`is_deleted` 独立，公开可见条件为 `status IN (0,1) AND is_deleted=0`。
- 普通用户发帖后立即公开，同时进入待审核队列；**管理员发帖直接已发布，跳过审核**。
- `published_at` 在创建（首次发布）时写入；Feed 写扩散与搜索索引也在发帖成功后立即触发，不再等待审核。
- 审核通过（0→1）只更新状态与审核字段，不改变可见性；**审核拒绝（0→2）立即从公开列表 / Feed / 搜索 / 热榜移除**。
- **作者可编辑 0/1/2，编辑后统一回到 0，清空审核字段并再次进入队列**；原状态 1/2 立即重新公开，原状态 0 保持公开；编辑不重置 `published_at`，不重复写扩散，但需要 `SEARCH_UPSERT` 更新索引。
- 作者自删走 `is_deleted=1`；管理员下架走 `status=3` + 审核字段，两条链路独立。
- `audited_by/audited_at` 记录最近一次发布态裁决（通过 / 拒绝 / 下架 / 恢复）；`audit_reason` 在拒绝 / 下架时必填，通过 / 恢复时清空。
- 审核不再阻塞发布，不再是发布关键路径；审核拒绝 / 下架是内容治理关键路径。审核动作仍按 P0 保障时效。
