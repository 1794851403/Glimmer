## 1. 设计规范与约定

### 1.1 命名规范

| 对象 | 规范 | 示例 |
|---|---|---|
| 表 | `t_` + 小写下划线 | `t_post`、`t_seckill_order` |
| 字段 | 小写下划线 | `user_id`、`published_at` |
| 主键 | `id` | `id` |
| 唯一索引 | `uk_` + 语义 | `uk_user_post` |
| 普通索引 | `idx_` + 语义 | `idx_status_deleted_published` |
| 布尔字段 | `is_` 前缀 | `is_deleted` |
| 时间字段 | `_at` 后缀 | `created_at`、`published_at` |
| 计数字段 | `_count` 后缀 | `like_count` |
| 状态字段 | `status` / `*_status` | `status`、`ai_tag_status` |
| 外键 | **不建物理外键**，字段统一 `xxx_id` | `post_id`、`user_id` |

### 1.2 数据类型约定

| 场景 | 类型 | 说明 |
|---|---|---|
| 主键 | `BIGINT UNSIGNED AUTO_INCREMENT` | 趋势递增，索引局部性好；不用 UUID |
| 状态 / 枚举 | `TINYINT UNSIGNED` | 不用 `ENUM`，避免加值改表 |
| 布尔 | `TINYINT UNSIGNED` | 0/1，配合 `CHECK` |
| 时间 | `DATETIME(3)` | 毫秒精度；不用 `TIMESTAMP`，避免时区与 2038 问题 |
| 金额 | `DECIMAL(10,2)` | 不用 `FLOAT` / `DOUBLE` |
| 短文本 | `VARCHAR(n)` | 按实际上限设置，不用统一 `VARCHAR(255)` |
| 长正文 | `TEXT` | 单帖正文上限 20,000 字符（约 64KB 内） |
| 大对象 | 不落 MySQL | 图片在 OSS，MySQL 只存 URL |

### 1.3 存储引擎与字符集

- 引擎：`InnoDB`；
- 字符集：`utf8mb4`；
- 排序规则：`utf8mb4_0900_ai_ci`（MySQL 8 默认，中文与 emoji 均安全）；
- 行格式：`DYNAMIC`。

### 1.4 约束约定

1. **不使用物理外键**：由应用层保证引用完整性，配合索引与对账；避免分库分表与批量删除时的外键开销。
2. **唯一索引是幂等最后防线**：点赞、收藏、关注、订单、MQ 重投都靠唯一键兜底。
3. **`CHECK` 只约束枚举与范围**：MySQL 8.0.16+ 真正生效；不把复杂业务规则放进数据库。
4. **逻辑删除只用于帖子与评论**：`is_deleted`；关系表（点赞、收藏、关注、帖子标签）物理删除，允许重新建立。
5. **计数不实时 `COUNT(*)`**：`t_user.following_count/follower_count`、`t_post.*_count` 由事务或异步 MQ 维护。

### 1.5 时间与排序口径

| 字段 | 口径 |
|---|---|
| `created_at` | 记录创建时间，写入后不变 |
| `updated_at` | 内容 / 状态变更时间；**计数变化不更新它**（SQL 显式 `updated_at = updated_at`） |
| `published_at` | 首次审核通过时间；管理员发帖在创建时写入；下架恢复不重置 |
| `last_interaction_at` | 最近一次点赞 / 评论时间；供热榜扫描 |
| `audited_at` | 最近一次发布态裁决时间（通过 / 拒绝 / 下架 / 恢复） |

**公开列表排序**：`ORDER BY published_at DESC, id DESC`；游标为 `(published_at, id)`，不使用 `OFFSET`。

**时区**：数据库会话 `time_zone = '+08:00'`；JDBC 连接串带 `serverTimezone=Asia/Shanghai`；应用层统一 `Asia/Shanghai`。

## 2. 实体关系

```
t_user 1 ── N t_post 1 ── N t_post_image
  │              │
  │              ├── N t_post_tag N ── 1 t_tag
  │              ├── N t_like      N ── 1 t_user
  │              ├── N t_collect   N ── 1 t_user
  │              └── N t_comment   N ── 1 t_user
  │
  ├── N t_user_follow N ── 1 t_user
  │
  └── N t_seckill_order N ── 1 t_seckill_activity
```

- 逻辑关系如上；**物理上不建外键**。
- `t_comment` 自关联：`parent_id=0` 为一级评论；回复的 `parent_id` 指向根评论，`reply_to_user_id` 记录被回复人。
- `t_seckill_order` 与 `t_seckill_activity` 通过 `activity_id` 关联；活动不物理删除。
- 完整 ER 图见 [03-数据库表结构ER图.png](03-数据库表结构ER图.png)。

## 3. 表结构设计

### 3.1 `t_user` —— 账号与身份主表

**用途**：所有“人”的唯一身份来源；承载角色、封禁状态、资料与关注 / 粉丝计数。

| 字段 | 类型 | 空 | 默认 | 说明 |
|---|---|---|---|---|
| `id` | `BIGINT UNSIGNED` | 否 | 自增 | 主键 |
| `phone` | `VARCHAR(20)` | 否 | — | 手机号，登录唯一标识 |
| `nickname` | `VARCHAR(32)` | 否 | — | 昵称，允许重复 |
| `avatar_url` | `VARCHAR(512)` | 否 | `''` | 头像 URL |
| `bio` | `VARCHAR(200)` | 否 | `''` | 个人简介 |
| `role` | `TINYINT UNSIGNED` | 否 | `0` | 0=普通用户，1=管理员 |
| `status` | `TINYINT UNSIGNED` | 否 | `0` | 0=正常，1=封禁 |
| `following_count` | `INT UNSIGNED` | 否 | `0` | 关注数 |
| `follower_count` | `INT UNSIGNED` | 否 | `0` | 粉丝数 |
| `created_at` | `DATETIME(3)` | 否 | `CURRENT_TIMESTAMP(3)` | 创建时间 |
| `updated_at` | `DATETIME(3)` | 否 | `CURRENT_TIMESTAMP(3)` | 更新时间 |

**索引**：

| 索引 | 字段 | 用途 |
|---|---|---|
| `PRIMARY` | `id` | 主键 |
| `uk_phone` | `phone` | 登录、注册唯一 |
| `idx_status_created` | `status, created_at` | 管理端用户列表 / 封禁筛选 |
| `idx_nickname` | `nickname` | 管理端按昵称搜索 |

**约束**：

- `CHECK (role IN (0,1))`；
- `CHECK (status IN (0,1))`。

**生命周期与边界**：

- 不物理删除；封禁用 `status=1`，并删除 Redis Token 白名单让用户下线；
- 注册并发靠 `uk_phone` 兜底：重复插入捕获唯一键异常后转为登录；
- 关注 / 粉丝计数在关注事务内更新，禁止实时 `COUNT(*)`；
- 验证码、JWT、在线状态在 Redis，不在本表。

---

### 3.2 `t_user_follow` —— 关注关系

**用途**：Feed 推拉模式的输入；用户主页“关注 / 粉丝”列表的数据源。

| 字段 | 类型 | 空 | 默认 | 说明 |
|---|---|---|---|---|
| `id` | `BIGINT UNSIGNED` | 否 | 自增 | 主键 |
| `follower_id` | `BIGINT UNSIGNED` | 否 | — | 关注者 |
| `followee_id` | `BIGINT UNSIGNED` | 否 | — | 被关注者 |
| `created_at` | `DATETIME(3)` | 否 | `CURRENT_TIMESTAMP(3)` | 关注时间 |

**索引**：

| 索引 | 字段 | 用途 |
|---|---|---|
| `PRIMARY` | `id` | 主键 |
| `uk_follower_followee` | `follower_id, followee_id` | 防重复关注 |
| `idx_followee_created` | `followee_id, created_at` | 查粉丝列表、写扩散 |
| `idx_follower_created` | `follower_id, created_at` | 查关注列表、拉模式 |

**约束**：`CHECK (follower_id <> followee_id)`。

**生命周期与边界**：

- **物理删除**，不用逻辑删除；否则重新关注会被唯一键挡住；
- 关注：事务内插入关系 + 双方计数 +1；提交后更新 Redis Set，并回填被关注者最近 50 条**已发布**帖子到我的收件箱；
- 取关：事务内删除关系；受影响行数为 1 才递减双方计数；Redis Set 同步移除；不清理收件箱历史，查询时按当前关注列表过滤。

### 3.3 `t_post` —— 帖子主体

**用途**：内容真相源；互动计数落点；热榜、审核队列、搜索同步的扫描入口。

| 字段 | 类型 | 空 | 默认 | 说明 |
|---|---|---|---|---|
| `id` | `BIGINT UNSIGNED` | 否 | 自增 | 主键 |
| `user_id` | `BIGINT UNSIGNED` | 否 | — | 作者 |
| `title` | `VARCHAR(100)` | 否 | — | 标题 |
| `content` | `TEXT` | 否 | — | 正文，上限 20,000 字符 |
| `status` | `TINYINT UNSIGNED` | 否 | `0` | 0=待审核，1=已发布，2=审核拒绝，3=已下架 |
| `is_deleted` | `TINYINT UNSIGNED` | 否 | `0` | 0=正常，1=作者已删除 |
| `published_at` | `DATETIME(3)` | 是 | `NULL` | 首次审核通过时间；公开列表排序依据 |
| `like_count` | `INT UNSIGNED` | 否 | `0` | 点赞数 |
| `comment_count` | `INT UNSIGNED` | 否 | `0` | 评论数（不含已删除） |
| `collect_count` | `INT UNSIGNED` | 否 | `0` | 收藏数 |
| `view_count` | `INT UNSIGNED` | 否 | `0` | 浏览数 |
| `ai_tag_status` | `TINYINT UNSIGNED` | 否 | `0` | 0=待处理，1=成功，2=规则降级，3=失败待重试 |
| `last_interaction_at` | `DATETIME(3)` | 否 | `CURRENT_TIMESTAMP(3)` | 最近互动时间，热榜扫描 |
| `audit_reason` | `VARCHAR(200)` | 是 | `NULL` | 拒绝 / 下架原因 |
| `audited_at` | `DATETIME(3)` | 是 | `NULL` | 最近一次发布态裁决时间 |
| `audited_by` | `BIGINT UNSIGNED` | 是 | `NULL` | 最近一次裁决管理员 |
| `created_at` | `DATETIME(3)` | 否 | `CURRENT_TIMESTAMP(3)` | 创建时间 |
| `updated_at` | `DATETIME(3)` | 否 | `CURRENT_TIMESTAMP(3)` | 内容 / 状态更新时间 |

**索引**：

| 索引 | 字段 | 支撑的查询 |
|---|---|---|
| `PRIMARY` | `id` | 详情、回表 |
| `idx_user_deleted_created` | `user_id, is_deleted, created_at` | 我的帖子（全部状态） |
| `idx_user_status_deleted_created` | `user_id, status, is_deleted, created_at` | 我的帖子按状态筛选 |
| `idx_user_status_deleted_published` | `user_id, status, is_deleted, published_at` | 作者主页、大 V 拉模式 |
| `idx_status_deleted_created` | `status, is_deleted, created_at` | 审核队列、管理端列表 |
| `idx_status_deleted_published` | `status, is_deleted, published_at` | 最新公开列表、搜索兜底 |
| `idx_status_deleted_interaction` | `status, is_deleted, last_interaction_at` | 热榜扫描最近 24h 互动 |
| `idx_ai_tag_status` | `ai_tag_status` | AI 打标失败重试 |
| `idx_updated_at` | `updated_at` | ES 增量同步补偿 |

**约束**：

- `CHECK (status IN (0,1,2,3))`；
- `CHECK (is_deleted IN (0,1))`；
- `CHECK (ai_tag_status IN (0,1,2,3))`。

**状态与时间口径**：

```
普通用户发帖 → 待审核(0) ─通过→ 已发布(1) ─下架→ 已下架(3)
                  │                 ↑                  │
                  └─拒绝→ 审核拒绝(2) └──── 恢复 ───────┘
管理员发帖 → 已发布(1)（跳过审核）
```

- 公开可见：`status=1 AND is_deleted=0`；
- `published_at`：首次审核通过时写入；管理员发帖在创建时写入；下架恢复不重置；被拒绝后编辑重提、再次通过时写入；
- `audit_reason/audited_at/audited_by`：只保留最近一次发布态裁决；拒绝 / 下架必填原因，通过 / 恢复清空原因；完整历史留给演进 `t_audit_log`；
- 作者删除：`is_deleted=1`，终态，MVP 不恢复；
- 管理员下架：`status=3` + 审核字段，可由管理员恢复；不会复活作者已删除的帖子。

**生命周期与边界**：

- 逻辑删除；`is_deleted=1` 或 `status!=1` 时公开详情 404、列表过滤；作者本人可在“我的帖子”查看自己的待审 / 拒绝 / 下架帖；
- 计数异步更新（点赞 / 浏览）或同事务更新（收藏 / 评论）；计数更新 SQL 显式 `updated_at = updated_at`，避免触发 ES 增量同步；
- `last_interaction_at` 在审核通过时置为 `published_at`；之后点赞 / 评论更新；
- 已发布帖子在 MVP **不支持编辑**；仅审核拒绝帖可编辑重提（2→0），重提时清空 `audit_*`，修改标题 / 正文 / 图片 / 标签，再进入待审队列；
- 帖子正文上限 20,000 字符；图片最多 9 张。

### 3.4 `t_post_image` —— 帖子图片明细

**用途**：一篇帖子多张图，保持展示顺序；`sort_order=0` 为封面。

| 字段 | 类型 | 空 | 默认 | 说明 |
|---|---|---|---|---|
| `id` | `BIGINT UNSIGNED` | 否 | 自增 | 主键 |
| `post_id` | `BIGINT UNSIGNED` | 否 | — | 帖子 |
| `url` | `VARCHAR(512)` | 否 | — | OSS / 本地 URL |
| `sort_order` | `TINYINT UNSIGNED` | 否 | `0` | 顺序，0 为封面 |
| `created_at` | `DATETIME(3)` | 否 | `CURRENT_TIMESTAMP(3)` | 创建时间 |

**索引**：

| 索引 | 字段 | 用途 |
|---|---|---|
| `PRIMARY` | `id` | 主键 |
| `uk_post_sort` | `post_id, sort_order` | 防重复顺序；按帖子取图 |

**约束**：`CHECK (sort_order BETWEEN 0 AND 8)`。

**生命周期与边界**：

- 不单独逻辑删除，随帖子一起隐藏；
- 编辑重提时在事务内 `DELETE` 旧图后重新插入；
- 封面必须存在：应用层保证至少一张图、`sort_order=0`；
- 未发帖的孤儿图片由 OSS 生命周期规则清理；MySQL 只存 URL。

### 3.5 `t_tag` —— 标签字典

**用途**：标签不能是帖子里的自由文本，否则无法聚合、无法作为 AI 候选集、无法做标签推荐。

| 字段 | 类型 | 空 | 默认 | 说明 |
|---|---|---|---|---|
| `id` | `BIGINT UNSIGNED` | 否 | 自增 | 主键 |
| `name` | `VARCHAR(32)` | 否 | — | 标签名 |
| `created_at` | `DATETIME(3)` | 否 | `CURRENT_TIMESTAMP(3)` | 创建时间 |

**索引**：

| 索引 | 字段 | 用途 |
|---|---|---|
| `PRIMARY` | `id` | 主键 |
| `uk_name` | `name` | 标签唯一 |

**生命周期与边界**：

- 10~100 条，初始化种子数据；
- 不存标签计数；需要时从 `t_post_tag` 聚合；
- AI Prompt 的候选标签集直接读本表，不在代码硬编码。

### 3.6 `t_post_tag` —— 帖子与标签关系

**用途**：多对多关系，并记录标签来源，区分人工、AI、规则降级。

| 字段 | 类型 | 空 | 默认 | 说明 |
|---|---|---|---|---|
| `id` | `BIGINT UNSIGNED` | 否 | 自增 | 主键 |
| `post_id` | `BIGINT UNSIGNED` | 否 | — | 帖子 |
| `tag_id` | `BIGINT UNSIGNED` | 否 | — | 标签 |
| `source` | `TINYINT UNSIGNED` | 否 | `0` | 0=MANUAL，1=AI，2=RULE |
| `prompt_version` | `VARCHAR(32)` | 是 | `NULL` | AI Prompt 版本 |
| `created_at` | `DATETIME(3)` | 否 | `CURRENT_TIMESTAMP(3)` | 创建时间 |

**索引**：

| 索引 | 字段 | 用途 |
|---|---|---|
| `PRIMARY` | `id` | 主键 |
| `uk_post_tag` | `post_id, tag_id` | 防重复标签 |
| `idx_tag_post` | `tag_id, post_id` | 按标签反查帖子 |
| `idx_created_at` | `created_at` | ES 增量同步补偿 |

**约束**：`CHECK (source IN (0,1,2))`。

**来源优先级**：人工 > AI > 规则。

| 写入方 | SQL 策略 |
|---|---|
| 手动标签 | `INSERT ... ON DUPLICATE KEY UPDATE source=0, prompt_version=NULL` |
| AI 标签 | 已存在 `source=0` 时保持人工；已存在 `source=2` 时升级为 1；不存在则插入 1 |
| 规则降级 | `INSERT IGNORE`，不覆盖人工 / AI |

**生命周期与边界**：

- 物理删除；用户编辑标签时先删后插；
- 标签变化（AI 打标完成、手动编辑）要发 `SEARCH_UPSERT`，否则新标签搜不到；
- 每帖 1~5 个标签，应用层限制。

- 情感分析失败：`sentiment=NULL` 表示未分析，不阻塞评论，不反复重试；

### 3.11 `t_seckill_order` —— 秒杀订单与状态机

**用途**：订单完整生命周期；三个唯一键分别兜底订单号、消息重投、一用户一有效单。

| 字段 | 类型 | 空 | 默认 | 说明 |
|---|---|---|---|---|
| `id` | `BIGINT UNSIGNED` | 否 | 自增 | 主键 |
| `order_no` | `VARCHAR(32)` | 否 | — | 订单号，全局唯一 |
| `request_id` | `VARCHAR(64)` | 否 | — | 抢购请求 ID，MQ 幂等 |
| `user_id` | `BIGINT UNSIGNED` | 否 | — | 用户 |
| `activity_id` | `BIGINT UNSIGNED` | 否 | — | 活动 |
| `quantity` | `INT UNSIGNED` | 否 | `1` | 数量；MVP 固定 1 |
| `amount` | `DECIMAL(10,2)` | 否 | — | 订单金额快照 |
| `status` | `TINYINT UNSIGNED` | 否 | `0` | 0=待支付，1=已支付，2=已关闭 |
| `active_flag` | `TINYINT` | 是 | 生成列 | 有效订单=1，已关闭=NULL |
| `pay_trade_no` | `VARCHAR(64)` | 是 | `NULL` | 支付平台交易号 |
| `paid_at` | `DATETIME(3)` | 是 | `NULL` | 支付时间 |
| `closed_at` | `DATETIME(3)` | 是 | `NULL` | 关闭时间 |
| `created_at` | `DATETIME(3)` | 否 | `CURRENT_TIMESTAMP(3)` | 创建时间 |
| `updated_at` | `DATETIME(3)` | 否 | `CURRENT_TIMESTAMP(3)` | 更新时间 |

**生成列**：

```sql
active_flag TINYINT GENERATED ALWAYS AS (
  CASE WHEN status IN (0, 1) THEN 1 ELSE NULL END
) STORED
```

**索引**：

| 索引 | 字段 | 解决的问题 |
|---|---|---|
| `PRIMARY` | `id` | 主键 |
| `uk_order_no` | `order_no` | 订单号全局唯一 |
| `uk_request_id` | `request_id` | 同一 MQ 消息重投不复活已关闭订单 |
| `uk_user_activity_active` | `user_id, activity_id, active_flag` | 一用户同时只能有一张有效订单；已关闭订单不占位 |
| `idx_user_created` | `user_id, created_at` | 我的订单列表 |
| `idx_activity_status` | `activity_id, status` | 活动订单统计 / 对账 |
| `idx_status_created` | `status, created_at` | 超时关单兜底扫描 |

**约束**：

- `CHECK (status IN (0,1,2))`；
- `CHECK (quantity >= 1)`；
- `CHECK (amount >= 0)`。

**状态机**：

```
待支付(0) ──支付回调 CAS──→ 已支付(1)
    │
    └──超时 / 关单 CAS──→ 已关闭(2)
```

- 支付回调：`UPDATE ... SET status=1, pay_trade_no=?, paid_at=NOW() WHERE order_no=? AND status=0`；受影响行数为 0 说明已处理，幂等返回；
- 超时关单：`UPDATE ... SET status=2, closed_at=NOW() WHERE order_no=? AND status=0`；成功后回补 DB / Redis 库存与限购计数；
- 已支付订单不允许关闭；已关闭订单不允许支付；
- `active_flag` 生成列让已关闭订单的 `active_flag=NULL`，MySQL 唯一索引允许多个 NULL，因此用户关单后可用新 `request_id` 重新抢；
- `amount` 是下单时的价格快照，后续活动改价不影响历史订单。

## 6. 事务边界与一致性

### 6.1 发帖（F-05）

**事务内**：

1. 插入 `t_post`（普通用户 `status=0, published_at=NULL`；管理员 `status=1, published_at=NOW(3)`）；
2. 批量插入 `t_post_image`；
3. 批量插入 `t_post_tag`（`source=MANUAL`）。

**事务提交后**：

| 动作 | 条件 | 失败处理 |
|---|---|---|
| 布隆过滤器 `add(postId)` | 总是 | MQ 补偿 / 重建 |
| AI 打标 MQ | 总是（待审阶段也可跑） | 重试 + 规则降级 |
| Feed 写扩散 MQ | 管理员帖（已发布） | best-effort + 告警 |
| `SEARCH_UPSERT` | 管理员帖（已发布） | 5 分钟增量补偿 |
| `SEARCH_DELETE` | 普通用户帖（待审） | 防御性，可不发 |

> 普通用户帖子审核通过后，由 F-10 统一触发 Feed 与搜索事件。

### 6.2 审核 / 下架 / 恢复（F-10 / F-28）

| 动作 | 事务内 SQL | 事务后 |
|---|---|---|
| 通过 0→1 | `UPDATE ... SET status=1, published_at=NOW(3), audited_at=NOW(3), audited_by=?, audit_reason=NULL, last_interaction_at=NOW(3) WHERE id=? AND status=0 AND is_deleted=0` | 删详情缓存；Feed MQ；`SEARCH_UPSERT` |
| 拒绝 0→2 | `UPDATE ... SET status=2, audit_reason=?, audited_at=NOW(3), audited_by=? WHERE id=? AND status=0 AND is_deleted=0` | 删缓存；`SEARCH_DELETE` |
| 下架 1→3 | `UPDATE ... SET status=3, audit_reason=?, audited_at=NOW(3), audited_by=? WHERE id=? AND status=1 AND is_deleted=0` | 删缓存；`SEARCH_DELETE` |
| 恢复 3→1 | `UPDATE ... SET status=1, audited_at=NOW(3), audited_by=?, audit_reason=NULL WHERE id=? AND status=3 AND is_deleted=0` | 删缓存；`SEARCH_UPSERT`；**不重复 Feed 扩散** |

**CAS 条件**防止并发重复审核：受影响行数为 0 时返回“状态已变化”，不重复发事件。

### 6.3 作者删除（F-05 / 我的帖子）

```sql
UPDATE t_post
SET is_deleted = 1
WHERE id = ? AND user_id = ? AND is_deleted = 0;
```

- 终态，MVP 不恢复；
- 事务后删详情缓存、发 `SEARCH_DELETE`；
- 已进入粉丝收件箱的帖子不主动清理，读 Feed 时过滤；
- 管理员不能对已删除帖子做审核 / 下架 / 恢复。

### 6.4 点赞（F-11）

```
Redis Lua（原子）：
  SISMEMBER liked:{postId} userId
    ├─ 已点赞 → 返回重复
    └─ 未点赞 → SADD + INCR count + 发 MQ

MQ 消费者事务：
  INSERT t_like (user_id, post_id)
    ├─ 成功 → UPDATE t_post SET like_count = like_count + 1, updated_at = updated_at WHERE id=?
    └─ 唯一键冲突 → 跳过（重复消息）

取消：
  Redis SREM + DECR + 发 MQ
  消费者 DELETE t_like
    ├─ 删除成功 → UPDATE t_post SET like_count = GREATEST(like_count - 1, 0), updated_at = updated_at
    └─ 未删除 → 跳过
```

- `updated_at = updated_at` 防止计数更新触发 ES 增量同步；
- 对账任务按 `t_like` 统计修正 `t_post.like_count` 与 Redis 计数。

### 6.5 收藏（F-12）

```
事务：
  INSERT t_collect (user_id, post_id)
    ├─ 成功 → UPDATE t_post SET collect_count = collect_count + 1 WHERE id=?
    └─ 唯一键冲突 → 已收藏，幂等返回
提交后：删详情缓存
```

取消同理，受影响行数为 1 才递减。

### 6.6 评论（F-13）

```
事务：
  INSERT t_comment
  UPDATE t_post
    SET comment_count = comment_count + 1,
        last_interaction_at = NOW(3)
    WHERE id = ?
提交后：
  删详情缓存
  发情感分析 MQ（F-24）
```

删除评论：逻辑删除 + `comment_count = GREATEST(comment_count - 1, 0)` + 删缓存；保留子回复占位。

### 6.7 关注（F-04）

```
事务：
  INSERT t_user_follow
    ├─ 唯一键冲突 → 已关注，幂等返回
    └─ 成功 →
        UPDATE t_user SET following_count = following_count + 1 WHERE id = followerId
        UPDATE t_user SET follower_count  = follower_count  + 1 WHERE id = followeeId
提交后：
  更新 Redis 关注 / 粉丝 Set
  回填被关注者最近 50 条已发布帖子到我的收件箱
```

取关：删除关系；受影响行数为 1 才递减双方计数；Redis Set 同步移除。

### 6.8 秒杀下单（F-20 / F-21）

**抢购路径**：

```
Redis Lua 预扣库存 + 限购 + 幂等标记
   │ 成功
   ▼
发送 MQ（携带 requestId、userId、activityId）
   │
   ▼
消费者事务：
  ① UPDATE t_seckill_activity SET stock = stock - 1
     WHERE id = ? AND stock >= 1
     （受影响行数 0 → 告警 + 回补 Redis）
  ② INSERT t_seckill_order (status=0, request_id=?, ...)
     （uk_request_id / uk_user_activity_active 兜底幂等）
  ③ 发送延迟消息（30 分钟后关单检查）
  ④ ACK
```

**支付回调**：

```sql
UPDATE t_seckill_order
SET status = 1, pay_trade_no = ?, paid_at = NOW(3)
WHERE order_no = ? AND status = 0;
```

**超时关单**：

```sql
UPDATE t_seckill_order
SET status = 2, closed_at = NOW(3)
WHERE order_no = ? AND status = 0;
```

成功后：`t_seckill_activity.stock+1`、Redis 库存 +1、限购计数 -1、删除幂等标记。

### 6.9 搜索索引（F-08）

- 业务事务提交后发 MQ；**不在事务内写 ES**；
- 消费者只取 `postId`，回查 MySQL 当前状态，再 `index` / `delete`；
- 事件乱序 / 重复都能收敛，无需版本号；
- 失败重试 + 死信 + 5 分钟增量补偿 + 全量重建；
- 详见附录 A。

### 6.10 事务边界总表

| 操作 | 事务范围 | 提交后动作 | 幂等手段 |
|---|---|---|---|
| 发帖 | `t_post` + `t_post_image` + `t_post_tag` | 布隆、AI MQ、Feed / 搜索事件 | 无（一次请求一个帖子） |
| 审核 | `t_post` CAS | 删缓存、Feed MQ、搜索事件 | CAS `status` |
| 作者删除 | `t_post` CAS `is_deleted=0` | 删缓存、搜索删除 | CAS |
| 点赞 | Redis 先行；DB 消费者事务 | 无 | `uk_user_post` |
| 收藏 | `t_collect` + `t_post.collect_count` | 删缓存 | `uk_user_post` |
| 评论 | `t_comment` + `t_post.comment_count` | 情感 MQ、删缓存 | 无（一次请求一条） |
| 关注 | `t_user_follow` + 双方计数 | Redis Set、回填收件箱 | `uk_follower_followee` |
| 秒杀下单 | 扣库存 + 插订单 | 延迟消息 | `uk_request_id`、`uk_user_activity_active`、库存 CAS |
| 支付回调 | 订单 CAS | 无 | `status=0` CAS |
| 超时关单 | 订单 CAS + 库存回补 | Redis 回补 | `status=0` CAS |
| 搜索同步 | 无 DB 事务 | ES index / delete | 回查 MySQL，天然幂等 |

## 7. 容量估算与演进

### 7.1 数据量估算

| 表 | 行数 | 单行估算 | 数据量 | 索引估算 |
|---|---:|---:|---:|---:|
| `t_user` | 10 万 | ~200 B | ~20 MB | ~10 MB |
| `t_user_follow` | 1,000 万 | ~40 B | ~400 MB | ~800 MB |
| `t_post` | 1,000 万 | ~1 KB（含正文） | ~10 GB | ~6 GB |
| `t_post_image` | 3,000 万 | ~150 B | ~4.5 GB | ~2 GB |
| `t_tag` | 100 | — | 忽略 | 忽略 |
| `t_post_tag` | 3,000 万 | ~40 B | ~1.2 GB | ~2 GB |
| `t_like` | 1 亿 | ~40 B | ~4 GB | ~8 GB |
| `t_collect` | 1,000 万 | ~40 B | ~400 MB | ~800 MB |
| `t_comment` | 3,650 万 | ~300 B | ~11 GB | ~6 GB |
| `t_seckill_activity` | 1 万 | ~500 B | ~5 MB | 忽略 |
| `t_seckill_order` | 100 万 | ~300 B | ~300 MB | ~500 MB |

**合计约 35~45 GB**（含索引），单机 MySQL +  SSD 可承载；ES 索引约 10~20 GB。

### 7.2 演进项

| 触发条件 | 演进方案 |
|---|---|
| `t_like` > 1 亿或查询变慢 | 按 `user_id` HASH 分区，或按 `created_at` 归档冷数据 |
| `t_comment` 历史数据过大 | 按 `created_at` 归档；热数据保留在 MySQL |
| 单表 > 1000 万且写入瓶颈 | 评估分库分表（优先按 `user_id` 分片） |
| ES 数据量增长 | 增加分片 / 副本；冷热分层；ILM |
| Feed 完整性要求提高 | 引入 Outbox / 本地消息表 |
| 需要完整审核历史 | 新增 `t_audit_log` |
| F-26 智能推荐 | 复用 ES 向量检索，或引入向量数据库 |
| 帖子支持已发布编辑 | 增加内容版本表 / 审计表，搜索事件改为 `SEARCH_UPSERT` |
| 多图 / 视频 | 扩展 `t_post_image` 类型字段，或新增媒体表 |

### 7.3 索引维护注意

- `t_post` 有 8 个二级索引，写入放大会高于普通表；计数更新避免触发 `updated_at`；
- 新增索引必须用 `EXPLAIN` 验证覆盖目标查询，禁止“先加再说”；
- 大表加索引使用 `ALGORITHM=INPLACE, LOCK=NONE`（MySQL 8 多数场景支持），并在低峰执行；
- 定期用 `sys.schema_unused_indexes` / `performance_schema` 检查未使用索引。

## 9. 附录 A：Elasticsearch 索引设计

> 与 02 §6.12 一致；本节给出可直接执行的 mapping 与同步约定。

### A.1 索引与别名

| 项 | 值 |
|---|---|
| 别名 | `glimmer_post` |
| 物理索引 | `glimmer_post_v1`（重建时 `v2`） |
| 分片 / 副本 | MVP 单节点：1 / 0；生产可调 1 / 1 |
| 刷新间隔 | `1s` |
| 只索引 | `status=1 AND is_deleted=0` |

### A.2 Mapping

```json
PUT /glimmer_post_v1
{
  "settings": {
    "number_of_shards": 1,
    "number_of_replicas": 0,
    "refresh_interval": "1s",
    "analysis": {
      "analyzer": {
        "post_index":  { "tokenizer": "ik_max_word", "filter": ["lowercase"] },
        "post_search": { "tokenizer": "ik_smart",    "filter": ["lowercase"] }
      }
    }
  },
  "mappings": {
    "properties": {
      "postId":      { "type": "long" },
      "userId":      { "type": "long" },
      "title":       { "type": "text", "analyzer": "post_index", "search_analyzer": "post_search",
                       "fields": { "keyword": { "type": "keyword", "ignore_above": 256 } } },
      "content":     { "type": "text", "analyzer": "post_index", "search_analyzer": "post_search" },
      "tagIds":      { "type": "long" },
      "tagNames":    { "type": "keyword",
                       "fields": { "text": { "type": "text", "analyzer": "post_index", "search_analyzer": "post_search" } } },
      "publishedAt": { "type": "date", "format": "epoch_millis" },
      "status":      { "type": "byte" },
      "updatedAt":   { "type": "date", "format": "epoch_millis" }
    }
  }
}
```

**不写入 ES**：`likeCount`、`commentCount`、`collectCount`、`viewCount`、`coverUrl`、`authorNickname`、`authorAvatar`。命中后回表 / Redis 批量补全。

### A.3 查询 DSL

```json
GET /glimmer_post/_search
{
  "query": {
    "bool": {
      "must": [
        {
          "multi_match": {
            "query": "露营装备",
            "fields": ["title^3", "tagNames.text^2", "content"],
            "type": "best_fields"
          }
        }
      ],
      "filter": [
        { "term": { "status": 1 } },
        { "terms": { "tagIds": [12, 18] } }
      ]
    }
  },
  "highlight": {
    "fields": {
      "title": {},
      "content": { "fragment_size": 80, "number_of_fragments": 1 }
    }
  },
  "sort": [
    { "_score": "desc" },
    { "publishedAt": "desc" },
    { "postId": "desc" }
  ],
  "from": 0,
  "size": 20
}
```

- `keyword` 为空时不走 ES，直接返回热榜 / 最新列表；
- `from + size <= 200`；更深分页用 `search_after`，游标 `[_score, publishedAt, postId]`。

### A.4 同步事件

| 事件 | 触发 | 消费者 |
|---|---|---|
| `SEARCH_UPSERT` | 管理员发帖、审核通过、恢复、标签变化、编辑重提后通过 | 回查 MySQL；可公开则 `index`，否则 `delete` |
| `SEARCH_DELETE` | 审核拒绝、下架、作者删除 | 回查 MySQL；`delete` |

**事件字段**：`eventId`、`postId`、`type`、`occurredAt`。消费者**不信任**事件里的标题 / 正文，只使用 `postId`。

### A.5 重建流程

```
1. 创建 glimmer_post_v2，写入最新 mapping
2. 记录 rebuild_started_at
3. scroll 查询 MySQL：
   SELECT id FROM t_post
   WHERE status=1 AND is_deleted=0
   ORDER BY id
4. 批量 bulk index 到 v2（每批 500~1000）
5. 追平：扫描 updated_at >= rebuild_started_at 的帖子，补写 v2
6. 校验文档数：v2 count vs MySQL count
7. 原子切换别名 glimmer_post → v2
8. 保留 v1 一个版本，确认无误后删除
```

- 重建期间线上仍读写 v1；
- 不要直接删除旧索引再建同名索引；
- 重建失败的索引保留现场，便于排查。

### A.6 失败与降级

| 情况 | 处理 |
|---|---|
| MQ 发送失败 | 记录指标并告警；5 分钟增量补偿 |
| 消费失败 | 有限重试 + 死信队列 + 告警 |
| ES 写入失败 | 重试；仍失败进入死信 |
| ES 查询超时 / 不可用 | 搜索降级返回热榜 / 最新；`degraded=true` |
| 索引与 MySQL 不一致 | 增量补偿；严重时全量重建 |
