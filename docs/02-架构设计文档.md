## 1. 文档说明

### 1.1 目的

承接 PRD，回答 **「怎么做」**：确定架构风格、技术选型、模块边界、数据存储职责，并给出关键业务难点（秒杀、Feed、缓存、幂等）的落地方案，作为详细设计与编码的依据。

### 1.2 范围

- **覆盖**：设计目标与容量假设、总体架构与模块划分、技术选型论证、存储职责划分、关键技术方案、非功能设计、部署形态、微服务演进路径。
- **不覆盖**：表结构与字段（见 03）、接口路径与出入参（见 04）、具体代码实现。

### 1.3 术语

沿用 PRD 1.3 术语表。本文档新增：

| 术语 | 说明 |
|---|---|
| 模块化单体 | 单进程部署，但代码按业务模块严格分包、边界清晰的架构风格 |
| Cache Aside | 缓存旁路模式：读时回填、写时删缓存 |

| 容量假设 | 为设计决策提供依据的预估业务规模 |

## 2. 设计目标与容量假设

### 2.1 设计目标

由 PRD 第 7 章推导，作为架构方案的**验收标准**：

| 编号 | 目标 | 量化指标 | 来源 |
|---|---|---|---|
| G-1 | Feed 读性能 | P95 < 200 ms | PRD 7.1 |
| G-2 | 秒杀吞吐 | QPS ≥ 1000（压测验证） | PRD 7.1 |
| G-3 | 弹幕实时性 | 端到端延迟 < 200 ms | PRD 7.1 |
| G-4 | 秒杀正确性 | 零超卖、零重复下单 | PRD 6.2 |
| G-5 | 幂等性 | 关键操作重复执行结果一致 | PRD 6.7 |
| G-6 | 可拆分性 | 模块边界清晰，可低成本拆为微服务 | PRD 7.5 |
| G-7 | 可演示性 | 单机 Docker Compose 一键启动 | 本文档补充 |
| G-8 | AI 流式体验 | 首 Token 延迟（TTFT）< 2s，整段 < 15s | PRD 7.1（v1.1） |
| G-9 | 搜索性能 | P95 < 300ms（ES 正常时） | PRD 7.1（v1.3） |

> **G-7 是个人项目特有目标**，但优先级不低：一个跑不起来的项目没有任何展示价值。凡是为达成 G-1~G-6 而引入的重量级依赖，都必须先通过 G-7 的检验。

### 2.2 容量假设

> ⚠️ PRD 未定义业务体量。**没有容量假设，架构设计只能靠猜**——例如布隆过滤器需要多大内存、Feed 阈值定多少，都取决于此。以下假设用于驱动设计决策，不代表真实运营目标。

| 指标 | 假设值 | 依据 / 用途 |
|---|---|---|
| 注册用户 | 10 万 | 个人项目演示体量 |
| DAU | 1 万 | 10% 日活率 |
| 帖子总量 | **1000 万** | **6.2 布隆过滤器容量依据** |
| 日新增帖子 | 1 万 | 写扩散压力评估 |
| 日新增评论 | 10 万 | 异步分析队列积压评估 |
| 点赞总量 | 1 亿 | 计数结构选型依据 |
| 人均关注 / 人均粉丝 | 100 / 100 | 6.5 Feed 推拉阈值依据 |
| 头部账号 | 约 100 个，粉丝 > 1 万 | 用于验证拉模式分支 |
| 秒杀单品库存 | 1000 件 | 防超卖验证场景 |
| 秒杀瞬时并发 | 5000 | 压测放大场景 |
| 预估真实峰值 QPS | ~500 | 日常容量规划 |
| 压测目标 QPS | **≥ 1000** | G-2 验收指标 |
| 单张图片 | ≤ 5 MB | 上传限制依据 |
| AI 流式峰值并发会话 | ~50（在线会话；同时生成流按 20 设计） | **6.11 线程池与限流依据** |

**两条重要推论**：

1. **1000 万帖子 → 布隆过滤器约 12 MB**（见 6.2.2），单 Redis Key 可承载，**不需要分片**。
2. **人均粉丝仅 100 → 绝大多数用户的发帖走写扩散成本极低**，Feed 的推拉结合主要是为头部账号设计的保护机制。

### 2.3 设计原则

| 原则 | 含义 | 反例（本项目的红线） |
|---|---|---|
| **MVP 优先** | P2 功能只留扩展点，不实现 | 不为"数据看板"提前设计 OLAP |
| **不过度设计** | 引入的每个中间件都必须有明确的、当下就要解决的问题 | 不在单体阶段引入 Nacos / Gateway |
| **边界先行** | 模块边界在编码前定死；跨模块可调对方 Service 接口，Mapper 保持私有 | 禁止 A 模块直接注入 B 模块的 Mapper，禁止直接写 B 表 |
| **正确性优先于性能** | 秒杀先保证不超卖，再谈 QPS | 不做"为了压测数字好看"而牺牲一致性 |
| **失败可降级** | 每个外部依赖（LLM / OSS / Redis）都要有降级路径 | 不允许 LLM 超时导致发帖失败 |
| **可演示** | 单机可启动，离线可开发 | 不允许本地开发强依赖公网 OSS |

## 3. 总体架构

### 3.1 架构风格选择

**决策：模块化单体（Modular Monolith）**

#### 3.1.1 备选方案对比

| 方案 | 优点 | 缺点 | 结论 |
|---|---|---|---|
| 传统分层单体 | 上手最快 | 按技术分层分包，业务边界模糊，后期拆分成本极高 | ❌ |
| **模块化单体** | 单进程/单库/单部署，无分布式复杂度；按业务垂直分包，边界清晰，可低成本拆分 | 仍需自律维持模块边界 | ✅ **采用** |
| 一步到位微服务 | 技术栈最亮眼 | 单人项目引入 Nacos/Gateway/Seata/分布式事务/链路追踪，调试成本爆炸，MVP 无法交付 | ❌ 阶段 7 再做 |

#### 3.1.2 决策理由

1. **PRD 8 明确 MVP 为单体**，阶段 7 才演进为微服务；
2. 单人开发场景下，分布式带来的一致性、调试、部署成本是**纯负担**，没有团队规模收益；
3. 但 PRD 5 的 7 个模块划分和 PRD 7.5 的"预留拆分边界"要求边界必须**在代码结构上真实存在**，而不是写在文档里；
4. 模块化单体是唯一同时满足"当下简单"与"未来可拆"的方案。

#### 3.1.3 边界的强制手段

边界不能只靠自觉，用以下手段强制：

- **包结构物理隔离**：每个模块一个顶层包（见 3.4）；
- **Service 是模块的公开 API**：允许跨模块注入对方的 Service 接口（如 interaction 注入 `ContentService`），**不强制单独建 `XxxFacade` 类**；Facade 只是对外 Service 的一种命名，不是额外一层；
- **Mapper 私有**：禁止跨模块注入 Mapper，禁止直接 UPDATE / INSERT 对方的表；写操作只能调用拥有方 Service 的写方法；
- **依赖单向**：模块间依赖必须无环（见 3.5）；`content` 不反向依赖 `interaction` / `ai`，详情计数由 content 读自己的计数列或 Redis 计数 Key；
- **ArchUnit 门禁（骨架阶段加入）**：
  - 禁止 content 包外的类访问 `..content.mapper..`（其他模块同理）；
  - 模块间依赖无环；
- **人工评审**：Code Review 时把“跨模块注入 Mapper / 直接写对方表 / 反向依赖”视为阻塞问题。

### 3.2 分层架构

```
┌─────────────────────────────────────────────────────┐
│  接入层  Controller                                  │
│  · 参数校验（Jakarta Validation）                    │
│  · 统一响应封装 / 全局异常处理                        │
│  · 鉴权：全局拦截器（默认登录 + 白名单 + ADMIN 前缀）  │
├─────────────────────────────────────────────────────┤
│  应用层  Service（用例编排）                          │
│  · 事务边界在这里                                     │
│  · 编排：领域逻辑 + 缓存 + MQ + 外部调用               │
├─────────────────────────────────────────────────────┤
│  领域层  Domain（业务规则）                           │
│  · 实体 / 值对象 / 领域服务 / 领域事件                 │
│  · 纯业务逻辑，不依赖框架（可单测）                     │
├─────────────────────────────────────────────────────┤
│  基础设施层  Infrastructure                           │
│  · Mapper（MySQL） / RedisRepo / MqProducer           │
│  · OSS Client / LLM Client / WebSocket Session 管理   │
└─────────────────────────────────────────────────────┘
```

> 说明：本项目不做完整 DDD（不设聚合根/仓储/限界上下文的严格划分），只借用其**分层隔离**思想。领域层保持轻量，避免教科书式的过度设计。

**Service 代码约定**：

- 业务 Service 统一采用「接口 + 实现」：接口放 `service/`，实现放 `service/impl/`，接口是模块对外的事实 Facade；
- 接口名直接使用 `AuthService`、`ContentService`，**不加 `I` 前缀**；实现名加 `Impl` 后缀；
- Controller、其他模块只注入接口，不注入实现类；
- 单实现的技术组件（`JwtService`、`TokenStore`、`RateLimiter`）不属于模块业务 API，保持具体类，避免为形式而抽象。

**读写路径的分布**：
- 读多写少（帖子详情、Feed、热榜）→ **Redis 承担主流量**，MySQL 兜底；
- 写少但需可靠（订单、点赞）→ **MQ 异步落库**，MySQL 保证最终一致；
- 外部重依赖（LLM、OSS）→ **全部异步化或降级**，绝不阻塞主链路。

### 3.4 模块划分与职责

| 模块 | 职责 | 对应 PRD | 关键依赖 |
|---|---|---|---|
| **user** | 注册登录、JWT、验证码、用户信息、关注关系 | F-01~F-04 | Redis（验证码/Token/关注 Set） |
| **content** | 帖子 CRUD、图片上传、标签、审核、搜索 | F-05~F-10 | MySQL、Redis、OSS、MQ、Elasticsearch |
| **interaction** | 点赞、收藏、评论、弹幕消息、通知预留 | F-11~F-15 | Redis、MQ、WebSocket |
| **feed** | 关注流、推荐流、热榜 | F-16~F-18 | Redis ZSet、MQ |
| **seckill** | 活动管理、抢购、订单、超时关单 | F-19~F-22、F-29 | Redis Lua、RabbitMQ |
| **ai** | 自动打标签、情感分析、**帖子 AI 助手（流式对话）**、摘要预留 | F-23~F-26、**F-31** | DeepSeek API、MQ（异步）、**SSE（流式）** |
| **admin** | 内容审核、用户管理、数据看板预留 | F-10、F-27、F-28、F-30 | 各模块 Facade |

> **模块 = 微服务拆分候选单元**。模块内高内聚，模块间低耦合，阶段 7 拆分时按此边界直接抽取。

### 3.5 模块依赖规则

**允许的依赖方向（无环）**：

```
                    ┌──────────┐
                    │  admin   │  ← 依赖所有模块的 Facade（只读为主）
                    └────┬─────┘
                         │
   ┌─────────┐     ┌─────▼──────┐     ┌──────────┐
   │  feed   │────►│  content   │◄────│interaction│
   └────┬────┘     └─────┬──────┘     └─────┬────┘
        │                │                  │
        │                ▼                  │
        │           ┌─────────┐             │
        │           │   ai    │             │
        │           └─────────┘             │
        │                                   │
   ┌────▼───────────────────────────────────▼────┐
   │                  user                        │
   └──────────────────────────────────────────────┘
   ┌──────────┐
   │ seckill  │  ← 只依赖 user（校验用户），与其他模块解耦
   └──────────┘
```

**规则**：

1. `content`、`user` 是**被依赖方**，不反向依赖 `feed` / `interaction`；
2. `feed` 依赖 `content`（取帖子）与 `user`（取关注关系）；
3. `seckill` **刻意与其他业务模块解耦**（秒杀商品不绑定帖子），便于独立拆分与压测隔离；
4. `admin` 是聚合方，只调各模块 Service，不直接操作他模块的 Mapper；
5. **跨模块同步调用只走对方 Service 接口**；不强制单独建 Facade 类，但 Service 接口就是事实上的 Facade；
6. **Mapper 永远私有**：A 可以调 B 的 Service，但不能注入 B 的 Mapper，也不能直接写 B 的表；
7. **写入口唯一**：每张表 / 每个计数列只有一个拥有方 Service 可写。`t_post.like_count` / `comment_count` / `last_interaction_at` 由 content 的 Service 统一更新，interaction 只负责 `t_like` / `t_comment`；`t_post_tag` 由 content 统一写入，ai 只提交标签结果；
8. **事务与缓存**：跨模块 Service 调用默认加入调用方的本地事务；拥有方 Service 不得用 `REQUIRES_NEW` 拆事务；外部 IO（OSS / LLM）不得放在事务内；写 `t_post` 的 Service 方法负责失效 `content:post:{id}`，调用方不直接删 content 的缓存。

**允许 / 禁止示例**：

| 场景 | 判定 |
|---|---|
| interaction 点赞消费者调用 `contentService.onLikeChanged(postId, delta)` | ✅ 允许 |
| ai 打标消费者调用 `contentService.replaceAiTags(postId, tagIds)` | ✅ 允许 |
| 评论 Service 调用 `contentService.onCommentCreated(postId, interactedAt)` | ✅ 允许 |
| interaction 注入 `PostMapper` 直接 `UPDATE t_post` | ❌ 禁止 |
| ai 注入 `PostTagMapper` 直接 `INSERT t_post_tag` | ❌ 禁止 |
| content 注入 `LikeService` 反向查点赞数（content → interaction） | ❌ 禁止（成环） |

## 4. 技术选型

### 4.1 选型总表

> 本章确定主要技术选型；支付与登录方式仍见 PRD 第 9 节。

### 4.2 关键选型论证

#### 4.2.1 Spring Boot 3 + Java 17

**理由**：Spring Boot 3 要求 Java 17+，是当前主流 LTS 组合；虚拟线程（Java 21）暂不引入——本项目瓶颈在 Redis 与 MQ，不在线程模型，引之为时过早。

#### 4.2.2 MyBatis-Plus

| 方案 | 取舍 |
|---|---|
| **MyBatis-Plus** ✅ | 单表 CRUD 零 SQL；复杂查询（Feed 归并、热榜聚合）仍可写原生 SQL；学习曲线平缓 |
| JPA / Hibernate | 复杂查询表达力弱，字段映射黑盒，不贴合互联网场景 |
| 纯 MyBatis | SQL 全手写，开发效率低，单表 CRUD 冗余 |

**分页实现（ADR-018）**

- **管理端列表**（审核、用户、活动、订单）使用 **PageHelper**：`PageHelper.startPage(page, size)` → `PageInfo<T>` → 映射为 `PageResult<T>`；总数由 PageHelper 自动 count。
- **用户端信息流**（Feed、搜索、评论、收藏）保持**游标分页**，手写 `WHERE (sort_key, id) < (?, ?)` + `LIMIT`，不经过 PageHelper。
- **不注册 MyBatis-Plus 的 `PaginationInnerInterceptor`**，避免两个分页拦截器同时改写 SQL；管理端查询使用 `selectList` + PageHelper，不使用 MP 的 `selectPage`。
- PageHelper 配置 `reasonable=false`、`pageSizeZero=false`，由 DTO 校验 `page >= 1`、`1 <= size <= 100`；`startPage` 后必须紧跟目标查询，中间不能插入其他 MyBatis 查询（ThreadLocal 只绑定下一次查询）。
- 依赖 `pagehelper-spring-boot-starter 2.1.x`（Spring Boot 3 / JDK 17 基线）；骨架阶段锁定实际版本并补一次分页集成测试。

#### 4.2.3 Redis + Redisson

**引入 Redisson 的理由**（而非仅用 Spring Data Redis / Lettuce）：

1. **分布式锁**：详情缓存重建、热榜重算、搜索补偿等任务的防重入 —— 自研 Redis 锁的续期、重入、锁误删是经典坑；**秒杀热路径不使用锁**（见 6.7）；
2. **布隆过滤器**：`RBloomFilter` 开箱即用且**分布式一致**，直接命中 6.2 的核心需求；
3. **延迟队列 / 限流器**：为 6.7 与 6.10 提供备选实现。

> 原则：**能用成熟组件解决的问题，不自己造**。自研分布式锁是面试扣分项，不是加分项。

#### 4.2.4 消息队列：RabbitMQ（PRD 第 9 节决策）

**选择理由**：

- 课程已学过，掌握度高，出问题能自己排查；
- 管理控制台（15672）直观，**演示时可直接展示消息堆积与消费过程**；
- Docker 部署轻量（单容器），符合 G-7；
- 本项目峰值量级（压测 QPS 1000）远未触及 RabbitMQ 的吞吐上限。

**必须应对的三个短板**（面试必问，务必掌握）：

| 短板 | 影响 | 本项目的应对方案 | 落点 |
|---|---|---|---|
| **无事务消息** | "DB 写成功 + 消息发送成功"无法原子保证，可能丢消息 | MVP：`publisher confirm` + 发送失败则回滚 Redis 库存并返回失败<br>演进：**本地消息表（Outbox）** + 定时补偿投递 | 6.7.5 |
| **延迟消息需插件** | 原生不支持任意延迟，超时关单无法直接实现 | 采用 `rabbitmq_delayed_message_exchange` 插件（方案 A）<br>降级：TTL + 死信队列（DLX）（方案 B） | 6.7.4 |
| **吞吐低于 RocketMQ** | 极端堆积时消费慢 | 当前量级不构成问题；消费端可水平扩容（增加 consumer） | 7.1 |

**被否决的方案**：

- *RocketMQ*：技术指标更优、国内大厂主流，但学习成本更高、部署需 NameServer + Broker 两组件；**本项目没有需要 RocketMQ 才能解决的场景**（事务消息用 Outbox 替代、延迟消息用插件替代）。若未来演进为微服务、量级上升，可再迁移。
- *Kafka*：面向流处理与日志，不适合业务消息 + 延迟消息场景。

#### 4.2.5 图片存储：阿里云 OSS（PRD 第 9 节决策）

**选择理由**：贴近真实生产环境；支持 CDN 加速与图片处理（缩略图、水印）；简历表述更有分量（"云存储集成 + 服务端签名直传"）。

**上传方案**：

| 方案 | 描述 | 取舍 |
|---|---|---|
| **服务端签名 + 前端直传** ✅ | 后端 `/upload/policy` 返回 STS 签名，前端直传 OSS，仅把 URL 回传后端 | 图片流量不经过应用服务器，**生产标准做法** |
| 后端中转上传 | 图片经应用服务器转发 OSS | 实现简单、服务端可做完整校验；但占用应用带宽与内存 |

**MVP 采用服务端签名直传**，并在后端保留二次校验（P1-17）：

- 签名 Policy 限定 `key` 前缀 `posts/{userId}/{uuid}.{ext}`、`content-length-range`（0–5 MB）、`Content-Type` 白名单（jpg/png/webp）；
- 发帖 / 编辑时后端校验回传 URL 的 host、bucket、prefix 是否属于配置；必要时对 OSS 发 `HEAD` 校验 `Content-Length` / `Content-Type`，拒绝任意外链；
- `LocalStorageServiceImpl` 返回 `${glimmer.storage.public-base-url}/uploads/...`，开发期该 base URL 指向 `http://192.168.157.129:8080` 或宿主机后端地址；
- CORS 按 profile 配置允许的前端 Origin，只放行 `Authorization` / `Content-Type`，`allowCredentials=false`（Bearer Token）。

> ⚠️ **代价与应对**：OSS 是公网外部依赖，会导致**离线开发与单元测试不可用**。因此：
> - 定义 `StorageService` 接口，提供 `OssStorageServiceImpl`（生产/演示）与 `LocalStorageServiceImpl`（本地开发/单测）两个实现，通过 profile 切换；
> - 这样既满足"集成 OSS"的展示目标，又保住 G-7（可演示）与可测试性。

#### 4.2.6 AI 供应商：DeepSeek API（PRD 第 9 节决策）

**选择理由**：

- **账号与 Key 已就绪**（当前已在用同一供应商），零接入成本与额外注册流程；
- 接口 OpenAI 兼容，可用通用 HTTP 客户端调用，无供应商锁定；
- 中文效果良好，价格低，适合异步批量调用；
- 支持 JSON 输出模式，便于结构化解析标签。

**接入方式**：`AiClient` 接口 + `DeepSeekAiClient` 实现，**不引入重型 AI 框架**。

| 方案 | 取舍 |
|---|---|
| **自建 `AiClient` + HTTP 客户端** ✅ | 轻量可控，便于实现超时/重试/降级/限流；无框架版本风险 |
| Spring AI / LangChain4j | 抽象完善，但额外依赖重、版本迭代快，本项目仅需 2 个 Prompt 场景，收益不抵成本 |
| 本地 Ollama | 离线可用，但模型能力弱，演示效果差（已在选型阶段否决） |

**工程要点**（详见 6.9）：超时 5s、失败重试 1 次、**失败降级为规则匹配**、输入截断控制成本、Key 走环境变量。

#### 4.2.7 JWT 认证

**方案**：`jjwt` 生成 HS256 Token，Payload 携带 `userId` / `role` / `iat` / `exp`；**同时在 Redis 存一份 Token**（`glimmer:user:token:{userId}`），支持登出与强制下线。

| 方案 | 取舍 |
|---|---|
| **JWT + Redis 白名单** ✅ | 无状态校验为主，Redis 用于主动失效；兼顾性能与可控性 |
| 纯 JWT（无 Redis） | 无法登出/踢人，安全性与演示效果差 |
| Session | 与"预留微服务拆分"冲突（跨服务共享 Session 麻烦） |

#### 4.2.8 流式推送：SSE（而非复用 WebSocket）

**背景**：PRD F-31 要求将模型生成的内容逐片段推送给客户端。

| 维度 | **SSE** ✅ | WebSocket | 分块响应（chunked） |
|---|---|---|---|
| 通信方向 | 服务器 → 客户端（单向） | 双向 | 单向 |
| 本场景需要 | **单向即足够**（一次请求 → 一段流式回复） | 双向能力用不上 | 单向 |
| 协议 | 纯 HTTP，复用现有端口 | 需 Upgrade 握手 | 纯 HTTP |
| 鉴权 | **复用现有 HTTP 拦截器与 JWT**（4.2.7） | 需在握手阶段单独实现 | 复用 |
| 代理/网关兼容 | 好（仅需关缓冲） | 需额外配置 Upgrade | 需关缓冲 |
| 事件分帧 | **协议自带**（`event:` / `data:`） | 需自定义消息格式 | 需自定义分隔符 |
| 调试 | `curl` 即可观察流式效果 | 需专用客户端 | 可 curl |
| 项目现状 | 未使用 | 弹幕已用（F-14） | — |

**决策**：**AI 问答走 SSE，弹幕继续走 WebSocket。两者不是二选一，而是各取所长。**

**可复用的判据**：

```
是「持续的、双向的频道」？        → WebSocket（弹幕：用户持续发、服务端持续广播）
是「一次请求对应一段流式响应」？  → SSE（AI 问答：发一句、流式回一段）
```

**为什么 AI 问答不复用 WebSocket**：

1. 双向能力用不上，却要承担心跳、重连、消息分帧、连接状态管理的全部复杂度；
2. WebSocket 无法直接走 HTTP 拦截器，**要单独实现一套鉴权**，与 4.2.7 的设计割裂；
3. 演示时 SSE 可直接用 `curl` 展示流式效果。

> ⚠️ **SSE 的消费方式**：虽然响应格式是 SSE，但本项目**不用浏览器原生 `EventSource`**，改用 `POST` + `fetch` 读取流。原因见 6.11.2——EventSource 的自动重连在生成式场景下会导致**重复生成、重复计费**。

#### 4.2.9 MySQL 8.0（ADR-016）

**决策**：使用 MySQL 8.0；不降级到 5.7。

**理由**：

| 理由 | 说明 |
|---|---|
| **默认 utf8mb4** | 社区内容包含中文与 emoji；5.7 服务端默认 `latin1`，需显式配置，容易遗漏 |
| **CHECK 约束生效** | 8.0.16+ 才真正强制执行；5.7 解析后忽略 |
| **窗口函数 / CTE** | 后台数据看板（F-30）与复杂聚合查询更易表达 |
| **`FOR UPDATE SKIP LOCKED`** | 为后续 Outbox / 任务队列 / 对账扫描预留能力 |
| **原子 DDL / Instant DDL** | 开发期改表更安全、更快 |
| **维护周期** | MySQL 5.7 已于 2023-10 EOL，不再有安全补丁；8.x 是当前主线 |
| **生态匹配** | Spring Boot 3 + `mysql-connector-j` 8.x 原生支持 8.0 认证方式 |

**说明**：本项目的 11 张表在 5.7 上也能运行（生成列 5.7+ 支持；搜索已由 ES 承担，不依赖 MySQL 全文索引），因此不是「非 8 不可」，而是**没有理由为新项目选择一个已停止维护的版本**。只有在学校/公司环境强制要求 5.7 时才降级，并需显式配置 `utf8mb4`、避免 CTE/窗口函数/`SKIP LOCKED`、不依赖 `CHECK` 约束。

**认证方式差异（必须注意）**：

| | MySQL 5.7 | MySQL 8.0 |
|---|---|---|
| 默认插件 | `mysql_native_password` | `caching_sha2_password` |
| 哈希 | SHA-1 | SHA-256 + 盐 |
| 老客户端 | 兼容 | 旧驱动/旧 Navicat 可能报错 |

- 8.0 首次在非 TLS 连接上认证需要 RSA 公钥交换；本地 JDBC 需加 `allowPublicKeyRetrieval=true&sslMode=DISABLED`，生产环境应启用 TLS。
- 驱动使用 Spring Boot 管理的 `com.mysql:mysql-connector-j` 8.x，不要使用旧的 `mysql:mysql-connector-java:5.1.x`。
- `mysql_native_password` 在 8.0.34 起废弃、8.4 默认禁用、9.0 移除，**不要作为正式方案依赖**。
- Docker 的 `MYSQL_USER` / `MYSQL_PASSWORD` 仅在数据卷首次初始化时生效；已有 volume 时改环境变量不会改密码。

#### 4.2.10 Elasticsearch 8 + IK（ADR-017）

**决策**：MVP 直接引入 Elasticsearch 承担 F-08 关键词搜索；MySQL 不建全文索引。

**理由**：

| 理由 | 说明 |
|---|---|
| 中文检索质量 | IK 分词 + BM25 相关度，明显优于 MySQL ngram 全文索引 |
| 检索与过滤组合 | 标题 / 正文 / 标签多字段召回，`term` 过滤标签，支持高亮与 `search_after` |
| 职责清晰 | MySQL 是真相源；ES 只存检索字段，展示字段回表补全，避免计数高频写 ES |
| 演进复用 | 后续 F-26 智能推荐可复用同一集群做向量检索 |
| 代价可控 | 单节点 + 512MB heap 即可支撑 MVP；Docker Compose 一键启动 |

**取舍**：

- 多一个 ES 容器、IK 插件与索引重建流程；
- 引入 MySQL → ES 的最终一致窗口（正常秒级、补偿分钟级）；
- ES 故障时搜索降级，不影响发帖、Feed、秒杀等主链路。

**不选 MySQL FULLTEXT ngram**：中文分词与相关度弱，全文索引无法与「状态 + 删除标记」组合成理想索引，后续仍要迁移 ES。
**不选「标签 + 标题前缀」**：正文搜不到，中文前缀匹配体验差，达不到 F-08 目标。
**暂不选 Canal 订阅 binlog**：MVP 用「业务 MQ + 定时补偿 + 全量重建」已足够，避免再引入一个中间件；量级增长后再评估。

**Kibana（开发辅助，ADR-020）**

- 仅用于本地开发 / 演示：Dev Tools 调试查询 DSL、Index Management 查看 mapping / 别名、Discover 检查文档、`_analyze` 验证 IK 分词；
- **不参与业务运行时**，后端不依赖；Docker Compose 使用 `profiles: ["tools"]`，默认不启动；
- 版本必须与 ES 完全一致；只绑定 `127.0.0.1:5601`，不暴露公网；
- 代价：多一个容器约 300–500MB 内存；CI 和自动化脚本仍用 `curl` / `_cat`。

|---|---|---|
| Canal | ES 同步 MVP 用 MQ + 定时补偿，不引入 binlog 订阅 | 搜索一致性要求提高 / 数据量增长后 |

## 5. 数据存储设计总览

> 本节仅定义**职责划分与设计规范**，具体表结构见 03-数据库设计文档。

### 5.1 存储职责划分

| 存储 | 角色 | 承载数据 | 一致性定位 |
|---|---|---|---|
| **MySQL 8** | 真相源（Source of Truth） | 用户、关注关系、帖子、标签、评论、点赞记录、秒杀活动、订单 | **最终权威**，Redis / ES 数据可从中重建 |
| **Elasticsearch 8** | 搜索派生索引 | 公开可见帖子的标题、正文、标签、发布时间 | **最终一致**，可全量重建；ES 故障不影响主链路 |
| **Redis Core** | 协调层 + 不可丢的短状态 | 分布式锁、Token 白名单、秒杀库存 / 资格 / 活动缓存、`idem`、布隆过滤器 | **不淘汰**（`noeviction` + AOF everysec）；仍以 DB 唯一键 / CAS 为最终防线 |
| **Redis Cache** | 纯性能层 | 帖子详情、空值缓存、Feed 收件箱 / 热榜、点赞 Set / 计数、关注 Set、AI 会话、验证码 / 限流、弹幕历史 | **可丢失**（`allkeys-lru`、不持久化）；miss 回源 MySQL / 重建 |
| **RabbitMQ** | 异步与削峰 | 下单、点赞落库、AI 分析、延迟关单、延迟双删 | **至少一次投递**，消费端必须幂等 |
| **阿里云 OSS** | 大对象存储 | 帖子图片 | 不可重建，需持久化保障 |

**核心设计立场**：

> **Redis 是加速器与协调器，不是数据库。** 除秒杀库存外，Redis 中的任何数据都必须能从 MySQL 重建。秒杀库存是唯一的例外，它采用"Redis 为权威、DB 为落账"的有损设计，因此必须有 6.7.8 的对账与补偿机制兜底。

**两个 Redis 实例的硬边界**：

- `redis-core` 与 `redis-cache` 是**两个独立进程、两套连接、两套 `RedisTemplate`**，不是同一个实例的 logical DB；logical DB 不隔离内存与淘汰。
- 禁止跨 core / cache 做多 Key 原子操作；需要原子的 Lua 脚本只能落在同一个实例。
- Redisson 只连 `redis-core`（锁 + `RBloomFilter`）；缓存重建锁也必须走 core。
- `redis-core` 内存满时**写命令报 OOM**，这是有意为之：宁可让写入失败并告警，也不静默淘汰锁 / Token / 库存。容量与告警见 5.2.1。
- 开发环境基础设施部署在 CentOS 7 VM `192.168.157.129`：core `6379`、cache `6380`；后端在 Windows 宿主机时直接用 VM IP，容器化后才用 Compose 服务名。

1. **所有 Key 必须带 `glimmer:` 前缀**，便于与服务共用同一 Redis 实例时隔离、便于 `SCAN` 巡检；

### 6.2 缓存设计 ★

#### 6.2.1 问题

PRD 6.5 要求同时防御三类缓存故障：**穿透**（查不存在的数据）、**击穿**（热点 Key 失效）、**雪崩**（大面积失效）。同时保证缓存与数据库的一致性。

#### 6.2.2 防穿透：布隆过滤器 + 空值缓存（双层）

**只做空值缓存的问题**：

> 空值缓存是**按 Key 存储**的。攻击者用**随机 ID**构造海量互不相同的 Key，Redis 需为每个都存一份垃圾数据 → **内存被打爆**。攻击者成本极低，防守方成本极高。

**布隆过滤器原理与容量计算**：

布隆过滤器 = 位数组 + k 个哈希函数。判定规则：**k 个位置只要有 1 个为 0，则元素一定不存在**；全为 1 则可能存在。

| 性质 | 结论 | 对设计的影响 |
|---|---|---|
| **无假阴性** | "不存在"绝对准确 | 可以安全拦截，不会误杀真实数据 |
| **有假阳性** | "可能存在"有概率 p 为假 | 少量请求会漏到 DB，需第二层兜底 |
| **不支持删除** | 元素删除后位数组无法清除 | 删除的数据会持续"被认为存在" |

**容量计算**（依据 2.2 的 1000 万帖子）：

```
m = -n · ln(p) / (ln2)²     位数组长度
k = (m / n) · ln2           哈希函数个数

n = 10,000,000，p = 0.01
m ≈ 9.59 bit/元素 × 10^7 = 95.9 Mbit ≈ 12 MB
k ≈ 6.64 ≈ 7
```

**结论：1000 万帖子、1% 误判率，仅需约 12 MB、7 个哈希函数。** 单体量级下单 Redis Key 即可承载，**无需分片**。

**内存效率对比**（说明为什么不能只靠空值缓存）：

| 方案 | 12 MB 内存能覆盖的判定范围 |
|---|---|
| 布隆过滤器 | **1000 万个 ID** |
| 空值缓存 | 约 10 万个 Key（每个 Redis Key 含元数据开销约 100+ 字节） |

量级差距约 **100 倍**。这就是布隆过滤器存在的理由。

**双层防护流程**：

```
请求 GET /post/{id}
   │
   ▼
① 布隆过滤器 glimmer:content:bloom:post
   ├─ 判定"一定不存在" ──► 直接返回 404        ← 拦住 99% 随机 ID 攻击
   └─ 判定"可能存在"（含 1% 假阳性）
              │
              ▼
② Redis 缓存 glimmer:content:post:{id}
   ├─ 命中 ──────────────► 返回
   └─ 未命中
              │
              ▼
③ 空值缓存 glimmer:content:post:null:{id}
   ├─ 命中 ──────────────► 返回 404            ← 兜住假阳性 + 已删除数据
   └─ 未命中
              │
              ▼
④ 查 MySQL
   ├─ 存在 ──► 回填①缓存（TTL 30min + 随机抖动）──► 返回
   └─ 不存在 ──► 回填②空值缓存（TTL 60s）──────► 返回 404
```

**两层是互补而非二选一**（面试关键表述）：

> 布隆过滤器用**固定内存**挡住海量随机 Key，代价是假阳性；空值缓存用**逐 Key 内存**提供**精确**判断，但无法承受海量 Key。两者叠加，才同时具备内存效率与判断准确率。

**落地细节**：

| 要点 | 方案 |
|---|---|
| 实现选型 | Redisson `RBloomFilter`（复用已有依赖，分布式一致） |
| 初始化 | `tryInit(10_000_000L, 0.01)`，期望容量按 2.2 容量假设上浮 20% 留余量 |
| 预热 | 应用启动后**异步分批**加载全量帖子 ID（`ApplicationRunner` + 每批 1000 条 + 分批 Sleep），**不阻塞启动** |
| 新增同步 | 发帖事务提交后 `add(postId)`；跨节点失败由 MQ 异步补偿消息兜底 |
| 重建预案 | 容量使用率达 **80%** 时告警；重建采用**双写切换**：新建 Key → 双写 → 全量重载 → 切读 → 删旧 |
| 分片 | 单体量级不需要；若帖子量增长 10 倍（1 亿），再按月或按 ID 段分片 |

**详情缓存值契约（P1-7）**：`glimmer:content:post:{id}` 只存**稳定字段**（作者、标题、正文、图片、标签、`publishedAt`、状态），**不存** `likeCount` / `commentCount` / `collectCount` / `viewCount`。响应组装时由 `PostDetailAssembler` 从计数 Key / DB 叠加，计数 Key miss 时回源 DB 并回填。这样点赞、评论后无需删除详情缓存，也不会返回 30 分钟前的陈旧计数。

#### 6.2.3 防击穿：热点 Key 重建

**问题**：热点帖子缓存过期的瞬间，大量并发同时击穿到 DB。

**方案**：**互斥锁重建**（MVP 采用）

```
缓存未命中 → 尝试获取分布式锁 glimmer:lock:post:{id}（Redisson RLock，core 实例）
   ├─ 获取成功 → 查 DB → 回填缓存 → 释放锁
   └─ 获取失败 → 短暂等待（如 50ms）后重试读缓存，最多重试 3 次
```

锁参数：`tryLock(0, 10, TimeUnit.SECONDS)`（不等待、lease 10s；缓存重建是短任务，不依赖 watchdog 续期）；重试读缓存最多 3 次，仍 miss 则直接查 DB（限流保护），不无限等锁。锁只保证“少重建一次”，**不保证缓存一定最新**；旧快照覆盖新缓存的窗口由延迟双删兜底。锁 Key 必须在 **core**，不能放 cache。

**备选方案（不采用，记录理由）**：逻辑过期（缓存不设 TTL，值内嵌逻辑过期时间，过期后异步重建返回旧值）。优点是零等待，但实现复杂且会返回陈旧数据，本项目无此必要。

#### 6.2.4 防雪崩

| 手段 | 做法 |
|---|---|
| TTL 随机抖动 | 基础 TTL 30 min + 随机 0~5 min，避免批量同时失效 |
| 缓存预热 | 启动时预热热榜前 100 帖 |
| DB 兜底保护 | 缓存大面积失效时，通过限流（6.10.3）保护 DB 不被打垮 |
| Redis 高可用 | 生产环境部署主从 + Sentinel（Docker Compose 阶段至少保证持久化） |

#### 6.2.5 缓存一致性：Cache Aside + 延迟双删

**写流程**：

```
1. 更新 MySQL
2. 删除 Redis 缓存
3. 发送 MQ 延迟消息（延迟 500ms）  ← 利用 4.2.4 的延迟交换机
4. 消费者收到消息 → 再次删除缓存   ← 清理第 3 步期间可能被读请求回填的旧值
```

**为什么是"先更库再删缓存"而不是"先删缓存再更库"**：

> 若先删缓存、再更库，则在两步之间到达的读请求会把**旧值**回填到缓存，且此后无人清理，脏数据长期驻留。先更库则把风险窗口压缩到"删缓存"这一瞬间，且该窗口内的脏值会被第 3、4 步的延迟双删清除。

**为什么不能只删一次**：删除缓存与更新 DB 之间仍存在极小窗口（读请求在 DB 更新前读了旧值并回填）。延迟双删是**降低概率**而非彻底消除，属于工程上性价比最高的方案。若需强一致，应引入 Canal 订阅 binlog —— 本项目不采用（违反 2.3 不过度设计原则）。

### 6.3 统一幂等方案（横向关注点）

> PRD 6.7 明确：点赞、抢购、MQ 消费、支付回调均需幂等。四者分布在不同模块，共用同一套思想，故在此统一设计。

#### 6.3.1 幂等键设计

**原则**：幂等键 = **能唯一标识"同一次业务意图"** 的最小字段组合。

| 场景 | 幂等键 | 存储 | 有效期 |
|---|---|---|---|
| 点赞 | `userId:postId` | Redis Set（业务结构自带） | 永久 |
| 秒杀抢购 | `userId:activityId` | Redis SETNX + DB 唯一索引 | 24 h / 永久 |
| MQ 消费 | `messageId`（或业务幂等键） | Redis SETNX + 业务唯一索引（不建消费记录表） | 24 h |
| 支付回调 | `orderNo` + `tradeNo` | DB 订单状态机（CAS） | 永久 |

#### 6.3.2 三层幂等防线

```
第一层：入口拦截   —— Redis SETNX 幂等标记，重复请求直接返回上次结果
第二层：状态机 CAS —— UPDATE ... WHERE status = '待支付'，靠受影响行数判断
第三层：唯一索引   —— DB 唯一约束兜底，捕获 DuplicateKeyException 转为幂等返回
```

**核心认识**：

> **Redis 幂等标记会过期、会因故障丢失，所以它是"性能优化"而非"正确性保证"。真正的正确性必须由数据库约束（唯一索引 / CAS）兜底。** 三层缺一不可：第一层挡掉绝大多数，第三层保证万无一失。
>
> **MVP 不建 MQ 消费记录表**：消费者用 Redis `SETNX` 挡重复，最终靠业务唯一索引（点赞 `uk_user_post`、订单 `uk_user_activity`、库存 CAS）兜底。搜索索引消费者不需要去重——它是「按 postId 回查 MySQL 当前状态」的幂等操作。

#### 6.3.3 MQ 消费幂等（通用）

所有消费者统一继承 `AbstractIdempotentConsumer`：

```
1. 取消息唯一 ID（MessageProperties.messageId，或业务键）
2. SETNX glimmer:mq:consumed:{msgId} 1 EX 86400
   ├─ 设置失败（已消费）→ 直接 ACK 丢弃
   └─ 设置成功 → 执行业务
3. 业务成功 → ACK
   业务失败 → NACK / 重入重试队列（最多 3 次）→ 超限进死信队列 + 告警
```

> ⚠️ **注意 QPS 1000 下的正确性问题**：RabbitMQ 是**至少一次投递**，重复消费是常态而非异常。**每一个消费者都必须幂等，没有例外。**

### 6.4 点赞方案

#### 6.4.1 数据结构

| Key | 类型 | 作用 |
|---|---|---|
| `glimmer:interaction:liked:{postId}` | Set | 点过赞的 userId 集合 → **一人一赞的判据 + 幂等依据** |
| `glimmer:interaction:like:count:{postId}` | String | 点赞数（前端展示读这里） |

**为什么用 Set 而不是 Bitmap**：Bitmap 更省内存，但需要 userId 是**连续稠密整数**。本设计以自增 ID 为前提勉强可用，但用户量增长后 ID 稀疏会造成浪费，且无法应对分库分表后的 ID 跳变。Set 语义清晰、通用性更好，在 1 亿点赞的假设下内存可接受。

#### 6.4.2 点赞 / 取消点赞（Lua 原子脚本）

**问题**：判断"是否已赞"与"增减计数"必须是**原子的**，否则并发下会出现计数与 Set 不一致。

```lua
-- KEYS[1] = glimmer:interaction:liked:{postId}
-- KEYS[2] = glimmer:interaction:like:count:{postId}
-- ARGV[1] = userId
-- 返回: 1=点赞成功 0=已点赞(幂等) -1=计数 Key 缺失，需要先回源初始化

if redis.call('EXISTS', KEYS[2]) == 0 then
    return -1                             -- 不能从 0 开始 INCR，先由 Service 读 DB 初始化
end
if redis.call('SISMEMBER', KEYS[1], ARGV[1]) == 1 then
    return 0                              -- 已赞，幂等返回
end
redis.call('SADD', KEYS[1], ARGV[1])
redis.call('INCR', KEYS[2])
return 1
```

取消点赞为对称逻辑（`SREM` + `DECR`，且需防计数减为负数）。

> **Hash Tag 注意**：若未来 Redis Cluster 化，两个 Key 需改为 `glimmer:interaction:{postId}:liked` 与 `glimmer:interaction:{postId}:count` 以保证同 Slot。
>
> **缓存淘汰兜底**：`liked` Set 被 LRU 淘汰后，同一用户可能再次通过 Redis 判重，导致计数多 `+1`；DB `uk_user_post` 会拦住重复记录，消费者只在插入成功时更新 `like_count`，每小时对账再以 DB 为准修正 Redis。**允许短暂偏差，不允许 DB 重复行。**

#### 6.4.3 异步落库

```
点赞成功 → 发送 MQ 消息 {postId, userId, action, timestamp}
   │
   ▼
消费者（幂等）：
  1. 写 t_like（唯一索引 uk_user_post 兜底幂等；重复消息直接跳过）
  2. 仅在本次插入成功时，调用 content 的 Service（如 ContentService.onLikeChanged(postId, delta)）
     更新 t_post.like_count —— interaction 不注入 PostMapper
     两步在同一个本地事务内，计数失败则 t_like 一起回滚
```

**为什么异步**：点赞是高频写操作（假设日 100 万），同步落库会给 MySQL 造成大量行锁竞争。Redis 计数 + MQ 异步落库把写压力转换成顺序消费。

#### 6.4.4 边界与兜底

| 问题 | 处理 |
|---|---|
| MQ 消费失败导致计数丢失 | 定时对账任务（每小时）比对 Redis 与 DB 计数，以 **DB 为准**修正 Redis |
| 帖子被删除 | 清理对应 Set，DB 侧软删除（`is_deleted`） |
| 用户点赞列表查询 | 走 DB（`t_like` 按 `user_id` 索引分页），不单独建 Redis 结构（避免双份内存） |
| 计数与 Set 不一致 | 上述 Lua 脚本保证单次操作原子；跨操作不一致由对账兜底 |

### 6.5 Feed 流方案

#### 6.5.1 问题

PRD 6.3 要求遵循**推拉结合**，按粉丝量阈值切换。核心矛盾：

- **写扩散（推）**：帖子**发布成功后立即**推给所有粉丝。读极快，但**大 V 发帖成本 = 粉丝数**（1 万粉丝 = 1 万次写入）；
- **读扩散（拉）**：读时聚合关注列表。写成本恒定，但**读成本 = 关注数**，且需要归并排序。

#### 6.5.2 阈值

**决策：粉丝数 < 1000 走推模式，≥ 1000 走拉模式。**

依据（结合 2.2 容量假设）：

- 人均粉丝 100 → 99% 的用户走推模式，单次发帖写入成本 < 100，成本可忽略；
- 头部账号（约 100 个，粉丝 > 1 万）若走推模式，单次发帖需 1 万次 Redis 写入，且其粉丝收件箱会被大 V 内容挤占 → **必须走拉模式**；
- 阈值可配置（`glimmer.feed.push-threshold`），便于演示与调参。

#### 6.5.3 推模式（写扩散）

```
普通用户 / 管理员发帖（事务提交后，异步）
   │
   ▼
查作者粉丝列表（glimmer:user:follow:ers:{authorId}）
   │
   ▼
分批（每批 500）写入各粉丝收件箱：
   ZADD glimmer:feed:inbox:{fanId} {timestamp} {postId}
   ZREMRANGEBYRANK glimmer:feed:inbox:{fanId} 0 -201   ← 只保留最近 200 条
   EXPIRE glimmer:feed:inbox:{fanId} 2592000           ← 30 天
```

**收件箱裁剪**是必须的：否则冷用户的收件箱会无限增长。写扩散只投递给**最近 30 天登录过**的粉丝；不活跃用户不写，等其下次登录读 Feed 时按“关注列表 + 最近公开帖子”回源重建一页，再异步补箱。`feed:outbox` 同样只保留最近 200 条。

**活跃用户的判定**（`t_user` 无 `last_login_at`，不为此加字段）：

- 登录成功时写 `ZADD glimmer:user:active {nowMs} {userId}`（**cache 实例**，登录本来就要写 Token，这里只是多一次轻量写）；
- 每日凌晨任务 `ZREMRANGEBYSCORE glimmer:user:active -inf {nowMs-30d}` 裁剪；
- 写扩散投递前用 `ZSCORE` 判断粉丝是否在集合内，不在则跳过；
- 该 ZSet 在 cache 实例，可能被 LRU 淘汰或 Redis 重启丢失。**丢失的语义 = 该批用户按“不活跃”处理**：不写收件箱不丢内容，用户下次登录 / 读 Feed 时按回源路径重建。因此这里不需要持久化，也不需要与 core 实例做任何补偿。

> **先发后审的影响**：普通用户发帖后立即公开并触发写扩散，同时进入待审核队列；管理员发帖跳过审核，同样在创建后立即触发。审核拒绝、下架或作者删除后，收件箱中的帖子 ID 可以保留，但读取 Feed 时必须按 `status IN (0,1) AND is_deleted=0` 过滤，不能把审核拒绝 / 已下架内容返回给用户。

**关注关系变更**：

- **关注**：DB 事务写 `t_user_follow` + 双方计数；事务提交后（`@TransactionalEventListener(AFTER_COMMIT)`）再更新 Redis Set，并把该博主最近 N（如 50）条**公开可见**帖子写入我的收件箱（保证关注后立刻有内容）；
- **取关**：同样在 DB 事务提交后更新 Redis Set；**不做收件箱同步清理**（成本高、价值低），在查询时按当前关注列表过滤；
- Redis Set 更新失败只记日志 / 告警，不回滚 DB；读路径 Set miss 时从 DB 重建。Redis 和 MySQL 没有共同事务，不能写成“同事务更新”。

#### 6.5.4 拉模式（读扩散）

粉丝数 ≥ 1000 的作者，其帖子**不写入**粉丝收件箱。

#### 6.5.5 关注流查询（推拉归并）

```
GET /feed/follow?cursor={ts}&size=20

1. 取自己的收件箱前 40 条（多取 2 倍，给过滤留余量）：ZREVRANGEBYSCORE glimmer:feed:inbox:{me} ...
2. 取当前关注集合（Redis Set，miss 回源 DB）
3. 取我关注的大 V 列表（粉丝 ≥ 1000 的）
4. 对每个大 V：按 published_at 查其公开可见帖子（Redis 缓存 / DB 索引），各取前 20 条
5. 用「败者树 / 优先队列」做 K 路归并，按 published_at 降序
6. 过滤：作者不在当前关注集合 / 审核拒绝 / 已删除 / 已下架
7. 不足一页继续取，直到凑够 20 条或耗尽；游标以最后一条**实际返回**的帖子为准
8. 组装返回
```

> **取关过滤是必须的**：取关时不清收件箱，如果读路径只过滤审核状态，已取关作者的内容仍会出现。多取 2 倍是为了避免过滤后大量空页；极端情况下允许返回空页 + `hasMore=true`，客户端继续翻。

**优化**：大 V 的最近帖子用 `glimmer:feed:outbox:{authorId}`（ZSet，作者自己的发帖列表）缓存，避免每次查 DB。

#### 6.5.6 分页

**决策：用户端信息流使用游标分页（时间戳 / Score 游标），不使用 Offset 分页。**

| 方案 | 问题 |
|---|---|
| `LIMIT offset, size` | 大 offset 需扫描跳过，越翻越慢；且**翻页期间有新帖会导致内容重复/丢失** |
| **游标分页** ✅ | `ZREVRANGEBYSCORE ... (cursor` 直接定位，性能恒定；天然避免翻页漂移 |

> 本节限定于 Feed / 搜索 / 评论等用户端信息流；管理端后台列表不属于信息流，使用 PageHelper 页码分页（见 4.2.2），两者不共用同一套查询。

#### 6.5.7 边界与兜底

| 问题 | 处理 |
|---|---|
| 冷启动（新用户无收件箱 / 未关注任何人） | 降级返回**推荐流**（热榜 Top N） |
| 收件箱为空或过期（长期未登录，期间未写扩散） | 先按“关注列表 + 最近公开帖子”回源重建一页并返回，异步补箱；无关注或重建结果为空，再降级热榜 |
| `glimmer:user:active` 丢失 / 粉丝未被判定为活跃 | 按不活跃处理，跳过写扩散；读 Feed 时走上面的回源重建，不丢内容 |
| 大 V 数量过多（关注 > 500） | 限制拉取的博主数量上限，超出部分按活跃度裁剪 |
| 写扩散 MQ 失败 | 不影响发帖（发帖 / 审核已成功）；记录失败指标并告警，**不做自动补偿**。漏推的帖子仍可从作者主页、热榜、搜索、拉模式获得；MVP 不建「未投递记录表」/ Outbox |

### 6.6 热榜方案

#### 6.6.1 热度分公式

**决策**：采用 **Hacker News 式时间衰减**：

```
raw   = 1 × 点赞数 + 2 × 评论数 + 0.1 × 浏览数
score = raw / (ageHours + 2)^1.5
```

**设计说明**：

| 部分 | 取值 | 理由 |
|---|---|---|
| 评论权重 2 > 点赞权重 1 | — | **评论的创作成本远高于点赞**，更能反映内容价值（互动质量） |
| 浏览权重 0.1 | — | 浏览是低意图行为，且易被刷，权重最低 |
| `(ageHours + 2)` | 分母加 2 | 防止新帖（age → 0）除零，并避免"刚发布就冲上第一" |
| **1.5 次方** | — | Hacker News 实证参数：衰减比线性快、比平方慢，**新内容有机会、老内容不霸榜** |

#### 6.6.2 实现

| 项 | 方案 |
|---|---|
| 数据结构 | `glimmer:feed:hot`（ZSet，member = postId，score = 热度分） |
| 更新方式 | **定时任务每 5 分钟**：扫描最近 24h 有互动的帖子 → 批量重算 score → `ZADD` |
| 时间衰减基准 | `ageHours = now - published_at`，不用 `created_at`；`published_at` 在首次发布时写入，审核通过、下架恢复、编辑重新提交均不重置 |
| 为何定时重算 | 时间衰减项随 `ageHours` 持续变化，**即使无新互动分数也会下降**，因此必须周期性重算 |
| 榜单范围 | ZSet 保留 Top 1000（`ZREMRANGEBYRANK 0 -1001`） |
| 查询 | `ZREVRANGE` 分页，附帖子摘要（批量 `MGET` 缓存） |
| 浏览量 | 浏览计数在 Redis 累加（`glimmer:content:view:{postId}`），由定时任务合并入 DB 并重置 |

#### 6.6.3 边界与兜底

| 问题 | 处理 |
|---|---|
| 定时任务多实例重复执行 | Redisson 分布式锁 `glimmer:lock:job:hot`（**core 实例**）保证单次执行；`tryLock(0, TimeUnit.SECONDS)` 使用 watchdog，任务结束主动释放 |
| 刷赞刷评论 | 权重克制 + 单用户对单帖的互动只计一次 + 异常账号过滤（预留） |
| 冷启动（Redis 空） | 任务首次执行时全量扫描最近 24h 帖子重建 |
| 浏览量丢失 | 浏览量最终以 DB 合并结果为准，Redis 计数允许丢失 |

### 6.7 秒杀方案 ★★

> **本项目技术旗舰。** 对应 PRD 6.2，需同时满足：防超卖、限购、削峰、异步下单、超时关单、最终一致。

#### 6.7.1 总体流程

```
【阶段一：活动预热】运营创建活动
        │
        ▼
  写入 MySQL（活动 + 库存）
  写入 Redis：{activityId}:stock = 库存
  写入 Redis：seckill:activity:{activityId} = 活动信息
  加入布隆过滤器：glimmer:seckill:bloom:activity
  预创建延迟交换机与队列

【阶段二：抢购（瞬时高并发，全 Redis 路径）】
  请求 ──► 限流 ──► 活动校验（纯 Redis）──► Lua 原子扣减（库存 + bought 资格）
                                                              │
                                    ┌─────────────────────────┤
                                    ▼                         ▼
                              扣减成功                    扣减失败
                                    │                         │
                    投递到秒杀独立舱壁线程池（有界）      返回 售罄 / 超限
                                    │
                    异步发送 MQ（publisher confirm）
                                    │
                    立即返回 202「已获资格，投递中」
                    （activityId + QUEUED，不等 confirm）

【阶段三：异步下单（消费端匀速处理）】
  MQ 消费者 ──► 幂等校验 ──► DB 条件扣减库存 ──► 创建订单（待支付）
                                                      │
                                          发送延迟消息（30 分钟）

【阶段四：支付 或 超时关单】
  用户支付 ──► 支付回调（幂等）──► 订单状态 = 已支付
                                    （延迟消息到达时检查状态，已支付则忽略）

  延迟消息到期 ──► 检查订单状态
                    ├─ 已支付 → 忽略
                    └─ 待支付 → 关单 + 回补库存（Redis + DB）；不释放该用户的抢购资格

【阶段五：对账补偿】（定时任务兜底）
```

#### 6.7.2 抢购的 Lua 原子脚本

**为什么必须用 Lua**：库存判断、限购判断、库存扣减、限购累加 —— 这四步在并发下**必须整体原子**。任何一步单独执行都会产生超卖或超额。

```lua
-- KEYS[1] = glimmer:seckill:{activityId}:stock      (String)
-- KEYS[2] = glimmer:seckill:{activityId}:bought     (Hash: userId -> 1，表示已占用抢购资格)
-- ARGV[1] = userId
-- ARGV[2] = limitNum (限购数)
-- 返回: 0=成功  1=售罄  2=超出限购

local stock = tonumber(redis.call('GET', KEYS[1]) or '0')
if stock <= 0 then
    return 1
end

local bought = tonumber(redis.call('HGET', KEYS[2], ARGV[1]) or '0')
if bought >= tonumber(ARGV[2]) then
    return 2
end

redis.call('DECR', KEYS[1])
redis.call('HINCRBY', KEYS[2], ARGV[1], 1)
return 0
```

**要点**：

1. **两个 Key 使用 Hash Tag `{activityId}`** → Redis Cluster 下同 Slot，脚本可执行；
2. 用 **Hash 而非 Set** 记录已购 → 保留未来**限购 N 件**的扩展空间；MVP 中值为 1，等价于“已占用抢购资格”；
3. 用 `tonumber(... or '0')` 防御 Key 不存在导致的 `nil` 比较异常；
4. 脚本内**只有 Redis 操作，无任何阻塞调用** → 执行时间微秒级；
5. **MVP 的 `limitNum` 固定为 1**，与 `uk_user_activity` 的「一人一单」一致；关单后 `bought` 不回落，用户不能重新抢；N>1 需要「一单多件」或配额表，列为演进，不在 MVP 实现。

#### 6.7.3 活动校验：全 Redis 路径

抢购校验**不允许查 MySQL**，否则秒杀瞬间会把 DB 打垮。活动信息在预热阶段已写入 Redis：

| 校验项 | 数据来源 |
|---|---|
| 活动是否存在 | `glimmer:seckill:bloom:activity` → 活动缓存 |
| 是否开始 / 是否结束 | 活动缓存中的起止时间 vs 服务器时间 |
| 是否恢复中 | `glimmer:seckill:recovering:{activityId}` 存在 → 50301 |
| 库存 | Redis 库存 Key |

> 注意：**服务器时间必须以单一时钟源为准**（单机部署天然满足；分布式阶段需 NTP 或 Redis 时间）。

#### 6.7.4 超时关单：RabbitMQ 延迟消息

**方案 A（采用）：`rabbitmq_delayed_message_exchange` 插件**

```
声明 x-delayed-message 类型交换机 → 发送时设置 header x-delay = 1800000 (30min)
```

优点：实现直接、支持任意延迟时长、无队头阻塞。

**方案 B（降级备选）：TTL + 死信队列（DLX）**

```
正常队列（无消费者）──────── TTL 30min 到期 ────► 死信交换机 ────► 关单队列 ────► 消费者
```

缺点：**队头阻塞** —— RabbitMQ 只检查队首消息的 TTL，若队首消息 TTL 较长，后面的短 TTL 消息无法及时过期。因此要求队列内所有消息 TTL 一致（本项目均为 30 分钟，故可行）。

> ⚠️ **部署要求**：方案 A 需要安装插件。`deploy/rabbitmq/Dockerfile` 已基于 `rabbitmq:3.13-management` 下载并启用 `rabbitmq_delayed_message_exchange 3.13.0`；Compose 必须使用该 build，否则换台机器部署会失败。这是本项目最容易被忽略的部署陷阱。

#### 6.7.5 消息可靠性：弥补 RabbitMQ 无事务消息

**问题（4.2.4 已述）**：Redis 扣减成功 → 发送 MQ 消息。若此时发送失败（网络 / Broker 宕机），会出现 **Redis 库存已扣、但订单永远不会创建** 的"幽灵扣减"。

**结论（2026-10-21）：异步 confirm + 延迟补偿 + 舱壁，禁止请求线程同步等待。**

```
1. Lua 扣减成功（stock -1，bought +1）
2. 提交「发送任务」到秒杀专用有界线程池（core 64 / max 64 / queue 0）
   └─ 拒绝 → 立即回滚 Lua（INCR stock / HINCRBY bought -1）→ 50301
3. RabbitTemplate.convertAndSend（独立 seckill 连接 + correlated confirm）
4. 立即返回 202「已获资格，投递中」（不等 confirm）
5. confirm ACK → 结束
6. confirm NACK / 超时（默认 1s，可配置 500ms–2s）：
   a. 不立即回滚；延迟 5s 查 (userId, activityId) 订单
   b. 订单已存在 → 说明消息实际投递成功，不滚
   c. 订单不存在 → 先写 cancel 标记
      glimmer:seckill:cancel:{userId}:{activityId}=1（TTL 24h）
      再回滚 stock / bought → 用户回到 NOT_PARTICIPATED
7. 消费者执行前先查 cancel 标记；存在则直接 ACK，不创建订单
```

**为什么不能同步等 3 秒**：

- Tomcat 默认约 200 个工作线程。1000 QPS × 3s 等待 = 3000 个并发请求，线程池 0.2 秒内打满；
- 打满后**整个应用**（Feed、登录、详情）一起不可用，Broker 的局部故障被放大成全站故障；
- 异步 confirm 下，请求线程只做“提交任务 + 发送”，不占等待时间；Broker 慢只会让秒杀舱壁先满并快速失败，不影响其他接口。

**舱壁与连接隔离**：

- 秒杀发送使用独立的 `ThreadPoolTaskExecutor`（32–64 线程、queue=0、`AbortPolicy`）；池满直接回滚 + `50301`，不排队；
- 秒杀使用独立的 `CachingConnectionFactory` / `RabbitTemplate`，与点赞、AI、搜索连接隔离；
- confirm 用 `CorrelationData.getFuture()` 异步回调，**不使用 `waitForConfirms`**；同时开启 `publisher-returns` + `mandatory`，捕获不可路由消息；
- 监控：confirm 失败率、超时率、cancel 标记数、回滚次数、舱壁拒绝数；任一持续 > 0 都告警。

**边界**：

- 延迟 5s 内订单可能仍在消费者队列中；cancel 标记确保晚到的消息不会创建订单，因此“先 cancel、后回滚”的顺序不能反；
- 若应用在“写 cancel”与“回滚”之间崩溃，对账任务按 `cancel=1 且无订单` 补回滚；
- 回滚本身失败时只告警，由 6.7.8 静默期对账兜底，禁止运行期自动重复回滚；
- MQ 发送成功但消费者持续失败 → 重试 3 次后进 DLQ，人工/对账处理。

**演进方案：本地消息表（Outbox）**

```
1. 本地事务：写入 t_seckill_request（状态=待投递）+ Redis 扣减
2. 定时任务扫描「待投递」记录 → 投递 MQ → 标记「已投递」
3. 消费端幂等处理
```

优点：DB 事务保证消息不丢；缺点：需额外表与扫描任务，延迟略高。**阶段 7 微服务化时升级采用**。

#### 6.7.6 异步下单（消费者）

```
消费消息 {userId, activityId}
  │
  ├─ ① 取消标记：GET glimmer:seckill:cancel:{userId}:{activityId}
  │     存在 → ACK（confirm 已失败并回滚，不能再建单）
  │
  ├─ ② 幂等快速校验：SETNX glimmer:seckill:idem:{userId}:{activityId}
  │     已存在 → 按 (userId, activityId) 查 DB 是否已有订单（含已关闭）：
  │        有 → ACK（真重复）
  │        无 → 继续执行（上次可能在 SETNX 后、提交前崩溃，不能直接 ACK）
  │
  ├─ ③ 先查订单（含已关闭）：
  │     已存在 → ACK，绝不再次扣库存
  │
  ├─ ④ 同一本地事务内：
  │     a. DB 条件扣减库存（第二道防超卖）
  │        UPDATE t_seckill_activity
  │        SET stock = stock - 1
  │        WHERE id = ? AND stock >= 1
  │        受影响行数 = 0 → 抛异常回滚事务，告警
  │     b. 创建订单（状态 = 待支付）
  │        唯一索引 uk_user_activity (user_id, activity_id) 兜底一人一单
  │        DuplicateKeyException → 整个事务回滚（库存扣减一起回滚）→ ACK
  │
  ├─ ⑤ 发送延迟消息（30 分钟后触发关单检查）
  │
  └─ ⑥ ACK
```

> **`idem` 不是成功标记**：它只表示“这条消息被消费过/正在消费”，最终是否成功以 `t_seckill_order` 是否有记录为准。因此重复消息即使 `idem` 存在、订单不存在，也要继续执行；`uk_user_activity` 与同一事务保证不会重复扣库存。
>
> **先查订单再扣库存**：防止 `idem` 被清理 / 丢失后，重复消息再次扣减 DB 库存。`t_seckill_order` 上必须有 `(user_id, activity_id)` 唯一索引，查询走该索引。

**消费端并发控制**：`concurrency: 5~10`（可配置）。**这是削峰的核心** —— 无论瞬时涌入多少请求，落到 MySQL 的写压力被限制在这个并发度上。

#### 6.7.7 库存回补（关单）

```
延迟消息到达 → 查订单状态
   ├─ 已支付 → 忽略（正常结束）
   └─ 待支付/不存在 → 执行关单：
        ① UPDATE t_seckill_order SET status='已关闭' WHERE order_no=? AND status='待支付'
           （CAS，受影响行数 = 0 说明状态已变，直接返回）
        ② DB 库存 +1：UPDATE t_seckill_activity SET stock = stock + 1 WHERE id=?
        ③ Redis 库存 +1：INCR glimmer:seckill:{activityId}:stock
        ④ 不回退资格标记：glimmer:seckill:{activityId}:bought 保持 1
        ⑤ 幂等标记无需改状态：idem:{userId}:{activityId} 保留至 TTL 到期
           ← 一人一单，用户不能重新抢购；查询按订单状态返回 CLOSED
```

**注意步骤 ④ / ⑤**：一人一单下，关单只回补库存，**不释放该用户的抢购资格**；否则用户可反复占库存。若订单创建失败（DB 无订单），才回补库存并 `HINCRBY bought -1`，允许用户重试。

**另需处理**：若 Redis 库存 Key 已因活动结束被清理，`INCR` 会创建新 Key（值为 1），这是错误状态。因此回补前需先判断活动是否仍在有效期，或**活动结束时间后不清理库存 Key**，交由对账任务统一清理。

#### 6.7.8 对账与补偿（MVP：静默期兜底）

> **原则：运行期不做破坏性自动补偿；以「静默期 + DB 真相」兜底。**

**运行期**：只做只读检查与告警；售罄后出现静默窗口时，只做安全重投，不改库存。

| 检查项 | 判据 | 处理 |
|---|---|---|
| Redis 库存一致性 | `redisStock + Σ有效订单qty == total` | 不一致 → 告警（任一时刻都应成立） |
| DB 内部一致性 | `dbStock + Σ有效订单qty == total` | 不一致 → 告警（要求消费者扣库存与建单同一事务） |
| 订单队列健康 | DLQ 无堆积 | 堆积 → 告警 + 人工排查 |

> 异步在途期间，Redis 库存低于 DB 属于正常状态，不判定为异常。`bought` 表示“已占用抢购资格”（含已关闭订单），不参与库存等式；其一致性单独校验：`bought` 的 userId 集合应等于该活动所有订单（含已关闭）的 userId 集合。

**Redis 重启 / core 故障恢复预案（P0-3）**：

```
检测到 core 重连（或健康检查由 DOWN 转 UP）
  │
  ├─ ① 对所有进行中的活动写 glimmer:seckill:recovering:{activityId}=1（TTL 30min）
  │     抢购入口看到 recovering → 50301「系统恢复中」，不读旧库存
  │
  ├─ ② 暂停秒杀消费者；等待订单队列 ready=0 且 unacked=0
  │     最多等 30 分钟；仍不满足 → 告警，人工介入
  │
  ├─ ③ 以 DB 为准重建：
  │     stock = total - Σ(待支付 + 已支付订单 qty)
  │     bought = 该活动全部订单（含已关闭）的 userId -> 1
  │     重建活动缓存 / 布隆
  │
  ├─ ④ 删除 recovering 标记，恢复消费者与新抢购
  │
  └─ ⑤ 记录告警与重建前后快照，人工复核
```

- AOF everysec 最多丢 1 秒扣减；重建以 DB 订单为准，**不能**用“Redis 库存 + 回滚日志”猜；
- 恢复期间禁止新抢购，避免用户拿到 `QUEUED` 后又被回滚；
- 恢复动作幂等，可重复执行；不要在恢复期做“自动回补库存”；
- cache 实例重启不需要该流程：缓存 miss 回源即可，秒杀只依赖 core。

**静默期判定（只使用现有数据，不新增表 / Redis Key）**：

- 活动已结束，或 `stock == 0`（售罄后 Lua 不再接受新请求）；
- 订单队列 `ready = 0` 且 `unacked = 0`；
- DLQ 无堆积；
- 距最后一笔订单创建 > `T_quiet`（5–10 分钟；无订单视为满足）。

**执行时机（不轮询）**：

- **第一次**：活动结束后 10 分钟执行，等队列排空；若 `ready/unacked` 不为 0，每 5 分钟重试，最多 30 分钟，仍不满足则告警，等人工处理；
- **第二次**：第一次成功执行后 35 分钟（且不早于活动结束 + 45 分钟）做关单补偿兜底重建；
- 应用重启时扫描最近结束的活动并补跑逾期任务；任务本身幂等，重复执行无副作用；
- 活动进行中不自动修复。若售罄后想提前修，提供手动触发的管理接口（可选），触发前检查 `stock == 0` + 队列静默；不为此增加轮询。

> 实现上用 Spring `TaskScheduler` 在活动创建/结束时注册一次性任务，重启时补跑；不需要额外的表或 Key。

**静默期动作**：

1. 对「Redis 已预占、DB 无订单」的用户，只做**重投补建订单**：`HSCAN` 现有 `bought` Hash，筛出 `bought > 0` 且在该活动下无任何订单的 userId，用 `userId + activityId` 重建消息；重复消息由 `uk_user_activity` 吸收；
2. **库存回补不自动执行**——误回补会导致超卖，只告警/人工处理；
3. 活动结束、队列排空后：以 DB 为准重建 Redis，`redisStock = dbStock`，`bought` 按**全部订单（含已关闭）**的 userId 重建；
4. 最后一笔订单创建后 35 分钟再跑一次兜底重建，修复关单补偿的漂移。

> 本节不新增表或 Redis Key：只用现有 `stock`、`bought`、订单表、队列指标和活动结束时间。

**超时关单**：延迟消息为主；定时扫描（创建 > 35 分钟仍待支付）兜底，CAS 关单 + 回补。

> **演进方向（工程完善后再做）**：请求级账本（pending ZSet + 每请求状态 + W1/W2/W3 水位 + CAS 释放）、Outbox 等生产级方案，见 `docs/00-开发进度.md` 的「演进待办（初版完成后）」。MVP 不实现。
>
> **为什么保留对账**：秒杀跨越 Redis、MQ、MySQL，任何"消息不丢"都只是概率保证；对账是最终一致性的最后一道防线。

#### 6.7.9 安全加固

| 风险 | 防护 |
|---|---|
| 脚本刷单 | 抢购接口按用户小时额度限流；库存 / 限购由 Lua 原子校验 |
| 提前抢购 | 严格校验服务端时间，活动未开始直接拒绝（**不依赖前端倒计时**） |
| 越权 | userId 从 JWT 取，**绝不从请求参数取** |
| 活动 ID 遍历 | 布隆过滤器 + 参数校验 |
| 恶意重复提交 | 幂等标记（6.3） |

#### 6.7.10 MQ 声明与可靠性（S-18）

| 项 | 约定 |
|---|---|
| Exchange / Queue | 订单、AI、搜索、点赞队列全部 `durable=true`；交换机与队列在应用启动时声明，参数变更需新建队列而不是改旧队列 |
| 消息 | `deliveryMode=PERSISTENT`；订单消息必须持久化 |
| 消费 | 手动 ACK（`acknowledge-mode=manual`）；业务成功后才 ACK，异常 NACK 且不重回队列（进重试 / DLQ） |
| 预取 | `prefetch=10~20`，按消费耗时调；秒杀订单消费者并发 5–10 |
| 重试 | 重试交换机 + 重试队列（TTL 递增：5s / 30s / 2min），3 次后进 DLQ 并告警 |
| DLQ | 每个业务队列配独立 DLQ；监控 `messages_ready` / `messages_unacknowledged` / DLQ 堆积 |
| 延迟插件 | 启动时检查 `rabbitmq_delayed_message_exchange` 是否存在；缺失则**启动失败**并打印安装方法，不允许静默降级 |
| 连接隔离 | 秒杀发送连接与普通业务连接分离；连接工厂设置合理的 `connection-timeout` / `channel-rpc-timeout`，避免 Broker 慢拖住全部线程 |

> 单节点 MVP 用 classic durable queue；演进到多节点 / 高可用时再评估 quorum queue。消息可靠性是“至少一次”，消费端幂等仍是最终保障。

### 6.8 弹幕方案

#### 6.8.1 目标与范围

| 项 | MVP 口径 |
|---|---|
| 需求 | F-14 弹幕（P0），G-3 端到端延迟 < 200 ms |
| 房间 | `post:{postId}` 或 `activity:{activityId}`；房间 ID 带类型前缀，避免 ID 撞号 |

| 部署 | **单实例本地广播**；多实例广播列为演进 |
| 内容安全 | MVP 只做长度限制 + 纯文本存储（前端 `textContent` 渲染，不拼 HTML）；**敏感词过滤不做，列为演进** |

#### 6.8.2 连接与鉴权

| 项 | 方案 |
|---|---|
| 协议 | WebSocket（Spring WebSocket + 原生 `WebSocketHandler`，不引入 STOMP/SockJS） |
| 端点 | `/ws/danmaku?roomId=post:123&token={jwt}` |

| 会话注册 | 本机 `ConcurrentHashMap<roomId, Set<WebSocketSession>>`；连接建立后注册，关闭后移除 |
| 历史回放 | 注册成功后推送最近 50 条（`HISTORY` 帧），客户端按 `messageId` 去重 |
| 在线人数 | 可选；本机房间 Map 的 size；多实例演进用 Redis ZSet |
| 心跳 | 应用层 `PING` / `PONG`，30 s 一次；连续 2 次无响应关闭连接 |
| 重连 | 客户端指数退避；重连成功后重新拉取历史 |
| 连接限制 | 单用户 ≤ 3 条、单房间上限、总连接上限；超限拒绝并关闭 |

> token 放 query 便于演示，但可能被日志/代理记录；演进改为一次性 WS ticket。
> 长连接建立后不再重复校验 JWT；token 过期时可主动关闭连接，MVP 可接受连接期间不校验。

#### 6.8.3 消息协议与处理链路

客户端发送：

```json
{"type":"SEND","clientMsgId":"...","content":"..."}
```

服务端处理：

```text
客户端 ──SEND──► 服务端
                  ├─ ① 长度限制（≤ 50 个 Unicode code point）
                  ├─ ② 纯文本校验：拒绝/剥离 HTML 标签，内容按原文存储，前端 textContent 渲染
                  ├─ ③ 组装消息（messageId / userId / nickname / content / ts）
                  ├─ ④ 写历史 List（LPUSH + LTRIM 0 199 + EXPIRE 24h）
                  ├─ ⑤ 广播给房间内所有本地会话（快照遍历）
                  └─ ⑥ 多实例时发布到 Redis Pub/Sub（MVP 不启用）
```

服务端下发：

```json
{"type":"DANMAKU","messageId":"...","roomId":"post:123","userId":1,"nickname":"...","content":"...","ts":1730000000000}
{"type":"HISTORY","items":[...]}
{"type":"ERROR","code":"CONTENT_TOO_LONG","message":"弹幕内容不能超过 50 个字符"}
```

`nickname` 在连接建立时从用户缓存取一次，不逐条查 DB。

**失败策略**：
- Redis 写历史失败：记录日志，继续广播（历史降级）；
- 单个 session 发送失败：关闭并移除该 session，不影响其他会话；
- 长度校验失败：返回 `ERROR` 帧，不关闭连接。

#### 6.8.4 广播与多实例

**MVP**：本机内存广播，延迟 < 10 ms；G-3 的关键是**不同步落库**。

**演进**：多实例部署时，各实例订阅 Redis Pub/Sub 频道 `glimmer:ws:broadcast`，发布消息携带 `roomId`，各实例只广播给本机该房间的 session。

| 方案 | 取舍 |
|---|---|
| **Redis Pub/Sub** ✅ | 低延迟、Redis 已在栈内、无需为每实例建队列；fire-and-forget，节点短暂断订阅会漏消息，弹幕允许丢 |
| MQ Fanout | 更可靠，但需为每实例维护队列/交换机，延迟与复杂度更高；更适合点赞、订单等可靠事件 |
| sticky session | 实现简单，但实例故障/扩容时房间迁移麻烦，不推荐 |

#### 6.8.5 历史与 Redis Key

| Key | 类型 | 用途 | TTL |
|---|---|---|---|
| `glimmer:ws:history:{roomId}` | List | 最近弹幕（最多 200 条） | 24 h |

- 写入：`LPUSH` + `LTRIM 0 199` + `EXPIRE 24h`；
- 读取：`LRANGE 0 49`，返回前反转成时间正序；
- **MVP 不维护 Redis 在线会话 Set**：本机 Map 即可；多实例在线人数演进用 ZSet（member=sessionId，score=最后心跳），定期清理。

#### 6.8.6 边界与兜底

| 问题 | 处理 |
|---|---|
| 慢客户端阻塞广播 | `ConcurrentWebSocketSessionDecorator(session, sendTimeLimit, bufferSizeLimit)`；发送超时/缓冲溢出直接关闭 |
| 广播时集合增删 | 先复制 session 快照，再遍历 |
| 重连/历史重复 | 客户端按 `messageId` 去重 |
| 多实例消息乱序 | 以服务端 `ts` 为准；弹幕允许轻微乱序，不引入全局序号 |
| 单房间热点 | 可选房间级每秒消息上限；超限丢弃并告警，保护广播线程 |
| 连接数过多 | 单用户/单房间/总连接数上限 |
| Redis 故障 | 历史降级，广播继续；不因历史写失败拒绝消息 |
| 敏感词 | **MVP 不做**；后续用 DFA/Trie 词库补上，列入演进 |
| 内容审核/举报 | 不在 MVP；列为演进 |

#### 6.8.7 MVP 与演进

**MVP**：单机本地广播 + Redis List 历史 + 长度限制 + 纯文本存储 + 心跳/重连 + 慢客户端保护；不落库、不做敏感词、不做多实例。

**演进**：
1. 多实例广播：Redis Pub/Sub（首选）或 MQ Fanout；
2. 在线人数：Redis ZSet（score=最后心跳）；
3. 内容安全：DFA/Trie 敏感词、举报/屏蔽、管理端删除；
4. 鉴权：一次性 WS ticket；
5. 审计/回放：异步落库或 Redis Stream。

### 6.9 AI 能力接入方案

#### 6.9.1 核心原则

> **本节的异步批处理 AI 绝不在主链路上同步执行。** 发帖、发评论的响应时间不受 LLM 影响（LLM 首字延迟可达秒级，与 G-1 的 200ms 指标相差两个数量级）。

> 📌 **项目中有两种 AI 集成范式，须区分对待**：
>
> | 范式 | 场景 | 用户是否等待 | 方案 |
> |---|---|---|---|
> | **异步批处理** | 打标签、情感分析 | 否（异步） | **本节 6.9** |
> | **实时流式** | 帖子 AI 助手（F-31） | **是**（主动等待） | **6.11** |
>
> 两者**必须使用独立线程池与独立通道**，AI 助手的慢调用不得阻塞发帖链路，反之亦然。

#### 6.9.2 帖子自动打标签（F-23）

```
发帖成功（事务提交后）
   │
   ▼
发送 MQ 消息 → 独立队列 glimmer.ai.tag（与秒杀、点赞队列隔离，互不阻塞）
   │
   ▼
消费者调用 DeepSeek API：
  Prompt（限定候选标签集，禁止自由发挥）：
    你是内容分类助手。请从以下标签中选择 1-3 个最贴合的：
    [美食, 穿搭, 旅行, 美妆, 数码, 运动, 读书, 宠物, 家居, 摄影]
    标题：{title}
    正文：{content 截断至 500 字}
    仅输出 JSON 数组，如 ["美食","旅行"]
   │
   ▼
解析 JSON → 校验（必须在候选集内）→ 调用 content 的 Service（如 ContentService.replaceAiTags）
   │                                 写入 t_post_tag；ai 不注入 PostTagMapper
   ├─ content 校验帖子存在且未删除，已删除则丢弃结果
   ├─ 帖子已发布 → 发送 SEARCH_UPSERT（标签参与搜索，见 6.12）
   │
   ▼
失败降级：关键词规则匹配（本地词库）→ 保证功能永远有输出
```

#### 6.9.3 评论情感分析（F-24）

```
评论发布 → MQ → 消费者调用 LLM → 返回 正面/中性/负面
         → 写入 t_comment.sentiment（1 / 0 / -1）
         → 管理端按帖子/时间聚合展示（F-30 预留）
```

#### 6.9.4 工程要点（面试重点）

| 要点 | 方案 | 理由 |
|---|---|---|
| **超时** | 连接 3s / 读取 5s | LLM 慢是常态，不能无限等 |
| **重试** | 最多 1 次，指数退避 | 重试过多会自己打自己 |
| **降级** | 打标签 → 关键词规则；情感 → 标记为"未分析" | **功能可用性优先于 AI 准确性** |
| **限流** | 本地令牌桶限制 QPS（如 5 QPS） | 成本控制 + 防被供应商限流 |
| **成本** | 输入截断（正文 ≤ 500 字）；相同内容哈希结果缓存 24h | 直接省钱 |
| **Prompt 版本化** | 代码中维护 `PROMPT_VERSION`，随结果落库 | 效果变差时可定位是否 Prompt 变更导致 |
| **密钥管理** | `DEEPSEEK_API_KEY` 走环境变量，**绝不入库、绝不提交 Git** | 安全红线 |
| **结构化输出** | 使用 JSON 输出模式 + 严格解析校验 | 防止模型自由发挥污染数据 |
| **队列隔离** | AI 队列独立，与秒杀/点赞队列分离 | 一批 AI 慢调用不能拖垮核心链路 |

#### 6.9.5 降级策略总表

| 依赖 | 故障 | 降级行为 | 用户感知 |
|---|---|---|---|
| DeepSeek API | 超时 / 报错 / 限流 | 打标签走关键词规则；情感分析跳过 | 标签质量下降，功能可用 |
| 阿里云 OSS | 上传失败 | 提示重试（**无降级，图片是必需数据**） | 明确报错 |
| Redis | 不可用 | 读穿到 DB + 限流放宽（**需谨慎，防雪崩**） | 变慢，不报错 |
| RabbitMQ | 不可用 | 秒杀返回"系统繁忙"；点赞/标签降级为同步或丢弃 | 秒杀不可用 |

### 6.10 鉴权与安全方案

#### 6.10.1 JWT 登录态

```
登录成功 → 生成 JWT（HS256）
  Payload: { userId, role, iat, exp: 7d }
  同时写 Redis：glimmer:user:token:{userId} = token  (TTL 7d)

请求携带：Authorization: Bearer <token>
  │
  ▼
AuthInterceptor：
  ① 读 Authorization；无 Token 标记为匿名
  ② 有 Token 则解析 JWT（签名 + 过期）并比对 Redis；失败标记为匿名并记录原因
  ③ Token 合法 → 注入 userId / role 到 ThreadLocal（UserContext）
  ④ 命中白名单（方法 + 路径）→ 放行；匿名访问白名单接口即游客
  ⑤ 未命中白名单：匿名 / 非法 Token → 40101，过期 → 40102
  ⑥ /api/v1/admin/** → 登录后再校验 role=ADMIN，否则 40303
```

**Payload 只放四类信息**：

| 字段 | 作用 | 为什么放在 Token 里 |
|---|---|---|
| `userId` | 当前用户 ID | 每个请求都要用；作为唯一可信身份来源，禁止从请求参数取 `userId` |
| `role` | `USER` / `ADMIN` | 管理端前缀校验需要；避免每次请求查权限表 |
| `iat` | 签发时间 | 标准声明，便于排查问题与计算 Token 年龄 |
| `exp` | 过期时间（7 天） | 服务端校验有效期；MVP 不做 Refresh Token |

> JWT 内部的 `iat` / `exp` 按 JWT 标准使用 NumericDate（秒级时间戳）；对外 API 返回的时间仍是 epoch 毫秒，两者不要混用。

不放手机号、昵称、头像等资料：JWT 只签名不加密，Payload 可被 base64url 解码；这些字段可变且可能敏感，应放在用户缓存 / 数据库。也不放权限列表和 `jti`：MVP 只有两种角色，且 Redis 白名单已经能主动失效旧 Token。角色变更或封禁时必须删除 `glimmer:user:token:{userId}`，让旧 Token 立即失效。

> **登出与重新登录**：登出只删除 Redis 白名单中的当前会话，不修改 `t_user.status`；用户重新登录时按登录流程重新签发 JWT 并写入 `glimmer:user:token:{userId}`。单用户单 Token 下，新登录会覆盖旧值。

> **HS256 是签名，不是加密**：JWT 的 Payload 只做 base64url 编码，可被解码查看；HS256 用共享密钥计算 HMAC，保证内容未被篡改，但不提供机密性。当前 Payload 不含敏感信息，因此不需要 JWE；若未来要隐藏载荷，应改用 JWE 或不透明 Token + Redis 会话。
>
> **`exp` 与 Redis TTL 的分工**：`exp` 是签名保护的 Token 硬过期时间，本地即可校验；Redis TTL 是会话记录的缓存生命周期，用于登出 / 封禁 / 单端登录的主动失效。Redis 可能被淘汰、重启或误设 TTL，不能作为唯一的安全过期依据；两者同时存在，才能兼顾「到期即失效」与「提前撤销」。
>
> 这里的「TTL 7d」指 **Redis Key 的过期时间**，不是 JWT 字段：JWT 本身没有 `ttl`，只用标准 `iat`（签发）和 `exp`（过期）。登录时两者按同一个 7 天配置写入；实现时 Redis TTL 建议略长于 `exp`（如 +5 分钟），避免 Redis 先过期。

#### 6.10.2 免登录接口白名单（对应 PRD 3 的"游客"角色）

```
POST /api/v1/auth/sms-code     发送验证码
POST /api/v1/auth/login        登录 / 自动注册
GET  /api/v1/posts             帖子列表
GET  /api/v1/posts/{postId}    帖子详情
GET  /api/v1/posts/{postId}/comments 评论列表
GET  /api/v1/comments/{commentId}/replies 回复列表
GET  /api/v1/feed/hot          热榜
GET  /api/v1/feed/recommended  推荐流
GET  /api/v1/search/posts      搜索
GET  /api/v1/seckill/activities 秒杀活动列表
GET  /api/v1/seckill/activities/{activityId} 秒杀活动详情
GET  /api/v1/users/{userId}    公开用户主页
GET  /api/v1/users/{userId}/posts 用户公开帖子
GET  /api/v1/users/{userId}/followers 粉丝列表
GET  /api/v1/users/{userId}/following 关注列表
GET  /api/v1/tags              标签列表
GET  /api/v1/tags/hot          热门标签
GET  /uploads/**               本地 profile 静态图片
```

> 其余接口默认**需要登录**（白名单模式，而非黑名单），避免新增接口忘记加鉴权。
>
> - 白名单是**唯一**的免登录配置，按「方法 + 路径」精确匹配，放在拦截器配置或 `glimmer.security.public-endpoints` 配置项中；**不给 Controller 加 `@RequireLogin` / `@RequireRole` 注解**。
> - 白名单接口允许携带 Token：合法则注入 `UserContext`（用于 `liked` / `collected` / `isFollowing` 等个性化字段），无 Token 或 Token 失效则按游客处理。
> - `/api/v1/admin/**` 统一在拦截器里校验 `ADMIN`，与白名单互斥。
> - 新增接口默认需要登录；忘记加白名单只会让公开接口暂时返回 401（fail-closed），不会意外公开数据。
> - CORS 预检 `OPTIONS` 直接放行；`/uploads/**` 静态资源不进入 API 拦截器。

白名单只维护这一处，配置形态示意：

```yaml
glimmer:
  security:
    public-endpoints:          # 仅此处列出的「方法 + 路径」免登录
      - "POST /api/v1/auth/sms-code"
      - "POST /api/v1/auth/login"
      - "GET /api/v1/posts"
      - "GET /api/v1/posts/{postId}"
      # ... 其余见 04 §1.3.3
```

#### 6.10.3 限流

**只对关键链路限流**：

| 场景 | 维度 | 阈值 | 目的 |
|---|---|---|---|
| 验证码 | 手机号 | 5 次/小时 | 防短信轰炸与费用 |
| 登录 | 手机号 | 10 次/小时 | 防撞库 |
| 抢购 | 用户 | 10 次/小时 | 防脚本刷单 |
| AI 提问 | 用户 | 20 次/小时；同时 1 条流 | 控 LLM 成本与线程池 |

> 其他接口不单独限流：发帖、评论、点赞、收藏、关注、上传、搜索、支付、弹幕等依赖登录校验、唯一约束、幂等、分页、长度限制与数据库容量。正常用户流量远低于需要限流的量级，逐接口加限流只会增加维护成本，还可能误伤正常业务流程。
>
> 抢购的活动总量由库存 + 限购控制，不再额外做活动级限流，避免正常用户被全局限流挡住。

**实现**：不逐接口加注解。只在上述关键用例的 Service 入口显式调用 `RateLimiter.check(Action, key)`，底层统一走 Redis Lua 滑动窗口；阈值全部走配置。**不引入 IP 维度**；公网部署如需流量兜底，在 Nginx 层配置 `limit_req` / `limit_conn`，不进入业务代码。

```lua
-- 滑动窗口限流（简化）
local key = KEYS[1]
local now = tonumber(ARGV[1])
local window = tonumber(ARGV[2])
local limit = tonumber(ARGV[3])
local member = ARGV[4]   -- 由应用传入 UUID，不能用 math.random
redis.call('ZREMRANGEBYSCORE', key, 0, now - window)
local count = redis.call('ZCARD', key)
if count >= limit then return 0 end
redis.call('ZADD', key, now, member)
redis.call('EXPIRE', key, window + 1)
return 1
```

> `member` 必须是应用生成的 UUID（或“请求 ID + 随机数”），否则同一毫秒内并发请求可能碰撞，导致 ZSet 去重、限流计数偏少。单实例 MVP 用应用时间；多实例阶段用 Redis `TIME` 或严格 NTP。

#### 6.10.4 其他安全措施

| 风险 | 防护 |
|---|---|
| **越权（水平）** | 所有涉及用户自身资源的操作，userId **一律从 JWT 取**，禁止从请求参数取 —— **本项目最重要的一条安全红线** |
| **越权（垂直）** | 管理端接口统一 `/api/v1/admin/**` 前缀，由全局拦截器校验 `role=ADMIN`；不依赖 Controller 注解 |
| SQL 注入 | MyBatis 全部使用 `#{}` 参数绑定；**禁止 `${}` 拼接**（`ORDER BY` 等动态字段需白名单校验） |
| XSS | MVP 帖子 / 评论 / 弹幕按**纯文本 + 换行 + 图片 URL**处理：入库保留原文，后端 JSON 不拼 HTML，前端用 `textContent` 渲染；若未来支持富文本，入库前用 Jsoup `Safelist` 白名单清洗；响应加 CSP 作为第二道防线。**不做入库前统一 HTML 转义**（会双重转义且无法还原） |
| 验证码爆破 | 单手机号 5 次/小时；验证码 5 分钟过期；验证成功立即删除 |
| 敏感信息泄露 | 响应 DTO 不含手机号全量、密码等；日志脱敏 |
| 上传安全 | 类型白名单（jpg/png/webp）、大小 ≤ 5MB；OSS 签名限定 `posts/{userId}/{uuid}.{ext}` 前缀与 `content-length-range`；后端校验 URL 的 host / bucket / prefix 属于配置，拒绝任意外链 |
| CORS | 按 profile 配置允许的前端 Origin；只允许 `Authorization` / `Content-Type` 等必要头；`allowCredentials=false`（Bearer Token）；非白名单 Origin 拒绝 |
| 密钥泄露 | 所有 Key 走环境变量；`.gitignore` 排除配置文件 |

### 6.11 AI 流式对话方案（帖子 AI 助手）★

> 对应 PRD F-31 / US-12 / 规则 6.8。**引入项目中的第二种 AI 集成范式：实时流式。**

#### 6.11.1 与 6.9 的本质区别

| 维度 | 6.9 异步批处理 | 6.11 实时流式 |
|---|---|---|
| 场景 | 打标签、情感分析 | 帖子 AI 助手 |
| 触发 | 发帖/评论后自动触发 | 用户主动提问、**同步等待** |
| 传输 | MQ → 消费者 | **SSE 逐片段推送** |
| 延迟要求 | 分钟级可接受 | **首 Token < 2s（G-8）** |
| 失败处理 | 规则降级（保证有输出） | **明确报错，不假回复** |
| 线程来源 | MQ 消费线程池 | **独立流式线程池** |

> **失败策略为什么相反**：打标签是"后台补全"，降级出个粗略标签比没有好；AI 对话是"用户当面提问"，用规则假回复会让用户困惑，**明确报错反而更诚实**。

#### 6.11.2 传输实现：POST + fetch 消费 SSE

**决策：响应格式用 SSE，但消费方式不用原生 `EventSource`。**

| 实现方式 | 问题 | 结论 |
|---|---|---|
| **`POST` + `fetch` 读取 `ReadableStream`** ✅ | — | **采用** |
| 原生 `EventSource` | 仅支持 GET → 问题须塞进 URL（长度受限、需编码）；**且自带自动重连** | ❌ |

> ⚠️ **SSE 用于生成式场景时最反直觉的一点**：
>
> `EventSource` 的自动重连在普通推送场景是优点；但在 LLM 场景下，连接断开后自动重连 = **让模型重新生成一遍** = 内容重复 + **重复计费**。它是故障放大器，不是可靠性保障。
>
> 因此**主动放弃 `EventSource`，用 `fetch` + `ReadableStream` 手动消费 SSE 帧**（这也是 OpenAI / Anthropic 官方 API 的推荐用法）。

**SSE 事件设计**：

| event | data | 用途 |
|---|---|---|
| `start` | `{"sessionId":"..."}` | 流建立 |
| （默认 message） | `{"delta":"..."}` | 内容片段，逐 token |
| `done` | `{"finishReason":"stop","elapsedMs":3200}` | 正常结束 |
| `error` | `{"code":"AI_UNAVAILABLE","message":"..."}` | 异常结束 |

#### 6.11.3 接口时序

```
① 创建会话
   POST /api/v1/ai/chat/session   { postId }
   → { sessionId }                      初始化 Redis 上下文，绑定 userId + postId

② 提问并流式接收
   POST /api/v1/ai/chat/stream    { sessionId, question }
   Content-Type: text/event-stream
   ← event: start   data: {"sessionId":"..."}
   ← data: {"delta":"这"}
   ← data: {"delta":"篇帖子"}
   ← ...
   ← event: done    data: {"finishReason":"stop","elapsedMs":3200}

③ 中断（用户点停止）
   前端 AbortController.abort() → 连接关闭 → 后端取消上游调用（见 6.11.6）
```

#### 6.11.4 后端实现：Spring MVC + `SseEmitter`

| 方案 | 取舍 |
|---|---|
| **Spring MVC + `SseEmitter`** ✅ | 基于 Servlet 异步（AsyncContext），**业务处理完立即释放 Tomcat 线程**；与现有阻塞式 MyBatis-Plus 栈天然兼容 |
| Spring WebFlux + `Flux` | 全响应式栈；但项目用阻塞式 ORM，混用会导致**阻塞调用跑在事件循环线程上**（严重事故）；为单个功能引入整套栈不划算 |
| `StreamingResponseBody` | 适合大文件下载；SSE 的事件分帧需手写 |

**线程模型（本节最容易被误解的一点）**：

```
Tomcat 请求线程 ──► 业务处理 ──► 返回 SseEmitter ──► 【线程归还线程池】
                                        │
                                   提交任务到
                                        ▼
                      【AI 流式线程池】固定 20 线程
                                        │
                        阻塞读取 DeepSeek 的 SSE 流
                                        │
                              emitter.send(delta) × N
```

- **Tomcat 线程不长期占用** → 并发连接数不受 Tomcat 线程池限制；
- **真正的占用点是 AI 流式线程池** → 固定大小，**它本身就是全局限流器**；
- **池满策略：快速失败**（返回 `event: error`「当前咨询人数较多」），而非无限排队——排队会让用户等到超时。

#### 6.11.5 上游调用（DeepSeek 流式）

```java
// JDK 11+ 内置 HttpClient，无需额外依赖
HttpRequest req = HttpRequest.newBuilder()
    .uri(URI.create("https://api.deepseek.com/chat/completions"))
    .header("Authorization", "Bearer " + apiKey)
    .POST(BodyPublishers.ofString(jsonBody))   // body 中 stream: true
    .build();

HttpResponse<Stream<String>> resp = httpClient.send(req, BodyHandlers.ofLines());
// 逐行：data: {"choices":[{"delta":{"content":"..."}}]}
// 识别结束标记：data: [DONE]
```

**注意点**：

1. 上游 SSE 以 `data: [DONE]` 结束，须识别为终止信号；
2. 上游可能返回**空行、心跳、非 JSON 片段**，解析必须容错（否则一个异常就断流）；
3. **不使用带自动重试的 HTTP 客户端** —— 流式中途重试会生成重复内容。

#### 6.11.6 中断传播（本方案最关键的一环）★

**问题**：用户点停止 → 前端 abort → 连接关闭。但后端若只感知到"写不进去了"，**上游 LLM 仍在继续生成**：线程被占用到生成结束，token 照常计费。

**方案**：

```
1. 保存上游响应流引用（Stream<String> / Closeable）

2. 注册 SseEmitter 生命周期回调：
     emitter.onCompletion(() -> cancelUpstream())   // 正常完成 / 客户端断开
     emitter.onTimeout   (() -> cancelUpstream())   // 超时
     emitter.onError    (e  -> cancelUpstream())    // 异常

3. cancelUpstream()：
     ├─ 关闭上游 Stream（触发底层连接中断，停止计费）
     ├─ 中断读取线程（Future.cancel(true)）
     ├─ 释放线程池配额
     └─ 记录「中断率」指标（用于观察体验与成本）
```

> **面试价值点**：这是"调通 API"与"工程实现"的分水岭。能说清"用户中断如何一路传播到上游、如何避免线程泄漏与费用浪费"，是这个功能真正的技术含量所在。

#### 6.11.7 会话上下文管理（Redis，不落库）

**上下文结构**（`glimmer:ai:chat:{sessionId}`，String(JSON)）：

```json
{
  "sessionId": "uuid",
  "userId": 10086,
  "postId": 20001,
  "createdAt": 1760000000000,
  "messages": [
    { "role": "user", "content": "..." },
    { "role": "assistant", "content": "..." }
  ]
}
```

**Prompt 组装**：

```
System（每次请求都携带）：
  你是「微光」社区的内容助手，正在与用户讨论下面这篇帖子。
  回答须基于帖子内容，友好简洁，不超过 200 字；
  若问题与帖子无关，礼貌引导回帖子内容。

  【标题】{title}
  【正文】{content，截断至 1000 字}
  【标签】{tags}

+ messages（裁剪后的历史）
+ 本轮 user 问题
```

**Token 预算**：

| 部分 | 估算 |
|---|---|
| System + 帖子内容 | ~800 tokens |
| 每轮问答 | ~200 tokens |
| 保留轮数上限 10 轮 | ~2000 tokens |
| **合计** | **~3000 tokens** |

远低于 DeepSeek 的上下文窗口，**无需摘要压缩**（对比 6.9 无需考虑上下文，更简单）。裁剪策略：超过 10 轮则从最早的消息开始丢弃（System Prompt 与帖子内容始终保留）。

**输入侧硬限制**：帖子正文截断 1000 字、用户问题 ≤ 500 字、单会话 ≤ 20 轮。

**为什么不落库（见 ADR-014）**：

| 维度 | 分析 |
|---|---|
| 产品价值 | 帖子 AI 咨询是**即时性需求**，峰值在浏览帖子当下；历史回看价值低 |
| 成本 | 落库需新增会话表 + 消息表 + 归档清理任务 + 分页接口 |
| 结论 | **有意的范围裁剪**，上下文仅存 Redis，30 分钟滑动过期 |
| 代价 | 无"历史会话"列表；Redis 故障时会话丢失（可接受——重新提问即可） |

#### 6.11.8 限流与成本控制

| 维度 | 限制 | 目的 |
|---|---|---|
| 单用户并发流 | ≤ 1 | 防多开标签页刷 |
| 单用户提问频率 | ≤ 20 次/小时 | 控成本；正常问答不会触发 |
| 单会话轮数 | ≤ 20 轮 | 控制上下文与成本 |
| **AI 并发流** | **固定 20 线程** | **全局限流**（池满快速失败） |
| 会话 TTL | 30 分钟滑动 | 释放 Redis 内存 |
| 输入截断 | 正文 1000 字 / 问题 500 字 | 直接控制 token 成本 |

**口径统一（P1-14）**：2.2 的“AI 流式峰值并发会话 ~50”指 `concurrent_sessions`（同时在线、可能正在阅读或输入），不是 `concurrent_streams`（同时向上游发起生成）。MVP 按 **20 条并发流**设计；第 21 条快速失败并提示“当前咨询人数较多”。50 个在线会话不会同时触发生成，20 条流是成本与体验的折中；压测时记录拒绝率、TTFT 与平均流时长，再决定是否调到 32。

#### 6.11.9 安全

| 风险 | 防护 |
|---|---|
| **会话越权（横向）** | `sessionId` 必须校验归属 `userId`；且**会话与 postId 绑定**，不可跨帖子复用 |
| Prompt 注入 | System Prompt 明确角色边界；输出侧做敏感词与合规校验（可选用 LLM 二次校验，MVP 不做） |
| 敏感内容 | 用户输入与模型输出**双向**过敏感词（独立 DFA/Trie 词库；弹幕敏感词列为演进，暂不复用） |
| 成本攻击 | 见 6.11.8 |
| 密钥泄露 | `DEEPSEEK_API_KEY` 走环境变量（同 6.9.4） |

#### 6.11.10 部署与配置注意

| 项 | 配置 | 遗漏后果 |
|---|---|---|
| **反向代理缓冲** | Nginx：`proxy_buffering off;` + 响应头 `X-Accel-Buffering: no` | 流被缓冲成一次性返回，**流式效果完全失效** |
| 异步请求超时 | `spring.mvc.async.request-timeout=120s` | 默认约 30s，长回答被截断 |
| Tomcat 连接超时 | 适当调长 | 长连接被提前关闭 |

> 这三个配置**在本地直连时都不会暴露问题**，只有上了 Nginx 才会显现——属于典型的"演示环境正常、生产环境失效"陷阱，必须提前写入部署清单。

#### 6.11.11 部分失败处理

| 情况 | 处理 |
|---|---|
| 流中途上游/网络中断 | 发送 `event: error`；**已生成内容不写入上下文**；前端保留已显示内容并提示"生成中断" |
| 用户主动中断 | 同 6.11.6；**已生成内容不写入上下文** |
| Redis 上下文丢失 | 视为新会话（不报错），只带 System Prompt 继续 |
| 上游返回空内容 | 视为失败，`event: error`，不写入上下文 |

> **设计取舍**：中断的回复一律不进入上下文。理由是半截回复作为历史会让模型误判"上次已答完"，导致后续对话错乱。代价是模型"忘记"上次说到一半——在本场景下可接受。

### 6.12 搜索方案（F-08）

> **定位**：MySQL 是帖子真相源，Elasticsearch 是**派生索引**。ES 只负责召回与排序，展示字段回表补全。

#### 6.12.1 为什么不用 MySQL 全文索引

| 方案 | 问题 |
|---|---|
| `LIKE '%关键词%'` | 用不上 B+Tree，1000 万帖子全表扫 |
| `FULLTEXT ... WITH PARSER ngram` | 中文分词与相关度弱；全文索引无法与 `status + is_deleted` 组合成理想索引 |
| **Elasticsearch + IK** ✅ | 中文分词、BM25 相关度、多字段召回、标签过滤、高亮、`search_after` 深分页 |

**取舍**：多一个 ES 容器、IK 插件与同步/重建链路；换来检索质量与后续向量检索的复用能力（ADR-017）。

#### 6.12.2 索引结构

**别名**：`glimmer_post` → 物理索引 `glimmer_post_v1`。重建时新建 `v2`，数据补齐后原子切换别名。

| 字段 | 类型 | 说明 |
|---|---|---|
| `postId` | `long` | 主键，回表依据 |
| `userId` | `long` | 作者 ID，不在 ES 存昵称 |
| `title` | `text` + `keyword` 子字段 | IK 分词，`title^3` |
| `content` | `text` | IK 分词，用于召回与高亮 |
| `tagIds` | `long[]` | 标签精确过滤 |
| `tagNames` | `keyword` + `text` 子字段 | 标签名召回 |
| `publishedAt` | `date` | 排序与时间衰减 |
| `status` | `byte` | 兜底过滤，正常文档恒为 1 |
| `updatedAt` | `date` | 诊断与增量核对 |

**不存入 ES 的字段**：点赞数、评论数、收藏数、浏览量、封面、作者昵称、头像。这些字段变化频繁或展示属性强，统一在命中 `postId` 后批量回表 / 读 Redis 补全，避免 ES 写放大与数据不一致。

**Settings 要点**：单节点 MVP 用 `number_of_shards=1`、`number_of_replicas=0`（生产可调 1）；`refresh_interval=1s`；IK 自定义 analyzer：

```json
{
  "settings": {
    "number_of_shards": 1,
    "number_of_replicas": 0,
    "refresh_interval": "1s",
    "analysis": {
      "analyzer": {
        "post_index":  { "tokenizer": "ik_max_word", "filter": ["lowercase"] },
        "post_search": { "tokenizer": "ik_smart",    "filter": ["lowercase"] }
      }
    }
  },
  "mappings": {
    "properties": {
      "postId":      { "type": "long" },
      "userId":      { "type": "long" },
      "title":       { "type": "text", "analyzer": "post_index", "search_analyzer": "post_search",
                       "fields": { "keyword": { "type": "keyword", "ignore_above": 256 } } },
      "content":     { "type": "text", "analyzer": "post_index", "search_analyzer": "post_search" },
      "tagIds":      { "type": "long" },
      "tagNames":    { "type": "keyword",
                       "fields": { "text": { "type": "text", "analyzer": "post_index", "search_analyzer": "post_search" } } },
      "publishedAt": { "type": "date", "format": "epoch_millis" },
      "status":      { "type": "byte" },
      "updatedAt":   { "type": "date", "format": "epoch_millis" }
    }
  }
}
```

**可见性规则**：只索引公开可见的帖子，即 `status IN (0,1) AND is_deleted=0`；审核拒绝、下架、作者删除时直接删除文档。待审核帖子已公开，因此创建成功后就进入索引；审核拒绝后才移除。

#### 6.12.3 同步链路

**写入时机**（均在业务事务提交后发 MQ，不阻塞主链路）：

| 业务动作 | 事件 | 消费者行为 |
|---|---|---|
| 普通用户发帖（0 已发布待审核） | `SEARCH_UPSERT` | 回查 MySQL → `index` |
| 管理员发帖（1 已发布） | `SEARCH_UPSERT` | 回查 MySQL → `index` |
| 审核通过（0→1） | `SEARCH_UPSERT` | 回查 MySQL → `index`（更新状态字段，不改变可见性） |
| 审核拒绝（0→2） | `SEARCH_DELETE` | 回查 MySQL → `delete`（立即从搜索移除） |
| 下架（0/1→3） | `SEARCH_DELETE` | 回查 MySQL → `delete` |
| 恢复（3→1） | `SEARCH_UPSERT` | 回查 MySQL → `index` |
| 作者删除（`is_deleted=1`） | `SEARCH_DELETE` | 回查 MySQL → `delete` |
| AI 打标 / 标签变更 | `SEARCH_UPSERT` | 公开可见（0/1）才 `index`，否则 `delete` |
| 编辑（0/1/2→0，重新提交） | `SEARCH_UPSERT` | 回查 MySQL → `index`（原 1/2 立即重新公开） |

**消费者设计**：

```
收到事件（只取 postId，不信任事件里的标题 / 正文）
   │
   ├─ 查 MySQL t_post + t_post_tag
   │
   ├─ status IN (0,1) 且 is_deleted=0
   │     → 组装文档 → ES index（按 postId 覆盖）
   │
   └─ 其他状态
         → ES delete（文档不存在则忽略）
```

> **为什么不需要版本号**：消费者每次都回查 MySQL 当前状态，事件乱序或重复投递都会收敛到同一结果。这是「事件通知 + 状态回查」模式，比在消息里携带快照更抗乱序。

**MQ 与失败处理**：

- 独立队列 / routing key：`glimmer.search.post`，与点赞、AI、秒杀队列隔离；
- 消费失败：有限重试 + 死信队列 + 告警；不阻塞其他消息；
- 发送失败：记录指标并告警；由 6.12.5 的定时补偿兜底。

#### 6.12.4 查询链路

```
GET /api/v1/search/posts?keyword=露营&tagId=12&cursor=...&size=20
   │
   ▼
ES multi_match（title^3 / tagNames.text^2 / content）
   + filter(status IN (0,1)) [+ term(tagIds, tagId)]
   + highlight(title/content)
   + sort(_score desc, publishedAt desc)
   │
   ▼
拿到 postId 列表（及高亮片段）
   │
   ▼
MySQL / Redis 批量补全：
   t_post（过滤 is_deleted / status）+ t_user（昵称、头像）+ t_post_image（封面、计数走 Redis）
   │
   ▼
按 ES 返回顺序组装、返回游标
```

**分页**：

- 前 N 页（`from + size <= 200`）用 `from/size`；
- 更深分页用 `search_after`，游标为 `[_score, publishedAt, postId]`，避免深分页开销；
- `keyword` 为空时不做全文检索，直接返回热榜 / 最新公开帖子。

**降级**：

- ES 超时 / 不可用：搜索接口返回热榜或最新帖子，并在响应中标记 `degraded=true`；记录告警；
- 搜索是 P1，降级不影响发帖、Feed、详情、秒杀。

#### 6.12.5 一致性与补偿

| 机制 | 做法 |
|---|---|
| 正常同步 | 事务提交后发 MQ，消费者回查 MySQL；正常延迟秒级 |
| 增量补偿 | 每 5 分钟扫描 `t_post.updated_at >= now-10min` 与 `t_post_tag.created_at >= now-10min` 的帖子，重新发 upsert / delete；10 分钟重叠窗口防漏 |
| 全量重建 | 管理端 / 运维脚本 scroll MySQL 已发布帖 → 写 `glimmer_post_v2` → 追平增量 → 原子切换别名 |
| 故障告警 | MQ 发送失败、消费死信、ES 写入失败、补偿任务失败均记录指标并告警 |

> **MVP 不引入 Outbox**：搜索索引是派生数据，允许分钟级不一致；「MQ + 定时补偿 + 全量重建」已能兜底。若后续要求更强的一致性，再评估 Outbox 或 Canal。

**重建期间的事件**：重建脚本先记录开始时间，全量写完后再扫一遍 `updated_at >= 开始时间` 的帖子追平，最后切换别名，避免重建窗口内的事件丢失。

#### 6.12.6 部署与配置

```yaml
# docker-compose.yml 片段
elasticsearch:
  image: docker.elastic.co/elasticsearch/elasticsearch:8.15.0
  environment:
    - discovery.type=single-node
    - ES_JAVA_OPTS=-Xms512m -Xmx512m
    - xpack.security.enabled=false      # 仅本地；生产启用 TLS + 认证
  ports:

  volumes:
    - es-data:/usr/share/elasticsearch/data

kibana:
  image: docker.elastic.co/kibana/kibana:8.15.0
  profiles: ["tools"]                   # 默认不启动：docker compose --profile tools up -d kibana
  environment:
    - ELASTICSEARCH_HOSTS=http://elasticsearch:9200
    - XPACK_SECURITY_ENABLED=false      # 仅本地；与 ES security=false 配套

```

- IK 插件版本必须与 ES 版本**完全一致**，在镜像构建时预装；版本不匹配会导致节点启动失败；
- 本地单节点 512MB heap 足够 MVP；生产按数据量调整；
- Java 客户端使用 Elasticsearch 8 Java API Client，禁止混用 7.x 的 `RestHighLevelClient`；

#### 6.12.7 边界

- 搜索只返回公开可见帖子；任何导致不可见的状态变化都必须同步删文档；
- 仅计数变化（点赞 / 评论 / 浏览）**不触发** ES 更新；
- 作者改昵称 / 头像**不触发** ES 更新（ES 不存这些字段）；
- 标签变化必须触发 upsert，否则新标签搜不到；
- ES 与 MySQL 不做分布式事务，接受最终一致；
- 全量重建必须走别名切换，不能直接删旧索引。

## 7. 非功能设计

### 7.1 性能

| 目标 | 手段 |
|---|---|
| G-1 Feed P95 < 200ms | Redis ZSet 读；游标分页；批量 MGET 取帖子摘要；**禁止 N+1 查询** |
| G-2 秒杀 QPS ≥ 1000 | 抢购路径全 Redis（无 DB 查询）；Lua 原子脚本；MQ 削峰；消费端并发可控 |
| G-3 弹幕 < 200ms | 内存内广播；不落库 |
| G-8 AI 首 Token < 2s | 流式输出（不等整段生成）；**System Prompt 尽量精简**（帖子截断至 1000 字）；上游直连不中转；线程池容量匹配（6.11.8） |
| G-9 搜索 P95 < 300ms | ES 多字段召回；只取 `postId` 后批量回表；`from/size` 上限 200，深分页用 `search_after` |
| 通用 | HikariCP 连接池调优；MyBatis 二级缓存**关闭**（用 Redis 统一管理）；慢 SQL 日志监控 |

**压测工具**：Apache JMeter 5.6.x，只负责负载 / 压力测试；接口功能与契约测试由 Apifox 负责。

| 场景 | 测试计划 |
|---|---|
| 秒杀抢购 | 5000 线程并发抢 1000 库存；CSV Data Set 提供 `userId` / `token` / `activityId`；断言返回 `202 QUEUED` |
| Feed / 搜索 | 按游标翻页、关键词集合持续加压，观察 P95 与错误率 |
| 登录 / 验证码 | 验证小时限流与 `42901` 是否符合配置 |
| WebSocket / SSE | 首轮不做 HTTP 压测；如后续需要，使用 JMeter 插件或独立客户端 |

压测环境与 Docker Compose 开发环境同构，结果写入 `05-测试报告.md`。

**秒杀验收标准**：
- 无超卖（成功订单数 == 1000）
- 无重复下单（每个 userId 至多 1 条订单）
- 接口 QPS ≥ 1000
- 错误率 < 1%

### 7.2 可用性与容错

| 故障 | 影响 | 应对 |
|---|---|---|
| **redis-core 宕机** | Token / 锁 / 库存 / 资格 / 布隆不可用；登录、鉴权、秒杀不可用 | 鉴权返回 `50301`（**不要返回 401**，避免把“服务故障”误判为“登录失效”）；秒杀快速失败；恢复后走 6.7.8 重建 |
| **redis-core 重启** | AOF 可能丢 1 秒；锁全部丢失 | 进行中活动置 `recovering`，暂停消费者，按 DB 重建 stock / bought，再恢复；锁丢失期间缓存重建可能重复，结果幂等 |
| **redis-cache 宕机** | 详情 / Feed / 点赞 / 关注 Set / AI / 弹幕历史 / 限流降级 | 详情直查 DB；Feed 回源重建；点赞计数以 DB 为准；AI 会话丢失（重新提问）；验证码 / 登录限流 **fail-closed**，抢购限流可暂时 fail-open（库存仍由 core 保护） |
| **MySQL 宕机** | 全站不可用 | 无解，只能靠运维（主从 + 故障转移，预留） |
| **RabbitMQ 宕机** | 秒杀、点赞异步、AI 异步、搜索补偿不可用 | 秒杀舱壁快速失败 `50301`；点赞可降级同步写 DB；搜索允许延迟 |
| **Elasticsearch 宕机** | 搜索不可用 | 返回 `degraded=true`，降级热榜 / 最新帖子；不影响发帖主链路 |
| **DeepSeek 不可用** | AI 功能不可用 | 关键词规则降级（6.9.5） |
| **OSS 不可用** | 无法发图 | 明确报错（图片为必需数据，不降级）；本地 profile 用本地存储 |

## 9. 微服务演进路径

### 9.1 拆分时机

**不预设时间，用信号触发**：

| 信号 | 说明 |
|---|---|
| 单体构建/启动时间 > 2 分钟 | 开发效率下降 |
| 某模块需要独立扩缩容（如 AI 服务被 LLM 限流拖慢） | 资源隔离需求 |
| 模块间出现资源竞争（AI 的慢调用影响秒杀） | 故障隔离需求 |
| 团队规模 > 5 人，并行开发冲突频繁 | 协作需求 |

> **原则：单体能解决的事，不要用微服务解决。** 拆分是有成本的，必须由问题驱动。

### 9.2 拆分顺序

按「**边界清晰度**」和「**事务耦合度**」排序，先拆**最独立**的：

| 顺序 | 服务 | 理由 |
|---|---|---|
| 1️⃣ | **ai** | 无 DB 事务、无强依赖、调用外部 API，可独立扩缩容，拆分成本最低 |
| 2️⃣ | **interaction** | 边界清晰，与 content 通过 postId 弱耦合 |
| 3️⃣ | **content** | 被依赖方，需先稳定 provider 接口 |
| 4️⃣ | **seckill** | 事务复杂但**本已与其他模块解耦**（3.5），且独立扩缩容价值最高 |
| 5️⃣ | **user** | 被所有服务依赖，最后拆 |

> **拆分时的改造点**：跨模块 Service 调用改为 HTTP / RPC；因为 Mapper 从未跨模块，数据归属不需要重新划分。这也是保留“Service 接口调用”而非“直接写表”的主要收益。

### 9.3 引入组件

| 阶段 | 组件 | 解决的问题 |
|---|---|---|
| 拆分起步 | Nacos（注册中心 + 配置中心） | 服务发现、配置集中管理 |
| 拆分起步 | Spring Cloud Gateway | 统一入口、鉴权前置、路由 |
| 服务间调用 | OpenFeign + LoadBalancer | 声明式调用 |
| 稳定性 | Sentinel | 限流、熔断、降级（替换自研限流） |
| 一致性 | Seata（或 Outbox + 补偿） | 跨服务事务；**优先选最终一致性方案，慎用 AT 模式** |
| 可观测 | SkyWalking | 链路追踪 |
| 部署 | Kubernetes | 编排、弹性伸缩 |

**演进过程中必须解决的三个新问题**：

1. **分布式事务**：秒杀从"单库事务"变为"跨服务调用"，需重新设计（优先 Saga / 本地消息表，而非 Seata AT）；
2. **布隆过滤器的一致性**：从进程内共享 Redis 变为每个服务各自持有，需统一维护或下沉为独立服务；
3. **弹幕多实例广播**：优先 Redis Pub/Sub，MQ Fanout 作为备选（6.8.4 已预留接口）。

| ADR-019 | 限流只做手机号 / 用户小时额度 | IP + 手机号双维度 + 全站 IP QPS | 简化实现，避免 NAT 误伤与 `X-Forwarded-For` 信任问题；MVP 为模拟短信，无真实短信费用 | 失去 IP 维度的批量防刷与全站兜底；公网部署需在 Nginx 补运维层限制 |
| ADR-020 | Kibana 作为 ES 开发辅助 | 仅用 curl / `_cat`；Cerebro | 官方工具，DSL 补全、索引管理、分词调试齐全；`tools` profile 默认不启动，不影响日常 | 多一个容器约 300–500MB 内存；版本必须与 ES 一致；仅限本地 |
| ADR-021 | 压测用 Apache JMeter | Gatling / k6 / wrk | 开源、脚本化、CSV 参数化与聚合报告成熟；适合秒杀 / Feed / 搜索 HTTP 压测 | GUI 偏重，复杂脚本维护成本高；WebSocket / SSE 需插件或独立客户端 |
